## 结论

“5090 没有吃满”不是单一问题。当前证据显示它由六类问题叠加造成：

1. 远端 Python、同步根目录、执行目录和命令入口曾漂移，导致训练或验证先被环境问题阻塞。
2. 早期训练默认值和部分历史命令偏保守：`device=cpu`、`batch=64`、`num_workers=0` 或 `batch=128` 这类入口容易让 5090 闲置。
3. 阶段 6.5 最大瓶颈不是 GPU 算力，而是编排串行：263 个窗口乘以 7 个候选的重放门禁会调度 1841 次重放，线性估算约 11 天。
4. 全量数据集物化曾把问题推到 90GB cgroup 边界，根因在 pandas 合并和数据集常驻内存，不是简单的“批量太大”。
5. 资源判断曾把系统负载、看板内存和页缓存当成硬失败，造成不必要停跑或错误降低并行度。
6. 性能优化证据分散在计划、变更记录、产物和代码里，没有统一的运行清单与性能分析合同，所以后续复盘经常只能依靠零散日志。

当前重构前的正确方向不是盲目加大批量或并行度，而是把“5090 运行合同”固化：固定解释器、固定干净工作树，显式记录批量、工作进程、分片和并行度，强制性能分析和资源采样，保留标准输出、标准错误、命令、总耗时和轮次耗时，并把吞吐与模型质量门禁一起看。

## P0 直接阻塞与吞吐瓶颈

### P0-1：远端 Python、同步根目录和干净工作树漂移

V2、`poly-arb-2`、`2-paper` 和 `sdk-live-trade` 都记录了同一条规则：5090 非交互 shell 可能解析到缺少 `pyarrow` 或 `torch` 的系统 Python，数据、训练、ONNX、校验器和冒烟测试命令默认应使用 `/root/miniconda3/bin/python3` 或显式激活 conda 基础环境。

直接旧错已经发生过：5090 conda 基础环境缺少 `pytest`，阻塞旧版训练测试发现。另一个旧错是普通 rsync 覆盖远端源码树，导致数据源根目录、目标根目录和提交或哈希回执不稳定。

影响：

- GPU 任务还没进入训练就被环境依赖挡住。
- 本地代码、远端代码和产物哈希不一致时，性能复盘没有可信基线。
- 同一命令在登录 shell 和非交互 shell 下可能使用不同 Python。

最低修正合同：

- 所有 5090 训练/验证命令显式写 `/root/miniconda3/bin/python3`。
- 远端执行根固定 `/root/autodl-tmp/V2-clean`。
- 默认同步是本地提交并推送，远端执行 `git pull --ff-only`；rsync 只用于明确范围的临时验证。
- 运行清单记录提交、工作树脏状态、完整命令、Python 路径、PyTorch 和 CUDA 版本。

### P0-2：训练入口默认值偏保守，容易让 5090 闲置

旧 `training/train.py` 默认 `device=cpu`、`batch_size=64`、`num_workers=0`。它虽支持 CUDA 锁页内存、持久工作进程、预取、AMP 和 `torch.compile`，但这些都不是默认启用。

`2-model-train` 的 M3/M5 调参记录更直接：批量为 128 时 GPU 利用率 18%、VRAM 1.4GB，被记录为“严重 GPU 饥饿”；批量为 2048 并启用编译后，GPU 利用率达到 72%、VRAM 4.1GB，轮次速度约快 17 倍。

影响：

- 新代理或新脚本如果直接使用默认训练入口，会把 5090 当作 CPU 或低并发机器使用。
- 多个工作树里的训练脚本和封装器默认值不完全一致，容易复发。

最低修正合同：

- 5090 专用启动器必须显式传入 `--device cuda`、批量、`--num-workers`，并明确锁页、持久化、非阻塞传输、AMP 和编译的取舍。
- 默认入口可以保守，但 5090 运行手册不能让保守默认成为训练默认。
- 每次运行的 `train_config` 或 `run_metadata` 必须保存加载器配置。

### P0-3：DataLoader 工作进程是已证实的吞吐杠杆

V2 性能分析产物显示：

- `num_workers=0`、批量为 2048：约 `4439 samples/s`。
- `num_workers=4`、批量为 2048：约 `10618 samples/s`。
- 同一性能分析中，主进程等待 DataLoader 批次的观测时间从约 `0.262s` 降到约 `0.000376s`；该数值受预取队列影响，不能单独解释为真实整理成本下降。

端到端 `samples/s` 提升约 2.39 倍，这不是推测优化，而是已有 5090 实测证据。

影响：

- 不配置工作进程会把瓶颈放在 Python 数据加载和批次拼接，而不是 GPU。
- 工作进程太多也可能触发文件句柄、I/O 或 CPU 过载，所以需要性能分析，而不是固定一个神奇值。

最低修正合同：

- 默认从 `num_workers=4` 开始，按数据集和批量进行性能分析。
- 记录 `samples/s`、DataLoader 等待、主机到设备（H2D）传输、训练步骤、GPU 利用率、RSS、工作进程 CPU 与 I/O 等待。
- 如果修改工作进程数量，必须留下性能分析前后对比。

### P0-4：大批量不是无脑收益，必须同时看吞吐和交易质量

V2 性能分析中，批量为 8192、工作进程为 4 时的 `samples/s` 与批量为 2048、工作进程为 4 时几乎相同，但 GPU 显存从约 5.3GB 升到约 19.2GB，进程 RSS 从约 17.6GB 升到约 30.0GB。

另一条 V2 阶段 A 原始变更记录证据更直接：旧 `AlphaV2Dataset` 在 GPU 训练前因 pandas 合并、字符串元数据和归一化全量拷贝而被终止，GPU 约 0%；修复后进入 GPU 训练，但批量为 4096 时已观测到约 `30.2GB / 32.6GB` 显存占用，继续使用 8192 的批量很可能 OOM 或没有有效余量。

`2-model-train` 的 M3 扫描也显示：批量为 4096 时达到更好的 PnL 和滚动最差表现；批量为 8192 时虽然 `val_top10` 更高，但端到端 PnL 和最差尾部表现变差。结论是适宜区间在 `[3072, 5120]`，不需要继续追加大于等于 8192 的批量。

影响：

- “显存占得更多”不等于训练更快或模型更好。
- 大批量可能牺牲泛化能力或尾部风险表现，并提高内存压力。

最低修正合同：

- 批量扫描的排名必须同时看吞吐、GPU 显存、RSS、验证或测试质量和滚动最差表现。
- 不把 GPU 利用率或 VRAM 占用单独作为成功指标。

### P0-5：阶段 6.5 重放编排串行是最大历史低效点

阶段 6.5 效率方案给出直接诊断：

- 转换导出已有 `--export-parallelism 8`。
- 转换校验器由单个 Python 进程串行扫描。
- 候选训练按候选串行。
- 重放门禁按候选和窗口串行。
- `all_train_boundary` 的 263 个窗口乘以 7 个候选等于 1841 条重放命令。
- 根据选定窗口耗时线性外推，仅重放约需 `264.6h = 11.0 days`。

报告明确指出这是编排低效，不是 GPU 原始算力不足。

当前 V2 代码已有修复方向：

- `--replay-parallelism`，默认 1，上限 16。
- p4、p8、p16 冒烟测试后再提升。
- 有效的既有重放检测和精确模型包路径验证。

最低修正合同：

- 所有完整重放必须先跑短矩阵冒烟测试。
- 默认采用安全配置，不直接使用 p16；p16 必须有 CPU、I/O、GPU 和 ORT 资源证据。
- 扩大到 p32、修改 ORT 或线程配置、修改重放调度器前，必须补齐 `vmstat`、`iostat`、PSI 和逐进程 CPU 证据。
- 重放报告、`candidate_report`、榜单和资源摘要必须一起落盘。

### P0-6：全量数据集或校验器物化会顶到 90GB cgroup

V2 阶段 A 已经有直接事故：首跑在 GPU 训练前停止，GPU 约 0%，CPU RSS 约 66.8GB；根因是旧 `AlphaV2Dataset` 通过 pandas 合并、重复字符串元数据和归一化全量拷贝把内存打爆。修复后的早期加载 RSS 降到约 6.9GB，说明物化路径才是第一故障点。

阶段 6.5 方案记录，修补重放并行后又遇到训练内存阻断：第一个完整候选在 `dataset_load` 阶段、cgroup 内存约 86.56GiB、Python RSS 约 52,423,616KiB 时停止。

后续变更记录也显示，完整校验器在重放前停止：`memory.current` 约 86.7GiB、校验器 RSS 约 42GiB；根因是旧校验器读取完整转换 Parquet 并保留全局行键状态。

当前 V2 代码已经把 MakerPolicyV2 训练改成分片路径：

- `DEFAULT_MAX_PATHS_PER_SHARD = 4`。
- `train_maker_policy_v2_smoke` 会按分片扫描、按分片运行 BC 或 RL 轮次。
- 报告中记录 `transition_shard_count` 和 `max_paths_per_shard`。

这只证明训练分片路径已有可复用修复；校验器的有界全局归约仍是未证明完成的重构合同，不能把 MakerPolicyV2 分片训练当作校验器修复证据。

最低修正合同：

- 完整边界训练必须使用分片且有界的加载方式。
- 完整校验器仍需有界全局归约：全局校验保持确定性归约，但中间行级数据必须有界。
- 运行清单必须记录 `max_paths_per_shard`、行数、RSS 峰值、cgroup 当前值和 `memory.events`。

## P1 运行治理与防复发合同

### P1-1：系统负载、页缓存和看板内存误诊会造成错误停跑或错误降低并行度

阶段 6.5 的 p16 首跑因系统负载超阈值被手动停止，但后续复盘认定这是结论不明的操作员停止，不是 p16 失败。证据显示当时 GPU 显存、总内存和 cgroup OOM 均安全，CPU 看板显示约 25 个 vCPU 中有 16 个繁忙。

随后 p16 重跑通过：

- 并行重放报告 16/16。
- CUDA 回退 0。
- ORT 中止 0。
- GPU 利用率最高 84%。
- GPU 显存最高 10319 / 32607 MiB。
- cgroup OOM / OOM kill 0 / 0。

内存规则也已修正：正常的 `file` 或页缓存增长不应清理；只有 OOM 或 `high` 增加、匿名内存接近上限、`memory.current` 贴近最大值且吞吐变差时才介入。

最低修正合同：

- 不使用系统负载或看板内存单项指标硬停止。
- 采样必须拆分 `anon/file/inactive_file/active_file/memory.events/throughput`。
- 资源异常动作必须分层：继续观测、降低并行度、停止新阶段、失败即关闭。

### P1-2：缺少统一性能证据合同，导致复盘靠碎片

V2 和 `sdk-live-trade` 的 AGENTS 已要求长训练或完整网格运行保留标准输出、标准错误、启动命令、总耗时、轮次耗时和 GPU、CPU 利用率采样。阶段 6.5 代码也已有 `ResourceSampler`，会记录系统负载、`MemAvailable`、磁盘、GPU 利用率或显存、cgroup 内存、进程 RSS 和 `memory.events`，并在摘要里计算平均值和最大值。

问题是这些合同没有被所有训练入口统一执行。不同工作树、不同阶段和不同封装器保存的证据粒度不一致。

最低修正合同：

- 所有 5090 运行输出同一类 `run_manifest.json`。
- 每次运行必须有 `resource_samples.csv` 或等价采样。
- 每个训练轮次必须有总耗时、每秒样本数、GPU 利用率摘要和内存峰值。
- 每个完整网格或重放必须有命令结果、标准输出、标准错误、产物清单和同步清单。

### P1-3：机器角色混用会放大“硬件没吃满”的误判

`sdk-live-trade` 明确：AWS 爱尔兰实盘主机只有约 2 vCPU、1.9GiB RAM，且没有交换空间；它只能运行二进制文件，不是构建或训练主机。`online-feedback` 也要求 `HardwareTierGate`：将 `live_exec`、`paper_runtime`、`training_gpu`、`research_sandbox` 分层；训练机允许训练和重放，实盘小服务器只允许轻量推理与执行。

影响：

- 把实盘主机的保守 ORT 或线程规则套到 5090，会低估训练并行能力。
- 把 5090 的训练并行配置套到实盘主机，会造成延迟、OOM 或构建事故。

最低修正合同：

- 每个命令先声明 `host_class`。
- 训练/回放命令只允许 `training_gpu`。
- 实盘和模拟盘只消费模型产物，不在弱服务器训练或构建。

## P1 补充问题

### P1-4：文件句柄上限是多工作进程训练的前置条件

`2-model-train` 变更记录显示，不带 `ulimit -n 65535` 时，验证评估进行到约 5% 即出现 `Too many open files`；加上后进入正常训练进度。

建议：5090 启动器统一前置 `ulimit -n 65535`，并在清单中记录 `ulimit -n` 当前值。

### P1-5：`torch_num_threads=104` 需要进入性能分析，而不是隐式默认

V2 性能分析产物记录 `torch_num_threads=104`。这不等于一定错误，但与 25 vCPU 训练主机边界不一致，可能和 DataLoader、ORT、Rust 重放并行互相抢占 CPU。

建议：不要立即硬编码线程数；先在 5090 运行合同中记录 `torch.get_num_threads()`、`OMP_NUM_THREADS`、`MKL_NUM_THREADS` 和 ORT 线程配置，再通过性能分析决定是否限制。

### P1-6：`poly-tx` 本轮没有直接 5090 训练证据

本轮在 `poly-tx` 中未发现 5090、GPU、训练、DataLoader 或性能分析器等直接命中。它更像数据采集项目，不是训练性能问题的直接来源。

建议：`poly-tx` 重构只需保证数据完整、Parquet 和清单可直接消费，避免训练前再做多步数据清洗；不要把 5090 训练优化塞进 `poly-tx`。

## 下一步建议

按最小改动顺序：

1. 先为 `5090_run_manifest` 编写数据模式和轻量校验器，不改训练逻辑。
2. 把 V2 现有 `ResourceSampler` 抽成复用模块或复用脚本，覆盖训练、校验器和重放。
3. 为当前主训练入口增加一个 5090 封装器：固定 Python、文件句柄上限、仓库根目录、清单和资源采样。
4. 对 `num_workers`、批量和 PyTorch 线程做 3 至 5 个短性能分析，先验证吞吐和内存。
5. 对重放继续使用 p4、p8、p16 冒烟测试递进，保留 p16 证据，不直接扩大到 p32。
6. 把相同规则同步到 V2、`2-model-train`、`poly-arb-2`、`2-paper`、`sdk-live-trade` 的活跃命令文档，避免工作树漂移。
