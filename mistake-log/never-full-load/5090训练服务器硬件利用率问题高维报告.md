## 结论

“5090 没有吃满”不是单一问题。当前证据显示它由六类问题叠加造成：

1. 远端 Python、sync root、执行目录和命令入口曾漂移，导致训练/验证先被环境问题阻塞。
2. 早期训练默认值和部分历史命令偏保守：`device=cpu`、`batch=64`、`num_workers=0` 或 batch=128 这类入口容易让 5090 闲置。
3. Phase 6.5 最大瓶颈不是 GPU 算力，而是编排串行：263 windows x 7 candidates 的 replay gate 会调度 1841 个 replay，线性估算约 11 天。
4. 全量数据集 materialization 曾把问题推到 90GB cgroup 边界，根因在 pandas/merge/Dataset 常驻内存，不是简单“batch 太大”。
5. 资源判断曾把 loadavg/dashboard memory/page cache 当成硬失败，造成不必要停跑或错误降并行。
6. 性能优化证据分散在 plan/changelog/artifact/code 里，没有统一的 run manifest / profiler contract，所以后续复盘经常只能靠零散日志。

当前重构前的正确方向不是盲目加大 batch 或并行度，而是把“5090 运行合同”固化：固定解释器、固定 clean worktree、显式 batch/worker/shard/parallelism、强制 profiler/resource samples、保留 stdout/stderr/命令/wall time/epoch time，并把吞吐与模型质量 gate 一起看。

## P0 直接阻塞 / 吞吐瓶颈

### P0-1：远端 Python / sync root / clean worktree 漂移

V2、poly-arb-2、2-paper 和 sdk-live-trade 都记录了同一条规则：5090 非交互 shell 可能解析到缺少 `pyarrow` / `torch` 的系统 Python，数据、训练、ONNX、validator、smoke 命令默认应使用 `/root/miniconda3/bin/python3` 或显式激活 conda base。

直接旧错已经发生过：5090 conda base 缺 `pytest` 阻塞 legacy training test discovery。另一个旧错是普通 rsync 覆盖远端源码树，导致 source root、target root、commit/hash receipt 不稳定。

影响：

- GPU 任务还没进入训练就被环境依赖挡住。
- 本地代码、远端代码、artifact hash 不一致时，性能复盘没有可信基线。
- 同一命令在 login shell 和非交互 shell 下可能走不同 Python。

最低修正合同：

- 所有 5090 训练/验证命令显式写 `/root/miniconda3/bin/python3`。
- 远端执行根固定 `/root/autodl-tmp/V2-clean`。
- 默认同步是本地 commit + push，远端 `git pull --ff-only`；rsync 只用于明确范围的临时验证。
- run manifest 记录 commit、dirty state、完整命令、Python 路径、torch/cuda 版本。

### P0-2：训练入口默认值偏保守，容易让 5090 闲置

旧 `training/train.py` 默认 `device=cpu`、`batch_size=64`、`num_workers=0`。它虽支持 CUDA pin memory、persistent workers、prefetch、AMP、`torch.compile`，但这些都不是默认打开。

2-model-train 的 M3/M5 调参记录更直接：batch=128 时 GPU util 18%、VRAM 1.4GB，被记录为“严重 GPU 饥饿”；batch=2048 + compile 后 GPU util 到 72%、VRAM 4.1GB，epoch 时长约 17x faster。

影响：

- 新 agent 或新脚本如果直接拿默认训练入口跑，会把 5090 当 CPU/低并发机器用。
- 多 worktree 里的训练脚本和 wrapper 默认不完全一致，容易复发。

最低修正合同：

- 5090 专用 launcher 必须显式传 `--device cuda`、batch、`--num-workers`、pin/persistent/non-blocking/AMP/compile 的取舍。
- 默认入口可以保守，但 5090 运行手册不能让保守默认成为训练默认。
- 每个 run 的 `train_config` / `run_metadata` 必须保存 loader config。

### P0-3：DataLoader worker 是已证实的吞吐杠杆

V2 profile artifact 显示：

- `num_workers=0`、batch=2048：约 `4439 samples/s`。
- `num_workers=4`、batch=2048：约 `10618 samples/s`。
- 同一 profile 里主进程等待 DataLoader batch 的观测时间从约 `0.262s` 降到约 `0.000376s`；该数值受 prefetch queue 影响，不能单独解释为真实 collate 成本下降。

端到端 `samples/s` 提升约 2.39x，这不是推测优化，而是已有 5090 实测证据。

影响：

- 不配 worker 会把瓶颈放在 Python 数据加载/拼 batch，而不是 GPU。
- worker 太多也可能触发文件句柄、I/O、CPU 过载，所以需要 profile，而不是固定一个神奇值。

最低修正合同：

- 默认从 `num_workers=4` 开始，按数据集和 batch profile。
- 记录 `samples/s`、DataLoader wait、H2D、train step、GPU util、RSS、worker CPU/iowait。
- 如果改 worker，必须留下 profile 前后对比。

### P0-4：大 batch 不是无脑收益，必须同时看吞吐和交易质量

V2 profile 里 batch=8192 + workers=4 的 `samples/s` 与 batch=2048 + workers=4 几乎相同，但 GPU memory 从约 5.3GB 升到约 19.2GB，进程 RSS 从约 17.6GB 升到约 30.0GB。

另一条 V2 Stage A 原始 changelog 证据更直接：旧 `AlphaV2Dataset` 在 GPU 训练前因 pandas/merge/字符串 metadata/normalization 全量拷贝被 kill，GPU 约 0%；修复后进入 GPU 训练，但 batch=4096 已观测到约 `30.2GB / 32.6GB` 显存占用，继续 batch=8192 很可能 OOM 或没有有效余量。

2-model-train 的 M3 sweep 也显示：batch=4096 达到更好的 PnL/rolling worst，batch=8192 虽然 val_top10 更高，但端到端 PnL 和 worst tail 变差；结论是 sweet spot 在 `[3072, 5120]`，不需要继续追加 batch >= 8192。

影响：

- “显存占得更多”不等于训练更快或模型更好。
- 大 batch 可能牺牲泛化/尾部风险，并提高内存压力。

最低修正合同：

- batch sweep 的排名必须同时看 throughput、GPU memory、RSS、val/test quality、rolling worst。
- 不把 GPU util 或 VRAM 占用单独作为成功指标。

### P0-5：Phase 6.5 replay 编排串行是最大历史低效点

Phase 6.5 效率方案给出直接诊断：

- transition export 已有 `--export-parallelism 8`。
- transition validator 是单 Python 串行 scan。
- candidate training 按 candidate 串行。
- replay gate 按 candidate/window 串行。
- `all_train_boundary` 263 windows x 7 candidates = 1841 replay commands。
- selected-window timing 线性外推 replay-only 约 `264.6h = 11.0 days`。

报告明确说这是 orchestration inefficiency，不是 raw GPU capacity 不足。

当前 V2 代码已有修复方向：

- `--replay-parallelism`，默认 1，上限 16。
- p4/p8/p16 smoke 后再提升。
- valid existing replay detection 和 exact bundle 路径验证。

最低修正合同：

- 所有 full replay 必须先跑 short matrix smoke。
- 默认 safe，不直接 p16；p16 必须有 CPU/I/O/GPU/ORT resource evidence。
- 扩大到 p32、改 ORT/thread 或改 replay scheduler 前，必须补齐 `vmstat`、`iostat`、PSI、per-process CPU 证据。
- replay report、candidate_report、leaderboard、resource summary 必须一起落盘。

### P0-6：全量 Dataset / validator materialization 会顶到 90GB cgroup

V2 Stage A 已经有直接事故：首跑在 GPU 训练前停止，GPU 约 0%，CPU RSS 约 66.8GB；根因是旧 `AlphaV2Dataset` 通过 pandas merge、重复字符串 metadata 和 normalization 全量拷贝把内存打爆。修复后的早期 load RSS 降到约 6.9GB，说明 materialization 路径才是第一故障点。

Phase 6.5 方案记录，replay parallelism patched 后又遇到 training memory blocker：第一个 full candidate 在 `dataset_load` 约 86.56GiB cgroup memory / 52,423,616KiB Python RSS 时停止。

后续 changelog 也记录 full validator 在 replay 前停止：`memory.current` 约 86.7GiB、validator RSS 约 42GiB，根因是 old validator 读取 full transition parquet 并保留 global row-key state。

当前 V2 代码已经把 MakerPolicyV2 训练改成 shard path：

- `DEFAULT_MAX_PATHS_PER_SHARD = 4`。
- `train_maker_policy_v2_smoke` 会按 shard 扫描、按 shard 跑 BC/RL epoch。
- 报告里记录 `transition_shard_count` 和 `max_paths_per_shard`。

这只证明 training shard path 已有可复用修复；validator 的 bounded global reduction 仍是未证明完成的重构合同，不能把 MakerPolicyV2 shard 训练当作 validator 修复证据。

最低修正合同：

- full-boundary training 必须使用 sharded/bounded loading。
- full validator 仍需 bounded global reduction：全局校验保持 deterministic reduction，但中间行级数据必须 bounded。
- run manifest 必须记录 `max_paths_per_shard`、row counts、peak RSS、cgroup current、memory.events。

## P1 运行治理 / 防复发合同

### P1-1：loadavg / page cache / dashboard memory 误诊会造成错误停跑或错误降并行

Phase 6.5 p16 首跑被手动停在 loadavg 超阈值，但后续复盘认定是 inconclusive operator stop，不是 p16 failure。证据显示当时 GPU memory、total memory、cgroup OOM 都安全，CPU dashboard 约 16 busy vCPU / 25 vCPU。

随后 p16 rerun 通过：

- parallel replay reports 16/16。
- CUDA fallback 0。
- ORT abort 0。
- GPU util max 84%。
- GPU memory max 10319 / 32607 MiB。
- cgroup OOM / OOM kill 0 / 0。

内存规则也已修正：正常 `file`/page cache 增长不应清理；只有 OOM/high、anon 接近上限、memory.current 贴近 max 且吞吐变差时才介入。

最低修正合同：

- 不用 loadavg 或 dashboard memory 单指标 hard stop。
- 采样必须拆分 `anon/file/inactive_file/active_file/memory.events/throughput`。
- 资源异常动作必须分层：继续观测、降并行、停止新阶段、fail closed。

### P1-2：缺少统一性能证据合同，导致复盘靠碎片

V2 和 sdk-live-trade AGENTS 已要求长训练/full-grid run 保留 stdout/stderr、启动命令、wall time/epoch time、GPU/CPU utilization samples。Phase 6.5 代码也已有 `ResourceSampler`，会记录 load、MemAvailable、disk、GPU util/mem、cgroup memory、process RSS、memory.events，并在 summary 里计算 avg/max。

问题是这些合同没有被所有训练入口统一执行。不同 worktree、不同阶段、不同 wrapper 保存的证据粒度不一致。

最低修正合同：

- 所有 5090 run 输出同一类 `run_manifest.json`。
- 每个 run 必须有 `resource_samples.csv` 或等价采样。
- 每个训练 epoch 必须有 wall time、samples/s、GPU util summary、peak memory。
- 每个 full-grid/replay 必须有 command_results、stdout/stderr、artifact manifest、sync manifest。

### P1-3：机器角色混用会放大“硬件没吃满”的误判

sdk-live-trade 明确：AWS Ireland live host 只有约 2 vCPU / 1.9GiB RAM / no swap，只能运行 binary，不是 build/training host。online-feedback 也要求 `HardwareTierGate`：live_exec、paper_runtime、training_gpu、research_sandbox 分层，训练机允许训练/replay，live 小服务器只允许轻量推理与执行。

影响：

- 把 live host 的保守 ORT/thread 规则套到 5090，会低估训练并行。
- 把 5090 的训练并行套到 live host，会造成延迟、OOM 或 build 事故。

最低修正合同：

- 每个命令先声明 `host_class`。
- 训练/回放命令只允许 `training_gpu`。
- live/paper 只消费模型 artifact，不在弱服务器训练或构建。

## P1 补充问题

### P1-4：文件句柄/ulimit 是 multi-worker 训练的前置条件

2-model-train changelog 记录，不带 `ulimit -n 65535` 时，val eval 约 5% 即 `Too many open files`；加上后进入正常训练进度。

建议：5090 launcher 统一前置 `ulimit -n 65535`，并在 manifest 记录 `ulimit -n` 当前值。

### P1-5：`torch_num_threads=104` 需要进入 profile，而不是隐式默认

V2 profile artifacts 记录 `torch_num_threads=104`。这不等于一定错误，但和 25 vCPU 训练主机边界不一致，可能和 DataLoader / ORT / Rust replay 并行互相抢 CPU。

建议：不要立即硬编码线程数；先在 5090 run contract 中记录 `torch.get_num_threads()`、`OMP_NUM_THREADS`、`MKL_NUM_THREADS`、ORT thread config，再用 profile 决定是否限制。

### P1-6：`poly-tx` 本轮没有直接 5090 训练证据

本轮在 `poly-tx` 中未发现 5090、GPU、训练、DataLoader、profiler 等直接命中。它更像数据采集项目，不是训练性能问题的直接来源。

建议：`poly-tx` 重构只需保证数据完整、parquet/manifest 直接可消费，避免训练前再做多步数据清洗；不要把 5090 训练优化塞进 `poly-tx`。

## 下一步建议

按最小改动顺序：

1. 先写一个 `5090_run_manifest` schema 和轻量 validator，不改训练逻辑。
2. 把 V2 现有 `ResourceSampler` 抽成复用模块或复用脚本，覆盖训练、validator、replay。
3. 为当前主训练入口加一个 5090 wrapper：固定 Python、ulimit、repo root、manifest、resource samples。
4. 对 `num_workers`、batch、torch threads 做 3-5 个短 profile，先验证吞吐和内存。
5. 对 replay 继续使用 p4 -> p8 -> p16 smoke，保留 p16 证据，不直接扩大到 p32。
6. 把相同规则同步到 V2、2-model-train、poly-arb-2、2-paper、sdk-live-trade 的活跃命令文档，避免 worktree 漂移。
