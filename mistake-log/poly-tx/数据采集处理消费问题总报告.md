## 结论

当前 `poly-tx` 不能作为新系统的数据层基础直接复用。它可以作为历史采集雏形，但必须先重构为具备市场发现门禁、T-30s 预加载、多源统一时间轴、V2 类型化原始 Parquet，以及产物和运行清单的数据服务。

最关键的判断：

1. `poly-tx` 只提前 3 秒建连，不满足 T-30s 预加载。
2. 默认首次目标是下一个窗口，不采当前活跃市场。
3. Binance/RTDS 辅助源等到首个 Polymarket 市场成功后才启动，预加载窗口会缺源。
4. Polymarket 采集写 NDJSON，且丢弃 `new_market`，不满足后续市场发现/预取证据要求。
5. V2 已能消费类型化原始 Parquet，但要求 `raw_json`、数据源类型元数据，以及清单、标签、校验和 `tick_stream_v2` 合同，不能只把文件后缀改成 `.parquet`。
6. 错误记录中与数据直接相关的旧错集中在：市场发现、预取与活跃状态边界、市场切换缓冲区、产物原子性、归档完整性、清单与标签边界、资源水位和执行反馈标签。

## P0 问题

### P0-1：T-30s 预加载缺失

`poly-tx` 的预热常量是 `PRE_SUBSCRIBE_LEAD_SECONDS = 3`，调度条件是 `now + 3 >= target_ts`。分段辅助源也复用这个 3 秒预热时间。新系统要求“活跃市场开始前 30 秒预加载数据源输入给模型”，当前设计不满足。

影响：

- 训练或回放如果要覆盖 `T-30s -> T+300s`，采集源天然少了 `T-30s -> T-3s`。
- 实盘运行时不能验证“模型从预加载开始就持续看数据”的合同。
- 市场切换前 30 秒准备下一市场上下文无法落地。

### P0-2：默认启动跳过当前活跃市场

`next_spawn_target_ts()` 首次返回 `current_window_ts(now) + step`。除非手动传入 `--start-market-ts`，否则进程启动时不会采集当前活跃市场，而是等待下一个市场。

影响：

- 采集中断后重启会漏掉当前市场。
- 数据缺口会被后续 V2 校验和缺口检查发现，但已经无法补齐完整市场数据。
- 若新系统自检和热身后立即进入活跃市场，数据层没有当前市场的完整上下文。

### P0-3：辅助源启动被 Polymarket 首个 `worker`（异步任务）绑住

Binance 订单簿和 RTDS Chainlink 只在第一个 Polymarket `worker`（异步任务）成功启动后拉起。若 Gamma `slug` 标识或 CLOB 资产 `token` 查询延迟、失败或重试，辅助源也同步变晚。

影响：

- 多源输入的覆盖起点不一致。
- `validation.parquet` 可能出现数据源缺口或丢弃。
- 模型看到的 Polymarket、Binance、Chainlink 可见时间不一致，容易制造伪信号。

### P0-4：市场发现只靠 `slug` 标识，且丢弃 `new_market`

当前 `fetch_asset_ids_by_slug()` 通过 Gamma `slug` 标识查找 `clobTokenIds`，没有保存 `active`（活跃）、`closed`（关闭）、`acceptingOrders`（接受订单）、`conditionId`（条件标识）、`tick`（最小价格变动单位）、`min_size`（最小数量）、`fee`（费用）和 `reward`（奖励）等市场上下文。采集端还会过滤 `event_type == "new_market"`。

影响：

- 与 `online-feedback` 的 OF-18/OF-30 冲突：`slug` 标识只能生成候选，不能作为交易授权。
- 预加载下一市场时无法证明 `candidate`（候选）、`prefetched`（已预取）、`active`（活跃）和 `retired`（已退役）四种状态的边界。
- 平台创建延迟、时钟偏移和 `slug` 变体会造成漏掉市场或市场错配。

### P0-5：市场切换状态污染未被独立建模

错误记录已把市场切换缓冲区泄漏列为高风险旧错：已预取上下文不能污染活跃提交路径，旧特征缓冲区、序列缓冲区、订单簿状态和未结订单（`open order`）状态不能泄漏到新的 `market_id`。

最低要求：

- 切换前执行撤单和审计。
- 每个市场独立保存特征、订单簿、订单和账户状态。
- 切换时重置每个市场的缓冲区，并记录重置回执。
- 新市场快照和 `seq_len` 预热完成前进入 `no-submit`（禁止提交）和 `no-quote`（禁止报价）状态。
- 已预取上下文只能准备数据，切换门禁成功后，提交路径才能使用新的 CLOB 资产 `token`。

### P0-6：账户/订单/持仓输入没有进入统一数据层

`poly-tx` 的 `user_channel` 是独立 CLI，只查当前挂单并监听事件，主要写日志。头寸信息在赎回路径用于查询可赎回仓位。本轮证据没有显示这些账户源进入 `ws-series` 的统一时间轴，也没有显示它们落盘为模型可消费的数据源；待超越价格、活跃挂单数、本地账本、未结订单（`open orders`）和当前头寸也没有出现在当前采集合同中。

影响：

- 新流程第 4 点“模型持续看到待超越价格、当前持仓和未结订单（`open order`）”当前没有数据合同。
- 不能从采集层直接构造执行反馈标签。
- 订单生命周期与账务权威源仍会分散，复发旧的账本与平台快照混淆。

### P0-7：从 NDJSON 转为 Parquet 不是简单替换后缀

V2 支持类型化原始 Parquet，但依赖严格合同：

- 数据模式元数据：`parquet_raw_layout_version=v1`
- 数据模式元数据：`parquet_raw_source_kind`
- Polymarket 订单簿和 Chainlink 必须保留可解析的 `raw_json`
- `aggTrades` 必须满足类型化列合同
- 下游必须联合消费 `manifest.parquet + labels.parquet`

因此，`poly-tx` 直接写入 Parquet 的正确目标是“V2 类型化原始 Parquet 镜像”，不是任意 Parquet。

### P0-8：直接写入 Parquet 会放大未完整写入的产物风险

Parquet 文件通常要关闭后才稳定可读。如果新采集器直接写最终 `.parquet`，V2 的发现过程可能读到未完整写入的文件。旧错误记录已把产物写入器、数据模式、运行清单和 SHA-256 列为 P0。

最低要求：

- 写入 `*.tmp` 或 `*-running.parquet`。
- 关闭后原子重命名。
- 运行清单记录必需文件、行数、SHA-256、数据模式版本和数据源覆盖。
- 发现过程只读最终化 Parquet。

### P0-9：归档与数据完整性旧错必须前移到采集门禁

`poly-arb-2` 历史归档出现过 `.rsync-partial` 混入原始数据树，导致迁移和覆盖检查失败；V2 规范数据也记录过损坏归档与排除清单。数据完整性问题不能等到训练阶段才发现。

采集重构门禁必须包含：

- 最终化文件数。
- 行数。
- 数据源覆盖与缺口。
- SHA-256 与内容链。
- 排除 `.rsync-partial`、运行中和临时文件。
- 磁盘水位。
- 归档上传与列表获取重试。

### P0-10：资源水位必须是采集运行门禁

T-30s 预加载、活跃市场加下一市场的双市场采集，以及 JSONL、Parquet 和 systemd 日志并发写入，都会直接影响数据完整性。如果磁盘、cgroup、PSI 或 systemd 日志水位异常，继续采集可能造成静默数据丢失、未完整写入的 Parquet、`fail-open`（故障时放行）或无法复盘。

最低要求：

- 运行清单记录 cgroup 的 `memory.current`、`memory.stat`、`memory.events`、PSI、匿名内存、文件缓存和 slab。
- 记录磁盘可用空间、`artifact_dir_bytes` 和 systemd 日志限额状态。
- 低于磁盘或内存硬阈值时，进入 `no-submit`（禁止提交）、`cancel-only`（仅撤单）状态，或停止新市场采集。
- 先保护已采数据的原子发布和 SHA-256 清单，再尝试恢复。

### P0-11：清单、标签与训练边界不能混用

V2 明确把市场发现与数据源路径放在 `manifest.parquet`，把待超越价格（`p2b`）、市场判定结果和标签放在 `labels.parquet`，把数据源缺口和丢弃放在 `validation.parquet`。训练消费端还要求规范切分和严格时间前向切分。

影响：

- 采集成功不等于训练边界批准。
- 规范根目录完整不等于可以扩大训练范围。
- 只读清单或只看 Parquet 存在，会复发归档清单与标签边界错误。

### P0-12：实盘和模拟盘的事实源不能被单一路径 Parquet 替代

历史模拟盘经验明确：模拟盘和实盘运行应保留 JSONL 事实源，Parquet 更适合后处理、压缩和训练镜像。对离线历史采集器，可以直接写入类型化原始 Parquet；对实盘和模拟盘运行时，应保留追加并刷新的事件日志或等价不可丢事件日志，再压实或合并整理为 Parquet（`compact parquet`）。

## P1 问题

### P1-1：`asset_ids` 查询失败会卡住后续目标

`collect.rs` 只有在成功启动 `worker`（异步任务）后才推进 `spawned_target_ts`。如果某个 `slug` 标识在创建延迟或接口抖动时一直找不到 CLOB 资产 `token`，调度会持续重试同一目标，而不是在过期后跳到当前应采窗口。

建议：记录遗漏后，在过期阈值跳过或重新按当前时间计算目标，同时写入 `discovery_miss_rate`。

### P1-2：`market_resolved` 关闭条件可能提前结束

当前关闭条件检查事件资产编号是否都属于已订阅集合，而不是已订阅集合是否都已完成市场判定。若出现单腿市场判定事件，可能提前关闭该市场 `worker`（异步任务）。

建议：改为已订阅集合的子集或相等语义，并编写单元测试覆盖两腿 CLOB 资产 `token`。

### P1-3：Binance aggTrades 实时/离线边界未被统一

V2 每日归档的当前第 2 步仍是回填 Binance `aggTrades`；本轮在 `poly-tx` 采集源码和文档中未发现实时 `aggTrades` 采集器。若新模型需要事件级连续输入，`aggTrades` 不应只靠日后补齐。

建议：新采集器至少明确：

- 订单簿深度是实时源。
- `aggTrades` 是实时源还是离线回填。
- 若仍采用回填，训练和实盘的可见性不得假装一致。

### P1-4：数据模式不匹配已经在模拟盘路径出现过

`2-paper-trade` 变更记录显示，转换器写入 `aggtrade` Parquet 时只写 4 列，但数据流水线严格读取 M0 真实 10 列，最终出现 `KeyError: 'symbol'`。这证明“写入 Parquet”本身不够，必须符合 V2 数据模式。

### P1-5：资源误诊仍需保留诊断遥测

错误记录已记录页缓存和资源压力误诊。P0 门禁负责保全以及 `no-submit`（禁止提交）或 `fail-closed`（故障时拒绝）动作；P1 遥测负责避免把正常页缓存、看板内存或系统负载均值误判成流水线或训练失败。运行清单仍应记录 cgroup、PSI、磁盘、systemd 日志、产物字节数和阶段延迟。

## 可优化的 V2 步骤

当前归档和数据流水线的典型链路：

1. 下载订单簿采集数据。
2. 回填 Binance `aggTrades` CSV。
3. 将原始数据迁移为类型化 Parquet。
4. 校验 Parquet 与原始数据的覆盖一致性。
5. 使用 `pigz` 压缩原始数据。
6. 使用 `pigz` 压缩 Parquet。
7. 上传。

`poly-tx` 直接写入 V2 类型化原始 Parquet 后，可以减少：

- 第 3 步的原始数据到类型化 Parquet 迁移。
- 第 4 步的部分原始数据与 Parquet 一致性比对。
- 部分重复的原始数据归档成本；但类型化原始 Parquet 仍必须保留 `raw_json`、数据源元数据、清单、哈希和归档证据。

不能减少：

- `manifest.parquet`
- `labels.parquet`
- `validation.parquet`
- Chainlink 与伪标签处理
- 资产映射就绪状态
- `tick_stream_v2` 导出
- 特征元数据检查
- 严格切分和规范边界审批
- 产物与资源完整性验证

## 新数据采集重构的最低验收合同

### 采集合同

- 每个 5 分钟市场都有候选、已预取、活跃和已退役状态，精确状态链为 `candidate -> prefetched -> active -> retired`。
- 从 `T-30s` 开始采集下一市场的 Polymarket 市场 WebSocket（`market WS`）数据。
- Binance 订单簿、Binance `aggTrades`、Chainlink 与市场 `worker`（异步任务）解耦启动。
- 当前活跃市场和已预取的下一市场不能共享账本、`order token`（订单使用的 CLOB 资产代币标识）或提交路径。
- 市场切换必须执行撤单、审计、重置和预热；每个市场的特征、订单簿、订单和账户缓冲区必须清空或隔离。
- Polymarket `new_market`、市场元数据、CLOB `token ids`（资产标识）、`condition_id`、`tick`（最小价格变动单位）、`min size`（最小数量）、`fee`（费用）和 `reward`（奖励）都要落盘。

### 文件合同

- 直接输出 V2 类型化原始 Parquet。
- 每个数据源 Parquet 都带 `raw_json` 和 `parquet_raw_source_kind`。
- 文件只通过原子重命名发布。
- 运行清单记录行数、SHA-256、数据源覆盖、数据模式版本和开始/结束时间。
- 临时文件、运行中文件和 `.rsync-partial` 文件不进入发现过程。

### 消费合同

- 离线开发消费清单、标签、校验结果和数据表，对应合同组合为 `manifest + labels + validation + tables`。
- 训练消费事件流、标签和规范切分，对应合同组合为 `tick_stream_v2 + labels + canonical split`。
- 实盘和模拟盘消费权威运行时事件日志与压实或合并整理后的 Parquet 镜像（`compact parquet mirror`）。
- 执行反馈标签记录决策、动作、订单簿、账户和订单生命周期的因果上下文。

## 下一步建议

先不要直接改大系统。最小可靠实施顺序：

1. 冻结市场发现、预加载和数据源覆盖合同：`slug` 候选加活跃扫描双路径、T-30s，以及 `candidate`（候选）、`prefetched`（已预取）、`active`（活跃）和 `retired`（已退役）状态。
2. 定义市场切换门禁：撤单、审计、重置和预热；每个市场的缓冲区隔离；预热前进入 `no-submit`（禁止提交）和 `no-quote`（禁止报价）状态。
3. 定义 V2 类型化原始 Parquet 写入器和原子发布合同。
4. 把 `PRE_SUBSCRIBE_LEAD_SECONDS` 从硬编码 3 秒改成 30 秒需求合同，并补测试。
5. 拆出独立数据源采集器：Polymarket 当前市场与预取市场、Binance 订单簿、Binance `aggTrades` 和 Chainlink。
6. 新增运行清单和覆盖校验器，先在 1-2 个市场上验证 V2 数据流水线可消费。
7. 最后再把实盘和模拟盘的用户通道、未结订单（`open orders`）、头寸和待超越价格接入统一时间轴。
