## P0：重构阻断级错误

这些问题如果没有在新架构中先解决，重构后的系统很容易继续复现旧错误，甚至把错误包装成更复杂的实现。

| 排名 | 错误主题 | 旧错误表现 | 重构前要求 |
| --- | --- | --- | --- |
| 1 | 权威源混淆 | 把 checkpoint 当成整计划完成，把 no-live / validator / smoke stdout 当成 live-funds 成功，把 dashboard fresh 当成账务正确，把 replay leaderboard 当成可上线依据。 | 新系统必须显式拆分 plan cursor、runtime state、validator result、platform snapshot、local ledger、report/dashboard 六类权威源。任何结论必须写明来自哪一层；只有 dashboard 被当成交易或账务权威时才是 P0。 |
| 2 | SDK-first 边界被绕过 | 曾多次出现 raw REST、manual signing、自建 client、synthetic alias、第二解释器等 shadow implementation 倾向。 | Polymarket 相关能力必须先使用官方 Rust SDK。SDK 缺口必须先形成缺口说明和用户决策，不允许在重构中暗自旁路。 |
| 3 | 订单生命周期语义不统一 | cancel TTL、matched cancel、generic not found、partial fill、late user-channel、synthetic event、open order audit 被分散解释。 | 重构必须先定义 `NormalizedOrderEvent` 或等价权威事件层，把 SDK submit、user-channel、CLOB query、cancel、fill、timeout、synthetic audit 归一化。 |
| 4 | submit accepted 与未知结果边界错误 | 把 HTTP 成功、SDK 返回、accepted 字段、per-order success、实际入簿、后续查询混成一个成功状态；timeout 后可能重复提交。 | 所有 submit 必须有 accepted classifier、unknown-outcome reconciliation、idempotency/client id 策略和重试禁区。 |
| 5 | 本地 ledger、钱包与平台 snapshot 权威混淆 | 本地账本、Data API positions/value、sellable balance、allowance、wallet/funder/signature_type、order history、active resting count 各自语义不同，却被互相替代；`poly-tx` 中 user-channel、positions/redeem、open orders 仍是独立命令/日志，没有进入统一模型输入时间轴。 | 新账务层必须区分 ledger-derived、platform-derived、SDK-derived、reconciled 四种状态；wallet/funder/signature/allowance source map 必须先于下单完成校验；price-to-beat、current position、open order、active resting count 必须成为 active market 的统一可见输入。 |
| 6 | sellable maturity 与平台拒单规则误读 | 买入成功后立即卖出、sellable balance 未成熟、平台 rejected、Data API 延迟等被误判成策略或 SDK bug。 | 交易状态机必须有 maturity / settlement / sellable gate；卖出前读取平台可卖余额或明确降级为 no-submit。 |
| 7 | artifact 写入、schema、持久化失败 | 多次出现报告看起来完成，但关键 JSONL、audit、fail trace、schema 字段或 final writer 缺失；直接写 parquet 时还会放大 partial artifact、缩水 schema、缺 `raw_json`/metadata 的风险。 | 重构必须把 artifact writer 当作一等组件：schema version、atomic write、required files、fail trace、run manifest、sha256 都是 gate 条件；parquet 只能以 tmp/running 路径写入，close 后 atomic rename，discovery 只读 finalized artifact。 |
| 8 | fail-close 严重度过宽或过窄 | 非交易问题触发过度停机，或交易安全问题只给 warning；validator 又形成第二业务解释器。 | gate verdict 必须有限枚举并有明确动作：pass、warning、no-submit、cancel-only、fail-closed。validator 只能校验，不得发明业务语义。 |
| 9 | 市场发现、T-30s 预加载与市场切换状态污染 | prefetched context 被当成 active market；换市场后 sequence buffer、feature buffer、active order、snapshot 没有严格清理；`poly-tx` 只提前 3 秒建连，默认首次目标是下一个窗口，辅助源在首个 Polymarket worker 成功后才启动，slug-only 发现还丢弃 `new_market`。 | market context 必须区分 candidate、prefetched、active、retired；market switch 必须执行 cancel/audit/reset/warmup 顺序；数据层必须覆盖当前 active market 和 T-30s prefetched next market，Polymarket/Binance/Chainlink/account 源独立启动并记录 market metadata、CLOB token ids、condition_id、tick/min size、fee/reward。 |
| 10 | Execution Reality Gate 缺失 | 训练和 replay 先行，但真实执行里的 queue、partial fill、cancel/replace、post-only reject、tick、latency、fee/rebate、slippage 没有先建模。 | 新训练和策略评估必须先过执行现实门；没有执行反馈标签，不得把离线 leaderboard 当成上线依据。 |
| 11 | 模型 bundle 与运行时 contract 漂移 | alias、bundle lineage、sidecar、normalizer、feature 维度、enabled slots、runtime consumer 之间多次不一致。 | 模型包必须有唯一 lineage、schema、input/output shape、normalizer hash、feature contract、runtime preflight。 |
| 12 | 采集/处理/训练边界与数据完整性错误 | new_unassigned_pool、canonical root、time split、purge/embargo、test rerank、archive corruption、feature 65/76/160 维混淆反复出现；`poly-tx` 仍以 NDJSON 为主，而 V2 消费 typed raw parquet、`manifest.parquet + labels.parquet + validation.parquet + tick_stream_v2` 合同；live/paper 还需要 append JSONL 或等价不可丢 event log，不能只保留单一路径 parquet。 | 训练入口必须先冻结 data boundary、split policy、feature/label contract、archive integrity，不允许训练脚本自行扩边界；采集器直接写 parquet 时必须写 V2 typed raw parquet mirror，保留 `raw_json`、`parquet_raw_source_kind`、schema metadata、source coverage、row count、sha256，并把 `.rsync-partial`/running/temp 文件排除在 discovery 外。 |
| 13 | paper lifecycle 与账务闭合混淆 | order lifecycle 100% closed 不等于 NAV、realized PnL、adjusted PnL、profile-local timestamp、fee formula 正确。 | paper runtime 必须拆分 order closure、position closure、accounting closure、report closure。dashboard 只展示，不做账务权威源。 |
| 14 | 部署边界、硬件角色与训练资源误判 | 在弱服务器上编译、运行过重任务、ORT 线程/内存/磁盘/日志水位无门禁，容易把资源问题误判成模型或交易问题；5090 训练侧还出现过 Python/sync root 漂移、保守默认入口、DataLoader worker 未用、replay 串行、Dataset/validator materialization、loadavg/page cache 误停等问题。 | live server 只运行发布产物；本地构建二进制并记录 commit、sha256、产物路径。本地开发/构建路径是 `/home/chillchill/btc-updown-marketmaker`；远端服务器工作目录统一写作 `~/btc-updown-marketmaker`，远端禁止在 weak live 服务器 cargo build/test/check/fmt，路径越界必须 fail closed。训练机命令必须声明 `host_class=training_gpu`、固定 `/root/miniconda3/bin/python3` 和 clean worktree，记录 batch/worker/thread/shard/replay parallelism、ulimit、stdout/stderr、resource samples、quality gate。 |
| 15 | online rule freshness 与外部平台规则未入 gate | 费率、奖励、tick、order version、rate limit、WSS freshness、endpoint 迁移、SDK 版本变化没有统一新鲜度检查。 | 重构必须有 OnlineFeedbackGate，并把规则版本、last checked、官方文档、SDK 版本、市场 metadata 放入启动门。 |
| 16 | 供应链与密钥隔离门禁缺失 | 外部 bot、依赖、脚本或参考仓库可能接触 `.env`、钱包、API key、网络出站和运行环境，却被当成普通参考材料。 | SupplyChainGate 必须是 P0：外部材料只能 pinned readonly，默认禁止 install/run，禁止读取 secrets，必要网络出站和执行权限必须显式批准并留证。 |

## P1：高风险设计债

这些问题不一定每次直接触发实盘损失，但会让重构后的系统继续不可解释、不可审计或不可训练。

| 排名 | 错误主题 | 旧错误表现 | 重构前要求 |
| --- | --- | --- | --- |
| 17 | review/docs sync 漏洞 | 代码、计划、changelog、lastest-command、review 结论不同步，导致阶段状态被误读。 | 重要阶段必须同步计划、变更记录、命令交接和验证证据。 |
| 18 | model promotion 边界不清 | bundle 生成被误认为 promotion，replay 好看被误认为 live ready。 | 生成、验证、候选、灰度、上线必须是不同状态。 |
| 19 | action surface collapse 被 leaderboard 掩盖 | 模型在 replay 分数上看似可用，但 action distribution 塌缩、side/action/size 没有真实策略能力。 | 模型评估必须先做 action-surface audit，再看 leaderboard。 |
| 20 | maker reward/action 语义反复重写 | reward finalization、churn、support metadata、zero support、unsupported reason 规则不稳定。 | MakerRewardV2、MakerActionV2、SizeHead、Flip 语义必须固定成 contract。 |
| 21 | 远端 GPU / Python / rsync 路径混乱 | 5090/3090 解释器、sync root、remote path、resume output 多次漂移；非交互 `python3` 可能缺 `pyarrow`/`torch`，rsync 覆盖源码树会让 commit/hash receipt 不稳定。 | 训练机只接受显式 source root、target root、interpreter、resume policy；5090 默认 `/root/miniconda3/bin/python3`，执行根固定 `/root/autodl-tmp/V2-clean`，优先本地 commit + push 后远端 `git pull --ff-only`。 |
| 22 | 资源压力被误归因 | OOM、page cache、terminal done row、large artifact 读写被误判为 pipeline 或训练逻辑问题；p16 replay 曾被 loadavg 手动停跑，后续证据显示并非 p16 failure；正常 page cache 增长不应被清理。 | 资源 telemetry、cgroup、PSI、disk watermark、artifact size 必须进入 run manifest；扩到 p32、改 ORT/thread 或改 replay scheduler 前，必须有 `vmstat`、`iostat`、PSI、per-process CPU、GPU util/mem 和吞吐证据。 |
| 23 | artifact manifest label 边界不清 | manifest、labels、recording boundary、pseudo resolution、sidecar 被混作事实来源。 | manifest 只描述产物；label 只描述监督目标；runtime 事实必须来自事件流或平台。 |
| 24 | experiment trial ledger 与过拟合治理不足 | trial ledger、训练成本、数据边界、特征集、规则版本没有绑定，容易让 trial 结果不可复现；小 batch、`num_workers=0`、CPU 默认入口会让 5090 饥饿，但 batch=8192 也可能只增显存不增吞吐，并损害 rolling worst。 | 训练实验必须记录 trial ledger、online rule version、数据边界、特征/标签 contract、成本和评价口径；5090 profile 必须同时记录 samples/s、epoch wall time、DataLoader wait、H2D/train step、GPU/RSS、batch、workers、threads、quality metrics 和 rolling worst。 |
| 25 | 策略族边界混杂 | maker、tail-snipe、directional、baseline、learned parameter head 的行为和指标混在一起。 | 策略族必须分开训练、分开评估、分开部署门禁。 |
| 26 | side-by-side model / hot swap 缺控制 | 多模型同跑、切换、enabled slot、旧模型残留没有清晰约束。 | model hot swap 必须有 slot registry、active generation、rollback bundle、per-model ledger。 |
| 27 | 外部机器人参考边界不清 | 相似 bot repo 可提供实现观察，但不能作为安全、合规或收益证据。 | 外部 repo 只能作为参考证据，不作为 live readiness 证据；secret/执行/网络边界归 P0-16。 |

1. 先写权威源模型，再写交易逻辑。
2. 先写订单事件归一化，再写策略下单。
3. 先写 artifact/schema/run manifest，再写报告和 dashboard。
4. 先写 data acquisition / source coverage / T-30s preload contract，再写数据采集重构。
5. 先写 market discovery / market switch gate，再写自动切市场。

7. 先写 execution feedback labels，再决定下一轮训练路线。

## 重构中明确禁止复现的做法

- 不允许把 raw REST、manual signing、自建 SDK client 作为默认路径。
- 不允许把 no-live、validator、smoke stdout、dashboard fresh 宣称为 live-funds 成功。
- 不允许在 AWS live-trade 服务器上编译 Rust 或安装构建依赖。
- 不允许远端源码部署和测试工作目录漂移出服务器 `~/btc-updown-marketmaker`；live 交易运行产物和运行命令按 AGENTS 的 `/home/ubuntu/live-trade` 产物根单独执行，路径越界必须 fail closed。
- 不允许通过 GitHub、`git push`、`git pull` 或服务器 `git pull` 同步模型文件。
- 不允许把 external bot repo 作为安全性、收益性或实盘可用性的证据，也不允许它默认读取 secrets、安装依赖、执行脚本或联网出站。
- 不允许把 replay leaderboard 或离线 AUC 作为上线依据。
- 不允许用本地 ledger 单独替代平台 snapshot，也不允许用平台 snapshot 单独替代 reconciliation。
- 不允许让 validator 成为第二套业务解释器。
- 不允许把 3 秒 pre-subscribe、next-window-only collector、slug-only market discovery 当作满足 T-30s 预加载和 active market 数据完整性的依据。
- 不允许把任意 `.parquet` 当作 V2 typed raw parquet；必须保留 `raw_json`、source kind metadata、manifest/labels/validation/tick_stream 合同和 atomic publish 证据。
- 不允许把 live/paper 的 append JSONL 或等价不可丢 event log 删除后只保留 compact parquet。
- 不允许用 GPU util、VRAM 占用、loadavg 或 dashboard memory 单指标判断 5090 训练效率或资源故障。

## 结论

这批 mistake-log 指向的核心问题不是某个单点 bug，而是旧系统缺少稳定的权威源分层、订单事件分层、数据采集/消费分层、执行现实分层、模型 contract 分层、硬件运行合同和 artifact 证据分层。

重构的第一步不应该是直接重写策略或训练模型，而是先把这些边界做成不可绕过的 gate。否则新代码会继续复现旧问题：看似更完整，实际只是把同一批错误移动到更复杂的位置。
