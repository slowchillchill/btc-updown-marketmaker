## 1. 文档状态与结论

本文汇总以下几轮讨论：

1. Pankaj Kumar 论文中的 DRQN、DQN 是否适合进入本项目模型框架竞赛；
2. 用户批准 DRQN、DQN 进入候选范围时的固定边界；
3. Polymarket Global 是否提供本账户 open order 的真实队列排序；
4. 只有聚合 L2 时，训练和 paper trade 应如何模拟是否成交及成交数量；
5. 其他成熟交易所、回测框架和开发者如何处理同类问题。

当前结论是：

- DRQN 和 DQN 已获批准进入未来 `FrameworkEntry` 预注册候选范围，但只能作为按本项目合同重新定义、独立实现的论文启发版本。
- 截至访问日，在 Polymarket Global 公开文档和当前官方 Rust SDK 表面，未发现 `queue_position`、`quantity_ahead`、`volume_ahead` 或逐订单 MBO/L3 接口。
- Global 的公开 Market WebSocket 是价格档聚合 L2。自己的 REST open order 和 User WebSocket 能确认订单生命周期及已成交数量，但不能给出成交前名次或前方数量。
- Global 官方公开资料没有说明同价订单采用 FIFO/price-time priority。FIFO 可以作为待确认、待校准的模拟假设，不能写成平台事实。
- 因此，本项目不能声称“准确恢复真实排序”，应建设可审计的 `Polymarket L2 Queue Uncertainty Model`，输出前方量区间、成交概率和多场景成交量。
- 无真实下单的 paper/shadow 环境不能提供 queue/fill ground truth。只有未来另行获批的真实账户 execution feedback 才能校准模型。

本文不授权实现 simulator、开始训练、启动 paper trade、发送小额探针订单或进行 live trade，也不替代后续 plan/changelog。若本文建议以后被冻结为强制需求，必须同步更新对应的 demand、plan 和 changelog。

## 2. DRQN 与 DQN 的论文分析和竞赛边界

### 2.1 论文事实

论文：Pankaj Kumar, *Deep Reinforcement Learning for High-Frequency Market Making*，PMLR 189，2023。

- 论文页面：<https://proceedings.mlr.press/v189/kumar23a.html>
- 论文 PDF：<https://proceedings.mlr.press/v189/kumar23a/kumar23a.pdf>

论文构造了股票限价订单市场的 agent-based simulator。做市 agent 同时提供买卖两侧流动性，环境包含 price-time/FIFO 撮合假设、maker-taker fee、延迟、库存、取消、交易成本和日末清仓。论文动作包含 `buy`、`hold`、`sell`、`cancel`。

论文中的 DRQN 在 DQN 基础上加入 LSTM 记忆，并组合 double Q-learning 和 prioritized experience replay。论文还比较了 DQN 与基于 temporal-difference/SARSA 的 RL agent。其实验使用 500 个模拟交易日，其中 400 日训练、100 日测试，约一千万 time steps，每个 simulation 使用三个随机 seed。

论文报告 DRQN 在其自建 simulator 中的平均 normalized PnL 高于 DQN 和 RL agent，但方差较大。这个结果只能证明特定论文环境中的实验结果，不能证明 DRQN 在 Polymarket、本项目数据、本项目 reward 或 100 pUSD 账户下更优或盈利。

### 2.2 可借鉴与不可继承的部分

| 论文内容 | 本项目处理 |
|---|---|
| DQN 的 value-based 决策结构 | 可作为独立实现的候选架构，不预设为 baseline 或胜者 |
| DRQN/LSTM 的时序记忆 | 可用于部分可观察、事件不规则的状态建模，但 recurrent state 必须按 `market_id` 隔离并服从重叠市场与 reset 合同 |
| Double Q-learning、prioritized replay | 可作为训练算法候选，仍须通过相同资源、复现、泄漏和评估门 |
| 事件驱动 agent-environment interaction | 可借鉴思想，但必须改为本项目 causal event 与 `ObservationContract` |
| 股票双边 BUY/SELL 做市动作 | 不可继承；本项目是 BUY-only `Model Intent`，互补 outcome BUY 也不等于 SELL |
| 论文 FIFO matching engine、agent-based market | 不可继承为 Polymarket 事实或本项目 simulator |
| 论文 PnL/reward、NYSE 风格 fee、日末清仓 | 不可继承；必须使用项目统一 reward、NOE、ledger、settlement 与 100 pUSD 合同 |
| 论文盈利和 DRQN 排名 | 不可作为本项目晋级、盈利或冠军证据 |

### 2.3 用户已批准的固定边界

用户于 `2026-07-12` 批准 DRQN 和 DQN 进入后续竞赛计划的 `FrameworkEntry` 预注册候选范围，并固定以下原文：

> 纳入按本项目合同重新定义、独立实现的论文启发版本；论文模型、模拟器、reward 和盈利结论都不能原样参赛。

DRQN 和 DQN 必须与其他候选共同使用：

- causal `ObservationContract`；
- BUY-only `Model Intent`；
- 同一 simulator、`NormalizedExecutionEventContract`、ledger 和 reward；
- 相同 100 pUSD 初始账户合同；
- 相同 split、seed、资源预算、评估和 runtime parity gate；
- 相同 queue/fill simulator artifact 和场景参数。

本轮批准不代表二者已经 `eligible`、已经晋级、优于其他模型、paper-ready、live-ready 或能够盈利。也不能预先指定 DQN 为 baseline、DRQN 为主模型。

官方 open order 的 `created_at` 只是订单字段。没有 Global 官方撮合优先级合同和其他逐单事件时，不能用它单独推导自己的真实顺序。`book.hash` 也没有被官方定义为逐订单 ID，不能拿来关联自己的订单。

User Channel 中 `MATCHED` 是非终态，后续仍可能进入 `MINED`、`CONFIRMED`、`RETRYING` 或 `FAILED`；模拟和账本不能把 `MATCHED` 直接写成终局经济确认。

### 3.2 Global FIFO 结论的边界

截至 `2026-07-12`，本轮查阅的 Global 官方公开文档没有说明同价订单采用 FIFO/price-time priority。这只支持以下表述：

> Global 同价撮合优先级尚未在本轮查阅的公开资料中得到官方确认。

它不支持“Global 一定使用 FIFO”，也不支持“Global 一定不使用 FIFO”。社区关于 FIFO 的说法只能作为向官方提问或设计 stress scenario 的线索，不能成为 simulator 真相。

### 3.3 Polymarket US 只能作为对照

[Polymarket US FIX Order Entry](https://docs.polymarket.us/institutional/fix-api/fix-order-entry-overview) 明确规定 price-time priority：同价位旧订单优先，增量会失去时间优先级，减量保留优先级。

[Polymarket US FIX Market Data](https://docs.polymarket.us/institutional/fix-api/fix-market-data-subscription) 描述 institutional FIX Market-by-Order 数据，每张订单具有独立数量和时间优先级时间戳。

这是独立的 Polymarket US 交易所和 institutional FIX 会话，只能用于说明理想数据合同，不能外推到 Polymarket Global CLOB。

## 4. 为什么仅靠 L2 无法恢复真实排序

假设自己的 BUY 挂在价格 `0.50`，该档公开总量从 `100` 变成 `70`。同一个 L2 结果至少可能来自：

- 自己前方订单成交或取消 `30`；
- 自己后方订单取消 `30`；
- 前后订单同时新增、取消和成交后的净变化；
- 多个底层事件被聚合；
- feed gap、重连或 snapshot replacement。

这些不可区分的逐单历史会产生相同 L2，却对应不同的 `quantity_ahead` 和成交时点。因此仅凭 L2：

- 不能确定“我是第几个订单”；
- 不能唯一恢复真实 `quantity_ahead`；
- 只能估计前方量的区间、期望值或 fill hazard；
- 价位下降、`size=0` 或 level delete 不能单独作为自己已经成交的证据。

精确维护可见 FIFO 队列至少需要稳定逐单 `order_id`、每单剩余量、priority/engine sequence、add/update/delete/execute、无缺口序列与恢复游标、自己的 client/exchange order 映射，以及正式撮合优先级规则。即使具备 MBO/L3，隐藏流动性、engine acceptance latency 和“历史 replay 不受我方订单影响”的反事实假设仍会限制绝对精确度。

## 6. 推荐的项目队列成交模型

### 6.1 能力名称和输出

推荐正式名称：

> `Polymarket L2 Queue Uncertainty Model`

不使用“真实 FIFO simulator”或“准确 queue position”。模型应输出：

- `queue_ahead_low/base/high`；
- `P(fill within 1s/5s/...)`；
- 预期成交数量及 `p10/p50/p90`；
- time-to-first-fill 分布；
- `queue_model_version`、`scenario_id`、`provenance` 和 `evidence_quality`。

### 6.2 每笔模拟订单的最小状态

```text
order_id
market_id
asset_id
side
price
send_ts
accepted_exchange_ts
leaves_qty
queue_ahead_low
queue_ahead_base
queue_ahead_high
own_orders_ahead
queue_model_version
scenario_id
provenance
evidence_quality
```

订单必须在模拟的 exchange acceptance/`PLACEMENT` 时刻进入 resting queue，而不是在模型 decision time 或本地 send time 立即入队。accepted、rejected 和 unknown 必须是不同状态。

### 6.3 初始前方量

在 send、预计 acceptance/ack 和随后短窗口观察同侧同价位聚合深度，形成初始前方量估计或区间。

如果 L2 已包含自己的数量，只有在可验证 self-contribution 对账时才扣除自己的剩余量。不能默认“ack 后盘口增加 `S` 就一定是自己”，因为同期外部新增和聚合可能产生相同观察。

### 6.4 成交量推进与 partial fill

在先完成 Polymarket trade-side、direct match 和互补 outcome/MINT 映射验证后，对有资格消耗该 BUY 队列的一笔 trade 使用唯一成交量预算：

```text
trade_budget = unconsumed_trade_qty

consume_ahead = min(queue_ahead, trade_budget)
queue_ahead -= consume_ahead
trade_budget -= consume_ahead

fill_qty = min(leaves_qty, trade_budget)
leaves_qty -= fill_qty
trade_budget -= fill_qty
```

等价地：

```text
fill_qty = min(
    leaves_qty,
    max(0, trade_qty - queue_ahead_before)
)
```

同一价格有多笔自己的订单时，必须按模拟 acceptance 顺序共享同一个 `trade_budget`。每笔订单各自消费完整 trade size 会制造重复成交。

### 6.5 无法归因的 L2 下降

先扣除已经由 trade event 解释的数量，避免 trade 与随后 depth update 双重推进：

```text
unexplained_decrease = max(
    previous_depth - new_depth - accounted_trade_qty,
    0
)
```

建议同时维护以下场景：

1. `conservative` / `RiskAverseQueue`
   - 假设取消或修改发生在自己后方；
   - 只有经验证的正确方向 trade 主动推进前方量；
   - 只应用 `queue_ahead <= new_external_depth` 的物理约束；
   - 作为正式报告的保守下界。
2. `base_provisional` / `ProbQueue`
   - 按前后相对量分配无法解释的下降；
   - 未由真实 execution feedback 校准前仍标为 `assumed`，不能称为 calibrated base。
3. `tail_stress`
   - 注入更慢成交、更差延迟、feed gap、cancel race 和不利分配；
   - 用于晋级敏感性门。
4. `optimistic_diagnostic`
   - 取消优先发生在前方或 touch 更易成交；
   - 只作上界诊断，不能用于可晋级盈利结论。

概率场景可以使用以下候选期望更新：

```text
front = queue_ahead
back = max(external_depth - front, 0)
p_ahead = f(front) / (f(front) + f(back))
queue_ahead = max(queue_ahead - p_ahead * unexplained_decrease, 0)
```

`f` 可预注册为 `x`、`log(1+x)` 或 `x^n`。函数类型和参数在真实校准前都只是建议，不是平台事实。

深度增加默认排在自己后方，不增加 `queue_ahead`。改单是否保留优先级必须服从未来核实的 Global 规则；未确认时，改价或增量应作为丢失优先级的保守 stress，而不是已知事实。

### 6.6 生命周期和反事实边界

模拟器还必须明确处理：

- order latency、feed latency 和 acceptance time；
- partial remaining、batch 逐项 mixed result；
- cancel request、cancel ack、cancel race 和 cancel 后 late fill；
- `MATCHED` 到 `CONFIRMED/FAILED` 的后续状态；
- lot size、size precision 和不可交易 dust；
- level delete、无明确 trade side、strict price-through 的独立场景；
- reconnect、sequence gap、matching-engine restart 后的 queue unknown；
- historical tape 不因自己的反事实订单而变化的 small-agent 假设；
- per-event/per-price liquidity-consumption ledger，防止重复使用同一历史流动性。

发生 gap/reconnect 后，新的 L2 snapshot 只能恢复总深度，不能恢复订单年龄。此时应把旧 queue 状态标为 unknown，并按冻结规则重新排到队尾、形成新区间或 censor；不得继续假装序列完整。

超过预注册 participation、visible-depth 或 candidate-size 上限的结果只能进入 market-impact stress，不能作为晋级盈利证据。

## 7. Polymarket 专属适配决策门

成熟股票或加密交易所的通用公式不能直接成为 Polymarket 真相。实现前必须核验：

1. Global 同价订单的正式撮合优先级；
2. 订单减量、增量、改价或 replace 是否保留优先级；
3. `last_trade_price.side` 在当前 Global API/SDK 中的精确业务语义；
4. BUY 与同 outcome ask 的 direct match 如何映射到公开 book/trade/user event；
5. 互补 outcome BUY 通过 MINT/complete-set 路径匹配时，两个 book 和 trade event 如何对应；
6. batch、feed coalescing、restart、sequence/gap recovery 的实际行为；
7. 是否存在面向 market maker 的非公开 MBO/queue-position 产品。

在这些问题没有官方回答或真实证据前，相关规则只能标为 `assumed` 或 `stress`。不能把 UP/DOWN 两个 outcome book 机械地当成完全独立的股票订单簿并重复计算成交量。

可向 Polymarket 官方支持或 developer Discord 提交上述问题；发送外部消息或进行真实下单实验仍需用户另行授权。

## 8. Paper trade 与真实校准

### 8.1 两类能力必须分开

- 无真实订单的 shadow/paper：可以验证事件处理、确定性、订单状态机、NOE、ledger、reward、场景敏感性和审计链；不能证明真实 queue/fill 准确。
- 真实账户 execution feedback：可以用自己的 placement、partial fill、cancel 和 trade 证据校准 queue/fill model；任何小额 live 探针都需要未来单独授权。

真实平台是 Polymarket/官方 SDK/User Channel/submit/cancel 的执行域；模拟平台是训练样本构造和 paper 生命周期模拟域。paper 是真实平台 artifact 的校准消费者，不是 live 行为的权威来源。

### 8.2 未来获批后的校准证据

需要记录：

- client send、exchange/order placement、cancel/modify request 与 ack 时间；
- ack 前后同侧同价 L2；
- public book、price change 和 trade event；
- User Channel order/trade event；
- 每次 actual partial fill、remaining 和最终状态；
- feed latency、order latency、clock、host/region、SDK/runtime 版本；
- gap、reconnect、restart 和 reconciliation 结果。

建议校准与验证指标：

- `P(fill <= horizon)` 的可靠性与 calibration error；
- time-to-first-fill；
- 各时间点累计成交量 MAE；
- full-fill probability；
- simulated/actual fill ratio；
- 按深度、价格、市场阶段和 latency regime 的向前 OOS 表现；
- 对取消但未成交订单进行 right-censored survival 处理。

参数只能在 development/calibration 时段拟合，在未来时间切分验证；final holdout 不得反复读取。真实执行 artifact 只能校准 simulator，不能未经合同许可直接成为模型输入。

## 9. 竞赛公平性与晋级边界

- 所有 `FrameworkEntry` 必须使用同一个冻结的 queue/fill simulator artifact、版本、参数、场景、事件序和随机语义。
- 参赛模型不能选择自己的 fill model，也不能利用 queue simulator 私有状态绕过 `ObservationContract`。
- raw simulated evidence 必须先进入 `NormalizedExecutionEventContract`，再进入 ledger 和 reward；simulator 不得直接写奖励或盈利结果。
- 多候选比较必须共享相同 future tape 和 common random numbers；同一输入 hash、simulator version、seed 必须逐事件复现。
- 正式报告至少同时给出 conservative、base provisional 和 tail-stress；optimistic 只作诊断。
- 未完成真实本账户 execution calibration 时，所有依赖 queue/fill 假设的候选保持 `research_only_non_promotable`。
- 固定 simulator 中胜出只能表述为“在该冻结模拟合同下胜出”，不能外推为 live 盈利。
- DRQN/DQN 同样受这些限制，不能通过学习 simulator 的乐观缺陷获得晋级资格。

## 10. 当前仓库能力与已发现缺口

### 10.1 已有能力

当前 [Polymarket orderbook layout](../data-collect/src/polymarket_orderbook_layout.rs) 保存：

- collector-local 与 venue timestamp；
- market、asset、event type；
- 聚合 bids/asks；
- price、size、side、best bid/ask；
- hash、fee、transaction hash 等公开字段。

这些数据足以构建 L2 queue proxy 和多场景 fill model，但 schema 没有逐订单 ID、逐单 priority 或真实 queue rank，因此不能支持 exact FIFO reconstruction。

当前 `data-collect/Cargo.toml` 使用官方 `polymarket_client_sdk_v2 = 0.6.0`，符合 SDK-first 边界。

### 10.2 市场事件顺序风险

当前 [live_runtime.rs](../data-collect/src/live_runtime.rs) 分别订阅：

```text
subscribe_best_bid_ask
subscribe_orderbook
subscribe_prices
subscribe_last_trade_price
subscribe_tick_size_change
subscribe_new_markets
subscribe_market_resolutions
```

然后通过 `tokio::select!` 合并处理。这个高层 typed-stream 组合不能证明保留 Book、PriceChange 和 Trade 的原始 WebSocket wire order。

官方 Rust SDK 的开放 [PR #20](https://github.com/Polymarket/rs-clob-client-v2/pull/20) 正提议增加统一 `subscribe_market_events()`，其动机明确指出合并独立 typed streams 不能保留原始 WebSocket 顺序。访问日该 PR 仍为 open、无 maintainer review，不能当成已可用的官方保证。

队列回放若不能确定 trade/depth 的事件顺序，可能重复扣减、先后颠倒或错误重建盘口。因此在修复并验证事件顺序前，当前数据最多支撑 approximate、non-promotable queue replay。

### 10.3 当前缺少本账户校准流

当前 `data-collect` 未发现 `subscribe_user_events()`、`subscribe_orders()` 或 `subscribe_trades()` 的本账户采集路径。因此现有训练数据不能校准本账户真实 placement、partial fill、cancel race 和 queue model。

后续仍须遵守 SDK-first 决策门：

1. 优先等待、推动或采用官方 SDK 已合并并发布的统一 market stream；
2. 若官方 SDK 仍缺失，先向用户报告具体缺口、影响和选项；
3. 只有用户明确同意后，才可考虑固定版本的最小 SDK patch/fork；
4. 未获同意不得改用 raw WebSocket/REST、manual signing、自建客户端或 shadow implementation；
5. 若继续使用独立 typed streams，则能力必须明确保持 approximate/non-promotable。

## 11. 推荐验收清单

- [ ] 官方接口字段与“公开资料未发现 queue rank/quantity-ahead”结论逐项对账。
- [ ] 没有把 Global L2 写成 L3/MBO，也没有把 FIFO 写成官方事实。
- [ ] 没有把 `created_at`、book hash、depth decrease、`size=0` 或 level delete 当作真实排位或成交证明。
- [ ] Polymarket trade side、direct match、互补 BUY/MINT 映射均有独立验证门。
- [ ] trade 与随后 depth update 不会重复扣减 queue。
- [ ] 同一 trade budget 在多笔自有订单间只消费一次。
- [ ] partial fill 不超过 leaves、未消费 trade quantity、visible liquidity 和精度边界。
- [ ] accepted/rejected/unknown、partial、batch mixed result、cancel race、late fill 均可重放。
- [ ] feed gap/reconnect/restart 后 queue 不会继续假装 exact。
- [ ] historical book 保持 immutable，own-order/own-consumption overlay 可审计。
- [ ] conservative/base/tail 场景的 provenance、参数、版本和 hash 完整。
- [ ] 无真实 execution feedback 时，结果保持 non-promotable。
- [ ] shadow paper 没有被描述为真实 fill calibration。
- [ ] `MATCHED` 没有被误写为终局 `CONFIRMED`。
- [ ] simulator 私有 queue state 没有绕过 `ObservationContract` 暴露给模型。
- [ ] raw simulation evidence → NOE → ledger → reward 链路 exactly-once 且可追溯。
- [ ] 全部参赛模型共享同一 queue/fill artifact，不能自行选择乐观参数。
- [ ] DRQN/DQN 的论文 URL、独立实现和不可继承边界完整。
- [ ] 没有把论文结果写成本项目 DRQN 优于 DQN 或能够盈利的证据。
- [ ] 本文没有被解释为自动授权实现、训练、paper、small-live 或 live。
