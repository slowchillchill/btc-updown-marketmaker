## 2. 当前业务与技术合同

### 2.1 依赖方向与唯一写入器

推荐依赖方向固定为：

```text
contracts <- sim-system
contracts <- ledger

模型意图 -> 共用风险准入/Intent Bridge -> execution/sim  -> sim-system
                                      \-> execution/live -> 官方 Rust SDK

模拟或真实平台原始证据 -> 唯一外部归一化入口 -> NormalizedLedgerTransactionV1
                                                    -> ledger
                                                    -> LedgerProjectionV1
```

1. `ledger` 不依赖 `sim-system`、官方 SDK、网络、钱包、DPT、模型框架或 Python。它是同步、纯 Rust
   的确定性应用核心；异步 I/O、队列和进程生命周期由各组合根拥有。
2. `sim-system` 不依赖、读取或回写 Ledger。模拟平台账户按平台有效时间独立决定最终资金准入；
   交易侧 Ledger 的本地预检不能推翻平台拒绝或提前使用平台隐藏状态。
3. 每个 `AccountInstanceKeyV1` 只有一个 Ledger 写入器。归一化、DPT、模型、奖励、查询和报告端
   通过窄接口读取投影，不取得可变状态或 `apply` 权限。
4. live 只依赖公共合同、唯一归一化接口、Ledger、模型运行时和官方 SDK 实盘后端；实际
   `cargo tree` 与二进制依赖闭包必须排除 `sim-system` 及全部模拟专用资源。

### 2.2 账户身份与唯一开户锚点

Ledger 自有的初始化入参只包含：

```text
LedgerGenesisInputV1 {
    account_opening_anchor: AccountOpeningAnchorV1,
}
```

1. 公共 `AccountOpeningAnchorV1` 是每条账户链唯一的初始经济输入；Ledger 直接消费并内容寻址
   保存该对象，不定义、派生或接受第二个 Ledger 专用开户锚点，也不允许调用方另填初始余额、
   持仓、开放订单或应收款。`AccountInstanceKeyV1` 必须由锚点字段机械派生并逐项一致，不能由
   构造参数覆盖。完全相同锚点的初始化重试只返回原账户实例与摘要，不重复入账；同一账户实例键
   绑定不同锚点或不同锚点内容时失败即关闭。
2. training、offline-evaluation 和 paper 只接受 `plan/sim-system-plan.md` 所定义且实际合同校验
   通过的 `SIMULATED` `AccountOpeningAnchorV1`；调用方和 Ledger 都不得覆盖其来源或字段，两侧
   运行清单绑定同一个 `anchor_id/SHA-256`。受信组合根只有在 Ledger 以同一锚点幂等初始化成功，
   且 sim 归属计划要求的同步开户前置也确认完成后，才能开放该轨迹的业务入口；Ledger 初始化
   结果未知时只能查询或重试同一锚点，明确拒绝时也不得换锚点或另发本金。sim 如何生成锚点、
   管理会话初始化状态、绑定输出桥和恢复均只由其归属计划规定，Ledger 不复制这些内部状态，
   也不反向调用或控制 `sim-system`。
   live 的新开户锚点只能由真实账户身份以及包含真实现金、持仓、开放订单、
   未决提交和应收款的明确核对证据生成；合法检查点必须继续绑定原锚点，不能生成新起点，也
   不能复用模拟器“给定现金、其他为零”的锚点。
3. 同一进程内，除完全相同锚点的物理初始化重试外，同一正在初始化或已经活动的 Ledger
   `AccountInstanceKeyV1` 的重复创建必须失败。不同训练运行可以使用相同业务 `account_id`，
   但必须由不同 `run_id` 和开户锚点形成不同账户链。
4. `2000 pUSD` 只由首个 training/offline-evaluation/paper 业务配置选择并写入模拟平台开户锚点及运行清单；Ledger
   构造器不提供隐藏默认值，运行中也不把余额补回该数值。live 只能从真实平台开户证据或合法
   检查点取得初始余额；若要运行同一 `2000 pUSD` 场景，该真实证据必须支持相同起点，配置不得
   覆盖、补齐或伪造平台余额。
5. 一个开户锚点对应一条完整账户轨迹。UTC 日、市场目录、物理文件、加载批次和模型小批次都
   不是开户边界；同一轨迹在这些边界上继续使用原 `AccountInstanceKeyV1`、资金和 Ledger 序号。
   training 需要新回合时，调用方必须提供新的 `AccountInstanceKeyV1` 和
   `AccountOpeningAnchorV1`；是否及如何创建模拟会话由 sim 归属计划规定。不得在原账户链内把
   余额恢复成 `2000 pUSD`。offline-evaluation
   不得因提前耗尽而自适应创建替代轨迹，paper 和 live 不得自动重新开户。
6. 开户锚点必须先于该账户实例的任何 `MarketEnrollmentV1` 或账户变化存在。市场登记只作为
   轨迹、运行清单、恢复和组合验证身份，不属于 Ledger 的两类经济输入，不改变现金、持仓、
   预留、应收款或 Ledger 序号。Ledger 只引用 sim 运行清单中的 `TradeFinalityPolicyV1` 身份以
   完成同候选核对，不解释、复制或执行该模拟策略。

### 2.3 输入事件、序号和摘要

Ledger 只接受两类封闭输入：

1. `LocalReservationEventV1`：只表达预留创建、能够证明尚未发送的本地失败释放，以及发送后
   结果未知标记；它不得表达平台接受、平台拒绝、查询消歧或平台资金变化；
2. `NormalizedLedgerTransactionV1`：唯一外部归一化入口从模拟或真实平台原始证据生成的经济或
   控制交易；平台接受、拒绝及查询消歧只能由该输入触发。

每笔输入至少绑定账户实例、来源种类、稳定事件身份、原因身份、可空的市场/资产/请求/订单/
成交/结算身份、来源证据摘要、来源序列或共同前缀、平台事实时点、本机接收/接纳时点、Ledger
可用时间、明确单位的多腿变化和合同版本。

- `ledger_entry_seq` 是 Ledger 本地唯一连续追加序号；同一事件身份重放返回原结果，不新增序号。
- 模拟来源必须绑定全账户 `account_transition_seq` 与前驱身份；该序号跨全部市场递增，不能按
  `condition_id` 分支。私有反馈交付序号只决定可见顺序，不能替代平台账户经济序号。
- live 平台未提供等价全账户序号时，归一化入口必须以本地原始证据接纳序列和对账围栏形成明确
  来源前缀，不能伪造平台序号。
- Ledger 状态摘要、平台原始状态摘要和平台转换链摘要前像不同，不要求字节相等。联合对账只在
  同一平台来源前缀比较归一化重放后的平台确认投影；本地未决预留按请求身份、提交状态和
  Ledger 本地序号另行守恒，不能混入平台前缀摘要。

### 2.4 最小账目与投影

Ledger 使用明确单位的平衡多腿交易，不建设通用会计科目配置系统。最小状态包括：

- 账户全局：已确认可用 pUSD、本地待提交预留、平台确认订单预留、成交待处理本金、即时手续费
  预留与费用、返佣应收、待赎回应收、累计已实现 PnL、Ledger 序号和摘要；
- 逐市场：本地待提交本金/费用、开放订单本金、成交待处理本金、两侧结果代币数量与成本、费用、
  返佣应收、待赎回资产、已实现 PnL、市场累计接受本金与当前含手续费占用；
- 逐订单/成交：只保留重建、查询、幂等、恢复和审计所需的稳定身份及紧凑经济分桶，不复制完整
  平台原始载荷。

内部至少满足：

```text
account_global_bucket
= sum(active_market_bucket) + account_only_bucket

full_ledger_projection
= platform_confirmed_projection + local_pending_reservation_projection

market_current_all_in_commitment
= local_pending_principal_and_fee
 + open_principal_encumbered
 + matched_pending_principal
 + unredeemed_position_cost_basis
 + attributable_immediate_fee
```

当前占用与累计接受本金是两个独立投影。撤单确认或未花预算释放可以降低当前占用，但不会删除
累计事实。返佣应收和待赎回应收可进入 NAV，但在实际付款或赎回到账前不得进入可用现金。

NAV 和未实现 PnL 只能使用同一模型可见截点的版本化 `ValuationMarkV1`；Ledger 不抓取行情，
不使用隐藏平台价格，也不把估值变化误写成现金。已实现 PnL、返佣应计和返佣付款各自只有一个
经济应用截点，付款不产生第二次收益。

`LedgerProjectionV1` 必须以既有账户、市场、订单、成交、来源前缀和摘要投影，让调用方机械
区分可用现金、全部本地或平台预留、未知提交、未结持仓、成交待处理或待补偿变化、返佣应收、
未结日桶、待赎回资产，以及平台确认前缀和本地未决前缀是否闭合。Ledger 不增加训练专用的
`terminated`、`truncated`、`reset` 或“经济耗尽”裁决字段；调用方只能在自己的版本化回合合同中
组合这些因果可见事实，不能读取模拟器隐藏状态或由 Ledger 猜测未来最小订单、市场价格和事件。

### 2.5 本地准入、容量配置与平台最终资金门

风险准入调用 Ledger 单写入器上的原子操作：

```text
try_reserve_intent(
    expected_ledger_entry_seq,
    request_identity,
    condition_id,
    requested_principal_pusd,
    immediate_fee_reserve_pusd,
    account_admission_policy_identity,
)
```

该操作先验证调用方读取的投影序号仍是当前序号，再同时检查已确认现金、全部本地未决预留和
逐市场当前占用，最后写入唯一 `LocalReservationCreated`。任一检查失败均零副作用；不能先读取
后异步登记，不能为并发请求重复使用同一余额。

首个 `AccountAdmissionPolicyV1` 场景由运行清单配置：

```text
per_condition_current_all_in_cap_pusd = 1000
```

- 运行清单分别绑定唯一 `AccountOpeningAnchorV1`、`AccountAdmissionPolicyV1` 和延迟场景；
  `2000 pUSD` 只能先进入模拟平台初始配置并由 `sim-system` 写入开户锚点，Ledger 不从准入策略或
  第二份配置加载开户金额。运行中不自动补资，约三分钟仍只属于场景输入。
- `1000` 包含请求本金和即时手续费预留，按 `condition_id` 约束当前占用，不是单订单或历史累计
  上限；实际取值可由其他运行配置替换，但语义和单位不能改变。
- `post_orders` 的各项按稳定原始顺序在同一个账户写入器内逐项检查和预留，每项使用独立请求项
  身份，后项看到前项已经形成的预留；局部拒绝零副作用且不改变返回项与原请求项的对应关系。
- 平台资金门仍必须独立检查平台侧真实可用余额。Ledger 预检通过不是平台接受承诺；Ledger
  暂时落后时平台可以拒绝，平台领先时模型也不能绕过 Ledger 使用尚未可见的资金。
- 一次资金不足、当前无合法 BUY 或 `available_pusd=0` 都不是 Ledger 层的经济耗尽结论。只要
  仍有预留、未知提交、开放订单、持仓、成交迁移、返佣应收、待赎回资产、来源前缀缺口或可能
  改变资金的在途反馈，投影就必须如实保留该未决事实；负余额属于守恒或合同错误，不能被标记
  为正常耗尽。
- 业务若未来需要“本金 1000、费用另计”或永久可部署上限，必须新版本化策略和验收，不能静默
  重解释当前字段。

### 2.6 订单、成交、费用、结算和赎回迁移

1. 提交前：本地现金可部署量迁入本地待提交预留。
2. 能证明请求尚未发送的平台前本地失败：由本地事件释放一次；跨过发送边界后不得再走该路径。
3. 平台明确拒绝：唯一归一化控制交易在一次 Ledger 原子提交中消费对应本地预留并释放；拒绝
   自身不生成平台订单或成交，宿主不得再提交本地释放事件。
4. 平台明确接受：唯一归一化交易在一次 Ledger 原子提交中消费本地预留，并转换为平台确认
   开放本金、成交待处理本金、未花预算释放和费用分桶；不能先释放再重新扣款，也不能另发本地
   转换事件。
5. 提交结果未知：本地事件只标记并继续保留预留；稳定查询证据必须先由唯一归一化入口形成控制
   或经济交易，再原子转换或释放，超时、重启和重试不得自动再签名或重复提交。
6. 成交最终性：待处理、经济已应用、未应用失败和已应用后补偿分别迁移，唯一经济身份只应用
   一次；结果代币数量和成本与 pUSD 变化同时守恒。
7. 撤单、GTD 到期、FAK 未花预算和合格市场判定关闭只释放各自真实未成交预留；调用请求、
   `end_at` 或外部盘口变化本身不释放账户资金。
8. 合格市场判定后，开放余量释放、结果代币终态、待赎回应收和 `AutoRedeemApplied` 是可区分
   的变化。约三分钟只影响代表场景中的事件时间；没有已确认赎回交易时不能增加现金。
9. maker/taker 返佣应计分别增加不可支出应收；日结和付款按来源事实迁移。付款只将应收转现金，
   不再次增加 NAV、PnL 或奖励。

### 2.7 可见时间与模型决策截点

每次只读投影至少绑定：

```text
LedgerProjectionV1 {
    account_instance_key,
    ledger_entry_seq,
    ledger_state_sha256,
    platform_source_prefix,
    ledger_local_prefix,
    available_through_utc_ms,
    platform_confirmed_projection,
    local_pending_reservation_projection,
    composed_global_account_projection,
    market_projections,
}
```

模型决策使用的 `DecisionVisibleCutV1` 同时绑定公开市场游标、Ledger 序号与摘要、私有反馈序号和
可见截止时间。平台事实可以先发生，模拟私有响应也可以早于对应公开行情，但只有接收并成功应用
到本实例 Ledger 的经济事实才能进入投影；查询或对账本身不能周期性触发策略，只有其归一化后
形成的模型可见业务变化才可以触发。

模拟反馈按其 `response_received_at` / `feedback_received_at` 进入 Ledger；paper 和 live 按本机
真实接收并持久接纳时间进入。后继来源变化先到时可以缓冲，但在前驱缺口闭合前不得投影其账户
结果。缓冲达到硬上限或超时只产生失败状态，不丢弃前驱要求或跳序应用。

### 2.8 恢复、对账和失败关闭

恢复基线为“仅追加证据 + 原子检查点 + 幂等尾部重放”，不是读取当前余额覆盖 Ledger。

- `LedgerCheckpointV1` 绑定账户实例、唯一开户锚点、最后 Ledger 序号、完整状态摘要、平台确认
  投影摘要、本地未决预留摘要、两个来源前缀、幂等索引摘要、适用合同和实现身份；候选完整
  验证后无覆盖原子发布。
- `RecoveryFenceV1` 分别绑定组合根的原始证据尾/平台来源前缀、归一化序号、Ledger 本地前缀与
  检查点/尾序号、公开市场游标、私有反馈序号和适用平台检查点；不能用单一摘要把平台事实与
  尚未到达平台的本地预留合并比较。
- training 首版固定开户锚点、输入、种子和合同，从干净起点重放；不为训练引入中途恢复分支。
- paper 只从 sim 检查点与 Ledger 的最近共同围栏恢复；两边前缀不同时回退共同旧围栏，不能把
  Ledger 单独补给模拟器或选择任一较新状态。
- live 先恢复本地原始证据与 Ledger，再重连用户频道并以官方 SDK 查询订单、成交、持仓和余额
  补证。查询差异先生成有来源的归一化补录交易；无法唯一解释、用户频道有缺口或未知提交未
  消歧时停止新决策和提交。
- allowance 只作权限和对账证据；平台余额快照不能成为模型热路径第二账本，也不能直接产生
  缺失成交、费用、返佣或 PnL。

模拟对账在共同 `account_transition_seq=N` 只比较归一化重放的预期平台确认投影与实际平台确认
投影；本地未决预留按请求身份、是否跨过发送边界、未知状态和 Ledger 本地序号单独闭合，完整
Ledger 状态必须等于两类投影的确定组合。live 没有等价平台序号时，在真实证据接纳围栏上按同一
分解逐项比较开放订单、已知成交、现金、持仓、应收和本地未决。平台与 Ledger 在任意墙钟时刻
暂时不同是正常现象，永久无法闭合的差异不是“异步”，而是失败。

### 2.9 各运行模式的组合合同

| 运行模式 | 平台账户权威 | Ledger 开户与恢复 | 模型可见边界 |
| --- | --- | --- | --- |
| training | 每条独立账户轨迹独占 `sim-system` 会话和 Ledger；同一轨迹覆盖全部日期与重叠市场，多条隔离轨迹可并行 | 同一模拟平台开户锚点；从干净起点确定性重放；新回合必须新身份和新锚点 | 平台按事件时间，公开市场按接收时间，私有反馈按模拟收到时间 |
| offline-evaluation | 每条预登记账户轨迹独占 `sim-system` 会话和 Ledger；不得按提前耗尽结果自适应补发轨迹 | 同一模拟平台开户锚点；只运行评估清单预先冻结的干净轨迹 | 平台按事件时间，公开市场按接收时间，私有反馈按模拟收到时间 |
| paper | 独占 `sim-system` 会话，以仅追加市场登记链扩展同一账户轨迹，只消费本机已收到的公开事件 | 同一模拟锚点；sim 与 Ledger 共同围栏恢复 | 公开和私有事实均按本机/模拟返回可见时间 |
| live | 真实 Polymarket | 真实核对开户或合法检查点；重连后查询补证与失败关闭 | 公开、用户频道、SDK 响应和查询均在本机接收并接纳后可见 |

各模式共享公共合同和纯 Ledger 应用代码，不共享可变实例。`source=SIMULATED` 进入 live、
`source=LIVE` 进入 training、offline-evaluation 或 paper、跨账户或跨运行事件必须在应用前拒绝。live shadow 也不把
模型意图改道到 sim；需要模拟成交时使用 paper 组合根。

同一市场时间带可供多个隔离账户作反事实重放，但每份初始资金只属于对应账户轨迹；它们不能
相加为单一资本，也不能冒充额外的独立市场历史。Ledger 只对每个账户实例给出投影；跨账户的
收益率、耗尽率和风险分布由训练或评估归属模块计算，Ledger 不提供跨账户合并余额或合并 PnL。
paper 在暂时或永久没有可下单现金时仍保持原账户链并继续接收后续经济事实；live 的现金变化
只能来自真实、受支持且已归一化的证据，本计划不借训练重置推定真实外部入金语义。

### 2.10 精确数值、成熟工具和资源边界

1. pUSD、份额、费用、应收和兑付均使用明确币种、标度和固定微单位新类型；核心不使用 `f32`
   或 `f64` 记账。优先复用工作区已锁定的 `rust_decimal` 边界校验和现有金额精度规则，但公共
   Ledger 类型不依赖官方 SDK `Amount`。
2. 版本化序列化复用 `serde`，内容身份复用 `sha2`，有序状态复用标准库 `BTreeMap/BTreeSet`，
   原子文件边界优先复用工作区已验证的标准库/`rustix` 做法。开始实施前以真实 `Cargo.lock`、
   `cargo metadata` 和许可证复核版本，不新增自研哈希、十进制、数据库或事务框架。
3. 纯核心保持同步和单写入器；不为未来 paper/live 预建异步运行时、远程服务、插件或数据库。
   每个账户顺序应用，账户间由调用方并行；单次事件更新复杂度随受影响订单/市场索引增长，不
   全扫描历史市场。并行汇总只能形成逐账户分布统计，不能形成合并本金或合并损益的虚构账户。
4. 仅追加日志、检查点、乱序缓冲、幂等索引、活动市场、终态保留和产物均由实测冻结硬上限。
   是否需要日志分段、压缩或其他成熟存储工具只能由阶段 4 的真实负载证据决定，不提前设计
   分布式存储。

### 2.11 输出、保留和安全

最小产物包括运行清单、开户锚点、仅追加 Ledger 交易段、原子检查点、只读投影、恢复围栏、
对账报告、资源高水位和不变量报告。产物必须绑定输入合同、来源、实现、配置、序号范围、内容
身份和 SHA-256，不复制完整平台原始载荷，也不包含钱包、签名材料、凭据或敏感环境变量。

终态市场可以从热索引压缩为紧凑投影，但在幂等、恢复、查询、对账和审计保留期结束前不得删除
其来源身份和累计经济结果。最终删除只按已冻结保留水位执行，不为证明不存在建设永久墓碑或
治理数据库。

  - 步骤 2.3.1：同一活动账户轨迹只允许一个写入器，全部重叠市场使用同一全局账户。
    -> 验证：同 `account_id` 不同运行允许隔离，同一 `AccountInstanceKeyV1` 重复创建失败；并行
    轨迹的状态、初始资金与 PnL 互不可达，汇总端不能把它们写成一条账户链。

阶段 2 完成门：本地预留、逐市场当前占用和全局现金门能在高频并发下防止双花，不把 Ledger
预检冒充平台最终接受。

## 6. 阶段 3：完整经济生命周期与因果可见

- 任务 3.1：接入订单、成交、费用与补偿迁移
  - 步骤 3.1.1：按唯一经济身份实现提交、开放、成交待处理、成功、未应用失败和已应用补偿。
    -> 验证：代表状态链及重复/乱序别名不重复现金、份额或费用。
  - 步骤 3.1.2：实现撤单、GTD、FAK 未花预算和市场判定关闭的独立释放原因。
    -> 验证：`end_at`、撤单请求或外部盘口本身不释放，只有确认变化迁移真实分桶。
- 任务 3.2：实现返佣、付款、结算与赎回迁移
  - 步骤 3.2.1：应计增加不可支出应收，付款只迁移应收至现金。
    -> 验证：maker/taker 分离，付款不产生第二次 PnL 或奖励。
  - 步骤 3.2.2：按实际结果代币形成待赎回和到账交易。
    -> 验证：获胜、全亏、零现金但仍待赎回、零现金但仍有可付款返佣、零持仓、重复赎回和约
    三分钟延迟场景彼此可区分；不按投入本金补回，也不把最终全亏写成 Ledger 错误。
- 任务 3.3：实现模型可见投影和估值
  - 步骤 3.3.1：按 Ledger 可用时间与连续来源前缀发布投影，缺口时缓冲。
    -> 验证：平台领先、私有响应先到和后继先到各一例，不暴露隐藏市场事实。
  - 步骤 3.3.2：只用同一可见截点 `ValuationMarkV1` 计算 NAV/未实现 PnL。
    -> 验证：未来行情、缺失估值和重复估值不改现金或已实现 PnL。

阶段 3 完成门：订单至赎回的完整经济链可重建，模型可见时间正确，奖励和估值没有重复经济
价值，任务自审和独立阶段审查通过。

## 7. 阶段 4：持久化、恢复、对账和资源硬上限

- 任务 4.1：实现仅追加日志和原子检查点
  - 步骤 4.1.1：实现有界记录、摘要验证、原子检查点与尾部重放。
    -> 验证：一个截断日志和一个摘要不符检查点拒绝恢复，正常重放摘要一致。
  - 步骤 4.1.2：实现紧凑幂等索引、市场终态压缩和保留水位。
    -> 验证：热状态压缩前后投影等价，保留期内重复事件仍能识别，状态不无界增长。
- 任务 4.2：实现模式化恢复围栏
  - 步骤 4.2.1：training 从干净锚点重放，paper 从 sim/Ledger 共同围栏恢复。
    -> 验证：不同前缀回退共同旧围栏，不重复提交、释放、付款或赎回。
  - 步骤 4.2.2：实现 live 原始证据尾、未知提交和查询补证接口。
    -> 验证：结果未知先消歧，无法唯一解释时禁止新提交；查询不直接覆盖余额。
- 任务 4.3：实现共同前缀对账
  - 步骤 4.3.1：模拟按 `account_transition_seq` 重放比较，live 按真实接纳围栏逐项比较。
    -> 验证：平台确认投影只与同一平台前缀比较；尚未到达平台的本地预留单独守恒且与前者组合
    成完整状态。暂时滞后允许，永久摘要/订单/现金/持仓差异失败关闭；allowance 不是账本。
- 任务 4.4：冻结资源预算
  - 步骤 4.4.1：预登记多账户、重叠市场、并发意图、乱序反馈和跨结算负载并实测。
    -> 验证：冻结吞吐、处理延迟、内存、队列、索引、检查点和产物硬上限。
  - 步骤 4.4.2：验证一个缓冲超限和一个持久写入失败。
    -> 验证：停止新接入并保留证据，不丢事件、不删除未到期状态或继续乐观下单。

阶段 4 完成门：恢复、共同前缀对账和全部资源上限有独立证据；没有数据库、服务或并发框架的
推测性扩张。

    一致；同一账户轨迹的全账户序列跨市场、跨 UTC 日连续，平台确认前缀与 Ledger 共同前缀
    闭合。直接响应、生命周期反馈和查询补证不重复记账；平台已经自动赎回而 Ledger 反馈尚未
    到达时，既不得误判耗尽，也不得向模型泄漏平台隐藏现金。
  - 步骤 5.1.2：完成 `2000/1000` 正常滚动与故障轨迹。

- 任务 5.2：执行组件确定性和恢复联合验证
  - 步骤 5.2.1：固定输入、规则、场景、种子和合同重复运行。

  - 步骤 5.2.2：封存 Ledger 组件回执。
    -> 验证：绑定实现、合同、测试、资源和产物摘要，不冒充 DPT Gate B、paper 或 live 就绪。

阶段 5 完成门：Ledger 纯核心和模拟联合链通过，签发可供 DPT 消费的组件回执；外部模块状态
