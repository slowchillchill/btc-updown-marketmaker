### 2.1 模块范围与运行边界

1. 首版只支持 Polymarket Global CLOB `btc-updown-5m`、pUSD 与两个结果代币，本账户主动
   操作仅为 BUY；不建设通用多市场、SELL、体育/赛事延迟或规则插件能力。
2. `model-train`、`offline-evaluation` 和 `paper-trade` 必须通过共用
   `Intent Bridge / Execution Adapter` 的模拟后端调用隔离模拟器实例。桥接器实例创建时
   固定后端，不得逐请求切换或在失败时跨模拟/实盘后端回退。
3. `live-trade` 只通过桥接器实盘后端委托官方 Polymarket Rust SDK；模拟器不接受
   `SignedOrder`、真实签名、认证、钱包、交易凭据或订单/账户网络调用，也不生成或覆盖
   真实平台事实。
4. `data-pipeline` 是规范市场事件的唯一生产方。`sim-system` 不读取类型化原始数据、
   Parquet、实时交接或原始帧，不重做排序、去重、规范化、缺口判定、因果可用性或兑付
   派生。
5. 模拟器只输出平台原始证据；订单 NOE、非订单经济归一化、调用方 Ledger、Observation、
   标签、奖励、模型训练、筛选、晋级和 `sim-calibration` 均在本模块之外。
6. 历史训练、离线评估和模拟盘复用同一核心与合同。各实例可以共享不可变、内容寻址的事件
   页和规则/场景产物，但账户、订单簿叠加层、队列、订单、RNG、游标、反馈和检查点必须
   隔离。

### 2.2 八方法与模拟领域请求

唯一公开操作词汇为：

```text
post_order | post_orders | cancel_order | cancel_orders |
cancel_all_orders | order | orders | trades
```

1. 公开名字与官方 Rust SDK 的当前方法词汇对齐，但模拟参数和响应使用框架中立的领域类型，
   不伪装官方 `Client`，不预建通用后端 trait、插件注册表或公开 `SimRequest` 派发类型。
2. 每个请求绑定合同版本、原始调用方角色和实例、会话、账户、全局请求 ID、调用方关联 ID、
   单调调用方序列、请求发出逻辑时间及决策因果游标；变更请求另有幂等键，批量项另有稳定
   项身份。跨会话/账户、未知角色、`live-trade`、错误版本、未来游标和幂等载荷冲突必须在
   改变状态前安全拒绝。
3. GTC/GTD 限价 BUY 使用 `limit_price_pusd_per_share + size_shares`；FOK/FAK 市价 BUY
   使用 `spend_pusd + worst_price_pusd_per_share`。订单精度、计量编码和舍入复用固定官方
   SDK 的类型或工具，不以手写浮点或含义不明的裸 `size` 混用 base 与 quote。
4. `post_orders` 接受 1 至 15 项并逐项、非原子处理；一项失败不回滚已接受项，幂等重试
   保持原项到结果映射。`post_order` 只包含一项。
5. `cancel_order`、`cancel_orders` 和 `cancel_all_orders` 只取消平台处理截点仍未成交且
   可撤的本账户剩余量。批撤上限冻结为 1,000，重复 ID 只处理一次，批量和全撤都保留逐 ID
   已撤、未撤或未知结果；模拟器不得自行制造调用方撤单。
6. `order` 返回请求处理截点的单笔平台投影；`orders` 只列活动订单；`trades` 只列已经
   形成的本账户模拟成交。两个列表使用绑定查询种类、过滤条件、会话、合同版本和冻结水位线
   的不透明游标。跨保留期请求必须明确返回范围错误，不得把残缺页伪装成完整结果。
7. 首版不存在 `amend_order`、`modify_order`、`replace_order` 或隐藏等价入口。改变订单
   必须先撤单，再以新请求、幂等键、本地引用和新平台订单 ID 独立提交；二者不是原子替换。
8. 合同错误、合法平台拒绝和证据不足的未知/未建模结果必须分层；合法空页、未找到、右删失
   和反馈延迟不得误报成程序损坏。

### 2.3 低频规则冷启动与成熟工具

1. 每个新运行在首个业务请求前冻结有界、运行中不可扩展的 `run_market_set`，完成一次
   `CURRENT_QUERY` 冷启动并原子密封 `PlatformRuleSnapshot`。同一运行恢复只验证并读取
   原快照；运行中不轮询、不热刷新，新市场或新规则只能进入新运行。
2. 历史训练和离线评估禁止联网回填，只接受回放因果起点已经存在、适用时点不晚于该起点且
   来源追溯完整的 `HISTORICAL_AS_OF` 同 schema 快照。两种模式进入同一确定性核心，不
   建立第二套规则引擎。
3. 私有 `PlatformRuleHttpLoader` 只允许：
   - 每个目标 `condition_id` 调用 CLOB
     `GET https://clob.polymarket.com/clob-markets/{condition_id}`；
   - 对每批不超过 100 个目标调用 Gamma
     `GET https://gamma-api.polymarket.com/markets/keyset`，使用重复
     `condition_ids=id`，分别查询 `closed=false` 与 `closed=true` 后按
     `conditionId` 合并。
   响应顺序无语义；重复、缺失和非目标市场都失败。不使用 `condition_ids[]`、旧
   `/markets`、无关全市场扫描、重定向、订单簿、订单、账户、用户频道或认证端点。
4. 每个响应先对原始字节计算 SHA-256，再由专用窄 DTO 强类型解析。DTO 忽略未知附加字段，
   不使用 `deny_unknown_fields`；数值接受官方线协议的数字或字符串表达并直接进入精确
   十进制，禁止先进入 `f64` 或用 `serde_json::Value` 任意探测。Gamma 的 JSON 编码
   `outcomes` 与 `clobTokenIds` 必须二次强类型解析并与 CLOB 和目标集合逐项核对。
5. 只读 GET 的瞬时传输错误或官方列明的 `500/503` 在同一冷启动总时限内最多额外重试
   一次；请求最终失败、解析失败、必需身份或规则缺失/非法/冲突不重试并使整个快照失败。
6. 规则来源固定为：
   - CLOB `mos` 提供逐市场最小下单 shares；
   - Gamma `negRisk`、`feesEnabled` 与完整 `feeSchedule` 提供对应规则，费用启用时
     与 CLOB `fd.r/e/to` 核对；
   - CLOB `itode` 提供 taker 暂缓开关，按官方省略语义缺失解释为 false；
   - Gamma `orderMinSize/orderPriceMinTickSize` 和 CLOB `nr` 仅作诊断，未消费的
     `oas` 只保留响应覆盖证据。
   tick 不属于低频规则快照，任何 CLOB/Gamma 当前 tick 近似字段都不得查询为模拟器当前
   tick、写入快照或参与跨端点一致性门。
7. 仓库版本化 `sim-system/config/platform-rules-v1.toml` 只保存官方文档规则和用户冻结的
   项目/账户规则，不保存会随市场变化的逐市场当前值。首版至少固定：
   - 只有 `itode=true` 的可立即成交订单应用 250ms 平台内部 taker 暂缓，并在结束时按
     已到达状态重新校验；地域网络时延配置档不能覆盖或重复叠加；
   - 批量提交 15、批量撤单 1,000、GTD 声明提前 180 秒并含 60 秒安全偏移；
   - 手续费公式版本、5 位手续费精度、最小非零手续费、返佣日界与 1 pUSD 付款门槛；
   - 可立即成交 GTC/GTD 限价 BUY 的提交本金至少 1 pUSD；非可立即成交限价单及
     FOK/FAK 不推测套用该门；
   - 平台小额余量、固定 Silver 8% taker 返佣、两类正常现金可用时刻和付款截取规则。
8. 快照按 `queried_market_rules`、`documented_platform_rules`、
   `project_account_rules` 与 `provenance` 分区，绑定市场集合、适用时点、端点、依赖、
   尝试数、原始响应 SHA、静态配置摘要和最终 SHA-256，且不含机密。
9. 每条可执行规则必须且只能归入一种证据类别：`OFFICIAL_PLATFORM_RULE`、
   `OFFICIAL_SDK_CONTRACT`、`LOCAL_SDK_PATCH_CONTRACT`、`OBSERVED_PLATFORM_BEHAVIOR`、
   `USER_CONFIRMED_PLATFORM_BEHAVIOR`、`RULE_DERIVATION`、`PROJECT_ASSUMPTION` 或
   `UNCERTAINTY_PROFILE`。当前 250ms `itode` 路径属于官方规则，L2 队列模型与返佣付款时刻/
   截取属于项目假设，平台小额余量与即时自动赎回属于用户确认的平台行为，可立即成交 GTC
   的 1 pUSD 门属于已观察平台行为，GTD 复用该门属于机械推导。规则产物记录来源、日期、
   范围、限制、版本、摘要和失败语义；不得把观察、推导或假设升级成官方永久保证。
10. 优先复用正式工作区已锁定的成熟 Rust 依赖：`reqwest` 负责固定 HTTPS 与查询编码，
   `serde/serde_json` 负责窄 DTO，`sha2` 负责内容身份，`rust_decimal` 负责精确数值，
   `toml` 只负责静态配置。阶段 0 复核实际解析版本、许可证、安全公告、Rust 版本和锁
   文件；不自研 HTTP、十进制、哈希、TOML、数据库、重试框架、调度器或通用规则引擎。

### 2.4 公共事件消费合同（`SIM-S-004`）

1. `ExecutionMarketEventV1` 的生产语义、字段和版本由
   `plan/data-pipeline-training-plan.md` 及公共 Rust 类型拥有；本计划只规定模拟器消费
   不变量，不复制 DPT 字段清单或建立兼容猜值层。
2. 初始 tick 与动态 tick 的唯一输入都是 `ExecutionMarketEventV1`。首次逐资产完整 L2
   快照携带必填正数初始 tick；动态 `tick_size_change` 的旧 tick 可以未知，新 tick 推进
   当前状态。冷启动规则快照不得提供、覆盖或交叉校验 tick。
3. 首次完整 L2 快照只表达初始装载，不携带 `purpose`。后续完整 `book` 状态相同时只
   确认，有唯一净差额时只沿公共 `BookResyncDeltaInference` 与质量边界路径应用；不得
   再生成第二个初始快照或恢复初始/重同步用途分支。
4. `active`、`closed`、`accepting_orders` 三个可空布尔彼此独立，不压成生命周期枚举
   或组合状态机。公开成交必须保留 `trade_id`，且 `trade_id_source` 能区分平台交易哈希
   与派生源证据；模拟器不得猜测平台 ID。
5. 模拟器只在初始装载完整且当前市场状态允许时接受相应订单。缺口、陈旧、epoch 切换或
   `source_attribution_quality=UNATTRIBUTED` 本身不关闭既有 maker 订单；下一份合同有效
   完整 `book` 在其 `available_at` 形成唯一新基准。初始快照始终缺失、完整 `book`
   自身非法/冲突或规范数量不能去重守恒时，相关市场进入明确未知或失败。
6. Observation 与模拟器事件必须引用同一已最终确定因果截止点。物理预取不产生未来可见性；
   请求执行截点之后的事件不能决定过去结果，尚未最终确定的因果组不能提前应用或事后回写。

### 2.5 动态影子 CLOB、队列和撮合

1. 每个会话分别维护外部影子订单簿、本账户订单叠加层和只读派生聚合盘口。外部数量、账户
   数量和所有权不能互写；账户订单进入盘口后仍保持账户身份。
2. 唯一 maker 队列模型为 `L2_BOOK_DELTA_FIFO_ESTIMATE_V1`，证据类别为
   `PROJECT_ASSUMPTION`。账户订单排在其接受游标前已存在的同价数量之后，后到外部新增和
   账户订单依稳定全序排在当时队尾；不得提供乐观、保守、比例或随机配置档选择。
3. 对去除同一底层变化已应用数量后的外部旧数量 `E` 与新规范数量 `S`，唯一残差为
   `R=S-E`：零只确认，正值排到当时队尾，负值 `D=-R` 作为一次性队头消耗。只有消耗
   穿过本账户订单的部分才形成 maker 撮合成交；完成后外部状态仍精确锚定 `S`。
4. `price_change`、公开成交和后续 `book` 对同一底层变化只应用一次；
   `best_bid_ask` 只更新或校验最优价格，不推进数量。公开成交与盘口变化没有权威共同
   因果 ID 时保留 `UNATTRIBUTED`，L2 推定结果标记 `DETERMINISTIC_INFERRED` 与
   `not_official_fifo=true`，不能冒充真实订单排位。
5. 可立即成交 BUY 在平台到达时完成适用准入；只有规则快照 `itode=true` 才进入 250ms
   内部暂缓并在结束时重校验。随后按价格优先从最优卖价逐档消费至限价/最差价格。GTC/GTD
   剩余量挂单，FOK 全成或全不成，FAK 成交后终止，post-only 会立即成交时拒绝。
6. 同一外部流动性、账户流动性或规范队列消耗证据在会话内只能消费一次。外部档位、队列
   归因、账户 taker、订单 base、成交最终性分桶与 quote 资金必须分别守恒，任何单位不得
   跨 base、quote、pUSD 或手续费币种相加。

核心数量关系固定为：

```text
external_pre + external_addition
= external_decrease + external_post

canonical_queue_head_depletion
= external_queue_progress + sum(account_maker_order_matched_delta)

account_taker_matched_quantity
= external_eligible_liquidity_consumed_by_account_taker
```

第一、二式是同一外部证据在外部状态与账户队列叠加层的分层投影，不能相加为两次市场变化；
第三式的成交两侧也不能相加为双倍执行。

### 2.6 订单、成交、账户和平台小额余量

1. 订单撮合轴与成交最终性轴分离。订单投影区分已接受、已撮合、活动未成交、平台小额余量
   关闭、调用方撤单、订单类型终止、到期和市场关闭；成交投影区分待处理且经济已应用、
   待处理且未应用、最终成功、失败补偿待处理、已补偿和未应用失败。
2. 每笔撮合成交拥有唯一 `fill_economic_delta_identity` 和规则选定的经济应用截点。后续
   `MATCHED_NOT_BROADCASTED`、`MATCHED`、`MINED`、`CONFIRMED`、`RETRYING`、
   `FAILED` 只推进生命周期；补偿只在原变化量已应用时引用原身份幂等执行一次。原变化量
   未应用时只释放相应待处理资金占用，不生成反向经济变化。
3. 所有改变模拟账户的成交、补偿、资金释放、返佣、付款和赎回共用单调
   `account_transition_seq`、前驱身份和账户之前/之后摘要。反馈可以迟到或乱序，但调用方
   必须能识别缺口、缓冲、按序应用和幂等去重。
4. `VENUE_DUST_TERMINAL` 只适用于本账户已接受、按 base 计量且已经有正撮合数量的订单：
   撮合/队列转换冻结后，其精确活动余量严格位于 `(0, 0.01 shares)`，且同价外部前后数量
   与其他账户订单均已由同一合格转换耗尽，才原子把该精确余量转入小额余量终态并把活动
   余量归零。
5. 平台小额余量不得读取外部盘口余量、使用概率或随机数量、夹紧余量、倒扣已撮合数量或
   生成额外成交、份额、费用、名义金额和现金流；只幂等释放该活动余量对应的实际资金占用。
   FAK 未花 quote、撤单、到期、市场结束、手续费份额差异和外部小量均使用各自语义。
6. 查询和反馈中的 base、quote、pUSD、手续费、原始计量基准、标度和币种必须显式。调用方
   不得被迫从裸份额反推资金变化，也不得把外部盘口数量写入本账户分桶。

按 base 计量的已接受订单必须满足：

```text
accepted_base_quantity
= order_matched_base_quantity
+ venue_dust_closed_base_quantity
+ canceled_base_quantity
+ expired_base_quantity
+ market_closed_base_quantity
+ open_base_quantity
```

`order_matched_base_quantity` 另在最终成功、待处理已应用、待处理未应用、失败补偿待处理、
终态失败已补偿和终态失败未应用六个互斥结算分桶中守恒。按 quote 预算计量的订单必须满足：

```text
accepted_quote_budget
= final_success_budget_consumed_quote_amount
+ pending_applied_budget_consumed_quote_amount
+ pending_unapplied_encumbered_quote_amount
+ released_or_unspent_quote_amount
+ open_encumbered_quote_amount
```

FOK/FAK 的固定 SDK `takerAmount` shares 等价值只作 base 审计投影；订单类型终止的未成交投影
进入 `canceled_base_quantity` 并保留专属 `terminal_reason`，未花预算只进入 quote 释放分桶。
每次余额或资金占用变化均由结构化 `PlatformAccountDelta` 表达；撤单、订单类型终止、到期、
市场关闭、平台小额余量和未应用失败各使用独立幂等 `encumbrance_release`，不得重复释放。

### 2.7 maker/taker 返佣与自动赎回

1. maker 返佣只来自最终成功、实际以 maker 身份成交的本账户数量；每笔使用撮合时冻结的
   `MarketFeeScheduleSnapshot`：

   ```text
   maker_fee_equivalent_pusd
   = executed_maker_shares × rate × [price × (1 - price)]^exponent

   maker_rebate_accrual_contribution_pusd
   = maker_fee_equivalent_pusd × rebate_rate
   ```

   逐笔贡献只供审计和逐市场汇总；只有唯一
   `MakerRebateAccrualFinalized` 可以增加 maker 应收款。规则有效但异常输入终态使潜在
   合格成交永远无法闭合时才使用 `UNKNOWN_INCOMPLETE`；无效规则快照不得进入核心。
   结果还必须区分 `CALCULATED`、`ZERO_NO_ELIGIBLE_MAKER_FILL`、
   `ZERO_FEES_DISABLED_OR_NO_REBATE` 与 `UNSUPPORTED_RULE_VERSION`；费用关闭或零返佣先形成
   明确零结果，费用启用且正返佣但 `taker_only=false` 才属于不支持规则版本。
2. taker 返佣只来自最终成功、实际收取正 taker 手续费的成交：

   ```text
   taker_rebate_accrual_pusd = actual_taker_fee_pusd × 0.08
   ```

   每笔唯一 `TakerRebateAccrualApplied` 只增加 taker 应收款。首版固定 Silver 8%，不
   累计或校验 wV，不查询等级、不实现动态等级或一次性奖金。
3. maker 与 taker 以“返佣种类 + 成交归属 UTC 日”分别维护未结日桶。D 日 taker 的正常
   现金可用时刻为 D+1 00:10 UTC，maker 为 D+1 00:45 UTC；只有该日全部潜在贡献在模拟
   平台内部闭合后才日结。普通训练截尾只保留未结应收款，不提前付款或制造未知终态。
4. 同类当日应计小于 1 pUSD 不付款且永久不并入后续日期；达到门槛时
   `paid=floor(accrual×10000)/10000`，截取余数继续锁定且不参与后续门槛。付款只把对应
   应收款一比一转为现金和可用现金，不改变 NAV、PnL 或训练奖励；两类返佣永不互相凑门槛。
   日结分别生成 `MakerRebateDayFinalized` / `TakerRebateDayFinalized`，付款分别生成
   `MakerRebatePaid` / `TakerRebatePaid`；日结与付款各自只发生一次。
5. 每个市场在市场结束且潜在 maker 经济最终性闭合后形成一次 maker 应计终态，全部合格
   taker 应计也必须形成。市场判定处理器只引用这些结果，不重新汇总或应用。
6. 合格 `MarketResolved.available_at=T` 到达时，先闭合全部因果上更早的成交、补偿、返佣
   和市场结束订单/资金释放，再按稳定子顺序以模拟账户实际结果代币余额和兑付向量原子销毁
   代币、增加 pUSD，并在同一逻辑时点生成唯一 `AutoRedeemApplied`。零余额也生成零变化
   终态反馈；重复、恢复或迟到不得重复赎回。
7. 结算屏障不完整、兑付冲突或缺少合格市场判定时明确失败/隔离，不得猜测、先按较小余额
   赎回，或新增调度、待处理、重试和失败赎回状态。

### 2.8 输出、生命周期、恢复与资源

1. 直接请求响应、`OrderLifecycleFeedback`、`TradeLifecycleFeedback` 和
   `SettlementLifecycleFeedback` 是彼此独立的封闭合同，通过稳定请求、订单、成交、市场、
   账户和结算身份关联。结算反馈首版包含自动赎回、两类返佣应计、两类日结和两类付款。
2. 输出保留模拟平台原始状态拼写和 SDK `Unknown(raw)`，明确标记为模拟；下游 NOE 才负责
   按接口面归一化。模拟器不输出 NOE、Ledger 事件、奖励、标签或真实平台格式。
3. 市场生命周期单向为：

   ```text
   PRELOADING
     -> ACTIVE
     -> POST_END_PENDING_RESOLUTION
     -> RESOLUTION_TERMINAL | EXHAUSTED_QUARANTINED
     -> EVICTED
   ```

   市场结束后先关闭本账户活动订单并释放其资金占用，再释放完整盘口和大缓冲；结算、返佣、
   反馈、查询投影和幂等证据持久化并满足引用屏障后，才移除紧凑热状态。输入终态缺失使用
   会话失败封存，不能伪造市场终态。
4. 热移除不等于查询记录删除。`order` 和 `trades` 在保留期内从紧凑索引返回相同终态；
   `orders` 不含终态订单；历史被裁剪时返回明确水位线/超出保留期，保留期到期后旧会话
   整体不可查询，不永久积累逐订单墓碑。
5. 训练首版从干净账户轨迹起点确定性重放，不从中途模拟器、账户或 Ledger 检查点续跑。
   模拟盘必须能从原规则快照、原子检查点、紧凑仅追加日志和 DPT 仅追加事件日志恢复，且不
   重复撮合、撤单、资金释放、返佣、付款、赎回或反馈。
6. 内存、热市场、输入/请求/反馈队列、活动订单、内部事件、查询缓存、单会话索引、单运行
   产物，以及整个运行时/产物根的记录数量和字节分别具有实测硬上限。超限时停止新接入并
   明确失败，不静默丢弃、删除未到期证据或无界扩容。
7. 每个正式运行至少绑定 `PlatformRuleSnapshot`、`RuleCoverageManifest`、
   `PlatformScenario`、公共事件合同/生产器、代码/构建、配置、随机种子和输入谱系，并生成
   `SimulationRunManifest`、仅追加请求/反馈证据、紧凑查询投影、生命周期/保留期报告、资源
   高水位和不变量报告。`SimulationRunManifest` 必须明确绑定规则快照、场景、随机种子、
   请求/反馈合同、确定性脚本意图身份和原始反馈摘要；其内容身份与 SHA-256 供 DPT 候选
   清单直接引用。全部持久产物均绑定 SHA-256 并原子封存。
8. 产物不得包含钱包、凭据、模型张量、训练检查点、类型化原始数据、调用方 Ledger 或完整
   规范事件带副本；确定性核心除已释放的冷启动加载器外必须能在断网、无钱包、无凭据、
   无模型框架和无 GPU 环境运行。
