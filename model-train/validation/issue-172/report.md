# #172 帧延迟：证据与取舍

本报告记录 [#172](https://github.com/slowchillchill/btc-updown-marketmaker/issues/172) 的实测依据。保留同帧 BBA 时间共用与不可变规则投影，原生 8 线程普通组均值两轮下降约 4.9%／4.1%。完整链路的 1,024 组样本全部超过 4 ms；本轮没有达到 4 ms 或 1 ms 目标，也没有证明各场景的完整链路均稳定提速。

## 合同和样本边界

获批基线为 `e57503821391a9943ce694eabab00ec0fdff1141`。沿用 `native_inputs_v5` 的五输入、完整六侧档位、两张图、float32 权重和原浮点运算顺序。精确有理数先完成既有投影，再得到最终 f32；没有截断盘口、改动合法动作、改变 hidden 生命周期、增加保护性丢弃或扩展完整输入增量缓存。

原始录制为 `target/realmarket-review-20260926/input-trace-r2`；原 1,024 帧输入为同批 `sampled-inputs`。原生清单沿用 `target/issue-170-performance/native-selection.json` 与来源、属性文件，以实际消费组去重：五分钟各 64 组共 320 组，旧 20 组，以及价量变化和缓存未命中两段各 64 组。选中组中的所有模型行都保留。高更新段每组同时含目标市场决定行与下一市场上下文行，64 组需要 128 次状态计算。

普通段为组 `201582—201645`，其目标市场前史有 7,752 个 ContextOnly 行。高更新段为 `418584—418647`；不能把普通段的短前史当成高更新段的 hidden。每个代表的所有 GRU 层都沿实际行顺序独立递推，初始化、上下文、决定和退休遵守原根合同。

录制完成统计中的 219,511 是原候选资格计数；#170 从同一录制恢复的原生完成产物记录实际目标 DecisionRequired 为 219,484，以及 28,652 个 ContextOnly 行。差异不能通过改分母消除。421,714 个源输入、421,621 个公开关闭组、420,725 个原生组属于不同层次。这些全窗口来源统计不冒称本轮只到组 418647 的有限前史计数。

## 计时和准备成本

原生单项计时包括整个 `NativeInputRoot::consume`，包括本组公共共享应用、账户冻结、编码和输出构造。恢复无交易前态、复制缓存及正确性核对在计时外，各有准备字段。冷缓存组单列，不混入热组均值。

两代表真实前史共同准备的进程墙钟为 2:23:31，累计进程 CPU 为 40,943.82 秒，峰值 RSS 为 2,867,292 KiB，退出码 0。普通入口到达耗时 470.324 秒，每个代表各有 7,752 个先前模型行；高更新入口为 8,600.663 秒，每个代表各有 243,172 个先前模型行。准备完成至组 418647，总计 243,300 个模型行／代表，其中 217,066 个 DecisionRequired、26,234 个 ContextOnly。两个入口的独立反序列化根在随后各 64 组的完整原生输出、共同历史／缓存和 Ledger 投影对照全部通过，共 128 组。保存的前史源码逐项 SHA-256 匹配后归档，之后才生成正式宿主；其源码与二进制身份分别保留。

完整服务使用独立 Rust ORT 宿主，不导入 Python，不开启 ORT profiler。计时从本组 `consume` 前开始，到所有适用 Actor 的实际执行入口返回为止，包括完整原生构造、打包、状态图、对象编码与归约、每步支持集和参数评分及执行。逐组序列化、hidden 摘要和证据写入在计时终点之后。公开输入读取、关闭组解码、图加载和预热不在该服务时间内，分别属于离线准备或入口工作；因此它不是“收到网络字节至订单完成”的线上总延迟。

诊断计时包含读时钟、锁和计数开销。`diagnostic_ns` 是独立诊断根调用的外层时间；它与 completion 内的 `target_consume_samples_ns`、内部阶段累计时间不是同一指标。内部作用域存在包含关系，工作线程上的累计时间还会重叠，不能求和成为完整服务时间，也不能直接解释成 CPU 占比。

图诊断使用原筛选器的 133 帧：两个代表分别是 MAIN-1×256／ORT 4 线程、MAIN-30×1024／ORT 16 线程。正式原生版本使用 1／4／8／16 线程两轮反序；完整服务原生固定 8 线程。全部 CPU 正式计时串行。进程 CPU 是所有进程线程累计的 CPU 时间；RSS 是进程资源，不能归给某个算子。短片段 P99 和最大值仅描述这些样本，不是最坏情况上界。

133 帧单帧图筛选沿原基准的零 `h_prev` 和真实已打包特征输入；准备张量在计时外。它回答相同输入口径下的图候选问题，不能替代逐帧真实 hidden 的完整服务片段。

### Binance 完整九维输入复用

只比较冻结片段内相邻实际组、同一市场同一侧，以精确有理价格关联，再逐位核对全部九个 f32。五个普通片段共有 630 对相邻侧、870,342 个当前档位，其中 870,270 个完整九维相同，按当前档位加权为 99.9917%；整侧顺序与全部输入相同为 622／630（98.7302%）。价量变化段的 126 对侧和高更新段的 252 对侧全部相同。高更新段两市场分别计数，不能当成 126 次独立行情变化。

本统计在已完整生成输入后观察相等性，是复用潜力证据；没有测出可低成本识别这些行的缓存算法，也不表示 fast、slow、PM 盘口或五输入整体不变。

普通片段观察到 47 个插入、38 个删除、25 个同价格九维变化；旧 20 组另有 9／6／2。所有这些相邻对中，Binance 最佳价格变化次数均为 0；不能据此推断最佳价跳变时仍有同样命中率，也不能覆盖每段入口前未保留的那次转移。插删仍可能改变当前坐标和归约树，即使其余逐价格输入未变。Binance 逐档 T5 当前为未知的零值，只是本合同的一项事实，不表示其他时间输入都可复用。

按本编码器 32 个 f32／档，仅当前组所有模型行 Binance 编码有效载荷的最大观测值为 747,776 字节；它不包含价格键、索引、容器节点、容量、暂态双份或归约树，不是缓存堆峰值。逐侧原始计数及逐对证据见 [binance-reuse.json](evidence/reuse/binance-reuse.json) 与 [binance-reuse-calls.csv.gz](evidence/reuse/binance-reuse-calls.csv.gz)。后续输入专项可以复用帧与失效观测；编码缓存则需要新图边界及训练处理，二者的收益不能相加。

### 动作图输出选择和重复对象编码

本机 Python ORT 为 1.28.0，Release build `45de2a8b06`。Python 独立能力探针在设置 `only_execute_path_to_fetches=true` 后，分别请求全部输出、仅 `family_logits`、仅 `cancel_embeddings`：小模型三者均执行同一组 1,629 个节点事件，大模型均为同一组 5,859 个节点事件。该探针是带一个有效零特征对象的图输入，不是实际市场动作延迟。

纯 Rust 宿主随后使用实际动态加载的同一 C 库和 `ort 2.0.0-rc.13` 的 `OutputSelector` 重复核查。两代表三种选择仍分别为 1,629／5,859 个节点事件，完整节点名字多重集相同，`ort::info()` 也返回同一 build；该 Rust 接口没有冒称设置 Python 的额外执行路径标志。[能力探针摘要](evidence/action-fetch/summary.json) 保留请求／返回输出、原始 profiler 身份和逐节点表。这里只验证当前实际构建，不能推广为所有 ORT 构建都没有该能力。

[ORT 1.28.0 的执行器实现](https://github.com/microsoft/onnxruntime/blob/v1.28.0/onnxruntime/core/framework/sequential_executor.cc#L670)把这条剪枝路径放在 `ENABLE_TRAINING` 条件内；普通分支显式忽略该参数。源码与本机观测一致，不能靠少取输出宣称当前推理构建跳过其他 head。

现有 `OrtActorScorer::reduced` 为每个有效对象块调用动作图并取 embedding；后续参数评分继续传入该块，当前图会重复计算对象编码。真正分离对象编码与参数 head 需要新的图边界、输入输出合同及跨块/三端验证。它属于后续设计，本轮不偷偷拆图。

### 精确数学库与认证快路径

冷组观察到 6,027 个不同 log 输入，其中 5,593 个分母不是二的幂；最大分子 59 位、最大分母 42 位。这反映业务输入是精确有理数，不能自动当成已精确表示的 f32 输入。

[CORE-MATH](https://core-math.gitlabpages.inria.fr/)公开的是 binary32、binary64 等格式的函数，包括 log1pf；binary32 单变量实现以穷举验证。该合同不等于“任意精确有理数经 log1p 后一次正确舍入为 f32”。先把本仓库有理数舍入成 f32 或 f64 已引入输入误差，最终输出接近舍入边界时不能忽略。

[RLIBM-ALL](https://arxiv.org/abs/2108.06756)的 n+2 位 round-to-odd 证明也有其浮点输入表示前提，不覆盖任意有理数先行舍入的缺口。若后续采用区间认证与精确回退，需要分别证明原输入包络、函数误差界及最终唯一舍入，并实际测量认证与回退开销。本轮没有替换经济类型或精确数学算法。

### 融合、持久归约和线程流水

当前状态图的 LayerNorm、盘口仿射和归约使用固定配对顺序。标准优化开关已为 ALL；“融合”不能仅凭代数等价改变中间 f32 舍入、sum 树、mask、空侧、max 并列首项梯度和有符号零行为。上面的整数形状候选证明，即使消除节点且位相等，也不保证净收益。[ORT 图优化文档](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html)和[性能分析文档](https://onnxruntime.ai/docs/performance/tune-performance/profiling-tools.html)用于区分优化资格与实测结果。

持久归约树若按价格键建树，会改变本合同按当前档位坐标相邻配对的树；插删、重新排序、动态补齐宽度、mask 空洞和计数变化都可能要求更新祖先。sum、mean 和 max 还分别需要保持同一加法树、整数有效计数及首个并列位置。它不能等同于“只重算变化价格”而直接替换当前图。

线程流水必须处理下一组输入与上一组动作反馈、账户冻结和同根 hidden 的依赖，不能用同时启动两个线程池当成吞吐改善的证据。本轮保持原语义的顺序完整服务，用四档原生线程和两个模型的 CPU、尾部及完整服务结果讨论后续方向；不承诺跨帧并行，也不改变 CPU 亲和性、频率或系统服务。
