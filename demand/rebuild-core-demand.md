  ### 模型评估与晋级业务流程

  ```mermaid
  flowchart LR
    TRAINING["model-train<br>训练 + 训练内诊断/选优"] --> CANDIDATE["冻结 ModelBundle<br>TrainingCandidateReceipt"]

    OFFLINE -- OfflineEvaluationReceipt PASS + PromotionDecision --> PAPER["paper trade<br>NO_REAL_FUNDS"]
    PAPER -- PaperQualificationReceipt PASS + PromotionDecision --> SHADOW["live shadow<br>NO_REAL_FUNDS / NO_SUBMIT_PERMISSION"]
    SHADOW -- LiveShadowReceipt PASS + PromotionDecision --> READY["可申请首次真实资金授权<br>仍不可提交"]
    READY -- UserFundsAuthorizationReceipt + run-admission PromotionDecision --> SMALL1["ModelRegistry active<br>SMALL_LIVE_1_MARKET"]
    SMALL1 --> SMALL1_RECEIPT["SmallLive1Receipt PASS"]

  ```

  上述模型生命周期是不可跳级的业务顺序；图中每条带 receipt 的转换都表示 Promotion Controller 校验前序证据后签发 `PromotionDecision`，receipt 本身和阶段 runtime 都没有 ModelRegistry、promotion stage 或资金 admission 状态写权限。真实资金阶段必须使用两个分离 decision：run 启动前的 admission decision 只绑定当前已通过 stage 与本 run 授权、不提前推进 stage；run 完成后的 completion decision 只在 PASS receipt 已存在且 admission 已关闭后推进到 `*_PASSED`。下一档用户授权只能在该 completion decision 落盘后签发，禁止把前一档完成与下一档 admission 合并为一个状态转换。训练内评估只负责诊断训练是否有效、在预算内选优和生成可解释报告，不是 paper/live 晋级 gate；model-train 只能签发 `TrainingCandidateReceipt` 和落盘不可变 bundle，由 Promotion Controller 验证后才能注册 ModelRegistry candidate。只有独立 `offline-evaluation` 可以读取晋级用时间外留出集并签发 `OfflineEvaluationReceipt`。paper、live shadow 和各级真实资金运行必须消费前一阶段绑定同一 `ModelBundle` 与合同身份的 PASS receipt；任何缺失、失效或不匹配都必须阻止进入下一阶段。ModelRegistry 状态、promotion stage、资金授权和执行权限是四条独立轴：模型成为 active 也不自动获得任何真实资金授权，每次 small-live / formal-live 仍必须按本文要求单独取得本 run 有效的用户授权。

  架构图只表达高层业务处理流程，不把权限/硬边界、schema 字段、具体订单状态枚举或 artifact 字段画成独立业务模块。Paper/live trade 图表表达在线运行闭环：`data-collect` 只把外部市场源转化为 realtime handoff、coverage、health/gap 和 manifest；paper 与 live 各自独立运行 `data-pipeline` 的 online-stream runtime / Market Context Builder，消费本机 `data-collect` realtime handoff、运行期 append-only log 和本实例 ledger projection，并调用与训练完全相同的版本化确定性处理核心生成实时市场上下文和模型输入。只有通过相应前序晋级 receipt 的模型产物才能加载到 paper/live；paper 把模拟订单提交给 `sim-system` 并消费其平台反馈，live 把真实订单提交给真实平台，二者返回的 raw evidence 经 NOE 和 ledger 后只回到本运行实例作为下一次交易状态反馈；进入训练只能通过离线反馈入库、训练数据集或校准数据池。

  Train 图表表达离线训练与回放闭环：`data-collect` 提供历史外部市场源typed raw、coverage、last-qualifying时间、availability运行诊断、missingness因果基础和manifest；训练独立运行`data-pipeline`的offline-replay runtime，按因果可见顺序把历史市场数据与本训练实例的NOE/Ledger projection送入同一版本化确定性处理核心，由`ObservationContract`因果派生age/mask并生成与offline-evaluation/paper/live相同的模型输入；只有离线数据构建侧的label builder、feedback-ingestion、训练切分和校准数据池可以额外消费权威resolution、达到maturity的NOE/Ledger派生反馈、order evidence digest/reference和reports。训练模块再消费明确分配给train/development/calibration/validation的数据，使用同一套`Intent Bridge / Execution Adapter`合同把模拟订单提交给`sim-system`，由`sim-system`模拟订单提交到平台后的accepted/rejected、成交、部分成交、不成交、撤单、延迟和结算反馈，再经NOE/Ledger用于回放和样本构造；training run只能加载冻结的simulator规则/校准版本，其结果若要影响simulator，必须经受控离线校准流程生成后续新版本。reward只能由训练模块唯一的版本化RewardContract根据模型action、本训练实例可回放ledger before/after、valuation和terminal evidence计算。训练模块生成不可变candidate ModelBundle、训练报告和训练批次排名表。训练内表现指标用于诊断和选优，不能因单一或组合表现阈值阻断整个训练批次完成，也不能代替独立offline-evaluation；训练产物不得跳过offline-evaluation直接进入paper/live。训练模块不在paper/live在线交易闭环中实时接收ledger反馈，也不得让paper/live的执行流程直接循环回训练。

  `sim-system` 是训练模块、独立 offline-evaluation 与 paper trade 共同调用的唯一模拟平台模块；三者必须使用隔离运行实例，但调用同一套版本化 `sim-system` 实现、规则合同和 artifact schema。training、offline-evaluation、paper、live 共享同一版本化 `data-pipeline` 确定性处理核心以及 Intent/NOE/Ledger 等合同；图中共用公共模块均在模块开头标注“（共用）”。共用表示同一代码实现、schema、配置、normalization artifact、时间线、causal cutoff、特征/输入合同和可回放语义，不表示共享进程、队列、checkpoint、缓存、运行根或 ledger 状态；四个角色必须分别运行各自实例。训练、offline-evaluation 和 paper 只能通过 `sim-system` 模拟订单提交平台后的反馈；live 只能通过真实平台模块连接官方 Polymarket Rust SDK 或经批准的 SDK 缺口方案发送到平台，禁止调用 `sim-system` 生成或覆盖真实执行事实。`sim-system` 必须由真实平台 artifact、当前规则证据、潜规则和 issues 校准。两类平台都必须先保留 raw evidence 并使用同一版本化 `NOE / NormalizedOrderEvent` 合同，但运行状态严格隔离：`sim-system -> train/offline-evaluation/paper NOE/ledger`，`真实平台 -> live NOE/ledger`；共享合同不代表共享 ledger 实例或允许模拟证据进入 live。

  权限、SDK、wallet、schema、路径、平台约束、模型 bundle、关键 writer 等硬边界校验发生在程序启动、自检、热身、T-30 预加载以及运行前/运行中的权限模式校验中，不作为图中的独立业务决策模块。执行时硬边界只能把 `execution_permission` 设为 `ALLOW_SUBMIT`、`NO_SUBMIT_PERMISSION`、`CANCEL_ONLY_PERMISSION` 或 `PAUSED_PERMISSION`，并写入 audit/operator；不得改写模型交易/风控意图，也不得把硬边界 verdict 当作训练标签或模型执行反馈。Ledger 是账户、持仓、挂单、pUSD CASH、NAV 等状态权威；训练报告、OfflineEvaluationReport 和交易报告必须能追溯到市场上下文、模型意图、raw evidence、NOE、ledger、manifest 和 artifact。

  ### 模块边界术语

  1. `data-collect` / `./data-collect/` 专指外部市场源采集模块，只负责 market discovery/metadata（market_id、condition_id、token_id、start/end、market lifecycle state、runtime current/next role、tick size、min size、fee/rebate、reward eligibility）以及 Polymarket market channel、Binance BTCUSDT depth、Binance BTCUSDT aggTrade、Polymarket RTDS Chainlink BTC/USD 的 raw evidence、`recv_time_utc`、typed raw parquet、realtime handoff、source coverage、source health/gap、reconnect trace、manifest 和 atomic publish；不负责 labels、features、tick_stream、训练切分、模型输入加工、paper/live append-only log、order evidence、NOE/Ledger 或 execution feedback ingestion。
  2. `data-collect` 的三种运行角色必须分别构建、记录 sha256 并独立部署为三个 release binary：`data-collect-training-collector` 只部署在数据采集服务器，`data-collect-paper-hot` 只部署在 paper trade 服务器，`data-collect-live-hot` 只部署在 live trade 服务器。三者共享 source/schema/handoff 合同，但不得共享进程、运行根、钱包、交易状态或消费者 artifact；`data-collect-live-hot` 是独立的外部市场源 handoff binary，不是 live-trade 主交易程序。
  3. `Market Context Builder` / runtime context builder 专指 `data-pipeline` 在 paper/live 热路径中的 online-stream driver 与运行编排层；它消费本机 `data-collect` realtime handoff、运行期 append-only log、NOE/Ledger projection 和模型 bundle 合同，驱动第 4 条的同一确定性处理核心，但不得另行实现 feature、normalization 或模型输入组装语义，也不能把 finalized parquet 当作 paper/live 热路径事实来源。
  4. `data-pipeline` / `data-processing` 专指 training、offline-evaluation、paper、live 共用的数据处理模块。它必须只有一套版本化、确定性的模型可见处理核心；该核心包含唯一的共享 semantic canonicalizer，统一负责从 lossless decoded source evidence 到 canonical event 的字段、单位、枚举、timestamp/causal-availability 映射，以及后续 total order、同毫秒 tie-break、去重、late/gap、market 隔离、因果持续状态、feature、normalization、Ledger projection 合并和 `ObservationContract` 组装。training 与 offline-evaluation 各自以独立 offline-replay runtime 消费彼此权限隔离的 finalized typed raw 分片，paper 与 live 各自以独立 online-stream runtime / Market Context Builder 消费 realtime handoff；driver 只能负责 I/O、framing 和无损 transport decoding，不得拥有语义 canonicalization。四个运行实例不得共享进程、队列、checkpoint、状态缓存、运行根或 ledger；只有离线数据构建侧可以额外生成 market supervision labels、execution-feedback labels、tick_stream、replay context、训练切分、校准数据池和 offline-evaluation 时间外留出集，且 model-train 不得读取该留出集。reward 不属于 `data-pipeline` 输出，只能由训练模块唯一的版本化 RewardContract 计算。runtime 可以由后续批准计划选择嵌入对应 training/offline-evaluation/paper/live 宿主 binary 或作为本机 sidecar，但必须 mode-local，禁止成为四个环境共用的远程服务或状态实例；每次构建必须固化由 version 与 source/build digest 组成的 `pipeline_core_identity`，并同时记录宿主或 sidecar binary sha256。
  5. `feedback-ingestion` 专指按来源路由 paper/live/simulation 的 append-only log、live artifacts、order evidence digest/reference 与 NOE/Ledger 输出：paper/simulation feedback 只能进入后续训练数据构建和审计；只有经审查的真实平台/live feedback 且被预注册独立 calibration split 纳入时，才能作为 `sim-calibration` 的经验 calibration target。paper/simulation 证据最多用于回归验证 simulator，禁止用 simulator 自身输出或 paper 模拟结果反向校准 simulator。它不是 `data-collect`，也不授权 offline-evaluation 用历史行为策略 execution feedback 替代当前 candidate 的评估结果。
  6. `sim-system` 是当前系统对模拟平台模块的唯一规范名称。它接收 training、offline-evaluation 或 paper trade 产生的 BUY-only 模拟订单意图，模拟订单提交平台后的执行与生命周期反馈，输出模拟 raw evidence；它不是模型、训练框架、evaluator、paper runtime、真实平台、NOE 或 ledger，也不得被 live trade 调用为真实状态源。
  7. `market_lifecycle_state`、`market_runtime_role`、`model_registry_state` 和 `deployment_hardware_status` 必须命名空间隔离：market lifecycle 可以使用 candidate / prefetched / active / retired；runtime role 表达 current / next 等相对角色；ModelRegistry 只使用 active / shadow / candidate / retired；`requires_hardware_upgrade` 只能是独立的部署硬件状态或 gate verdict，不能成为第五种 ModelRegistry 状态。不得跨域比较裸字符串。
  8. 模型策略态、gate 判定和执行权限必须使用独立字段：模型使用 `model_strategy_mode=ALLOW_SUBMIT|MODEL_NO_SUBMIT|MODEL_CANCEL_ONLY|MODEL_PAUSE`；gate 使用 `gate_verdict`；执行边界使用 `execution_permission=ALLOW_SUBMIT|NO_SUBMIT_PERMISSION|CANCEL_ONLY_PERMISSION|PAUSED_PERMISSION`。`ALLOW_SUBMIT` 允许执行通过 preflight 的模型 submit/cancel intent；`NO_SUBMIT_PERMISSION` 是 observe/reconcile-only，阻止所有模型来源的平台变更；`CANCEL_ONLY_PERMISSION` 阻止 submit，但允许执行明确的模型 cancel intent；`PAUSED_PERMISSION` 停止消费模型 intent。operator emergency cancel 是独立 actor，不因模型权限态消失。不得跨字段比较裸字符串；执行权限只能允许或阻断模型 intent，不能把一个 intent 改写成另一种模型策略。
  9. `account_global_projection` 专指跨 market 唯一的 pUSD 现金、reserve、matched-pending exposure、账户级 NAV 和 ledger sequence；`market_local_projection(market_id)` 专指目标 market 的两个 outcome position、订单列表、pending cancel 和 lifecycle 状态。旧 market 的经济影响必须进入 account-global 投影，但其订单、持仓和 lifecycle 明细不得混入新 market 的 market-local 投影。
  10. `offline-evaluation` 专指训练完成后的独立、只读、artifact-driven 晋级评估模块。它加载冻结 candidate ModelBundle 与最新合格且完整、从未进入训练或任何自适应决策的时间外留出集；“任何自适应决策”至少覆盖 development/calibration/validation、early stopping、HPO、候选排名/选优、normalization 拟合，以及人工 feature、RewardContract、评估阈值、baseline 或 `sim-system` 参数/规则设计。该模块使用独立 `data-pipeline` offline-replay runtime、`sim-system`、NOE 和 Ledger 实例生成 `OfflineEvaluationReport` 与 `OfflineEvaluationReceipt`；不得训练或微调模型、重拟合 normalization、改变 candidate bundle、改写留出集、校准 simulator、写 ModelRegistry 或直接授权 paper/live。它可以先实现为独立 batch/CLI job，不要求成为长驻远程服务，但必须有独立 runtime role、命令入口、权限和 artifact 根。
  11. `Promotion Controller` 专指消费各阶段 PASS receipt、用户明确授权证据并签发 `PromotionDecision` / run admission 的唯一 writer；只有它可以注册或改变 ModelRegistry、推进 `promotion_stage`、为本 run 设置 `funds_authorization_tier`，以及写入 receipt/资金授权的 append-only 状态事件。每个 decision 必须绑定唯一 decision id、`expected_current_stage`、前序 receipt/decision digest 和目标状态，形成 append-only 审计并保证同一请求幂等；真实资金 admission 还必须绑定目标 environment、公开 wallet/funder/address identity、稳定且不会随事件变化的 `account_global_ledger_id`、`admission_start_ledger_sequence/digest`，原子检查唯一性并设置 `active_admission_run_id`。唯一性键必须同时满足：同一 `(environment, wallet, funder, account_global_ledger_id)` 跨所有 promotion chain 最多一个未关闭 admission；同一 promotion chain 无论账户为何也最多一个未关闭 admission。旧 run 只有在完成、失败、中断或撤销事件关闭 admission 后，才能在同一 stage 重试。stale、重复消费、并发竞态、current stage/账户/environment 不匹配或任一唯一性键已有 outstanding admission 必须拒绝，具体事务实现留给获批后的计划。它可以是后续批准实现中的最小本地控制组件，不是模型、评估器、用户授权来源或交易策略。model-train 只能提交不可变 bundle + `TrainingCandidateReceipt` 的注册请求；training、offline-evaluation、paper、shadow/live runtime 和排名表都不得自行跨级、写上述三条轴或给自身签发下一阶段权限。
  12. `UserFundsAuthorizationReceipt` 是 Promotion Controller 根据用户对单次真实资金运行的明确批准生成的不可变、一次性 run admission artifact，至少绑定 receipt/schema id、authorization id、用户批准证据 digest、candidate bundle、签发时 current promotion stage、目标 `funds_authorization_tier`、run id、目标 environment、公开 wallet/funder/address identity、稳定 `account_global_ledger_id`、目标 market 或最大市场数/时长、issued/expiry time 和前序 receipt；不得写入 secret，也不得用随事件变化的 ledger digest 代替稳定 ID。receipt 本体不得原地修改；授权状态只允许 `UNCONSUMED -> BOUND_TO_THIS_RUN|EXPIRED|REVOKED|INVALIDATED`，以及 `BOUND_TO_THIS_RUN -> COMPLETED|FAILED|INTERRUPTED|EXPIRED|REVOKED|INVALIDATED`，所有转换必须由 Promotion Controller 在独立 append-only `FundsAuthorizationStateLog` 中写状态事件，并绑定 authorization id、event id/time、前序状态 event digest、environment/account identity、原因和 active admission run id；任一终态不可再转出。该 log 是 control-plane 授权状态权威，不是记录现金/持仓/订单的交易 Ledger。live runtime 必须联合校验不可变 receipt、run-admission PromotionDecision 与该 log 最新权威事件中的 environment/account identity 完全相等；`BOUND_TO_THIS_RUN` 表示不得启动第二个 run，不表示已获准的当前 run 当场失权。它不是长期权限；当前运行完成、失败、中断、超时、到期或用户撤销后必须关闭 admission、转为不可复用，并立即阻止新的真实 submit。
  13. `sim-calibration` 专指 `sim-system` 规则与参数的受控离线校准角色，是 `sim_system_version` 与 `sim_calibration_artifact` 的唯一 writer。它只能消费经审查的真实平台/feedback-ingestion 证据、官方规则、用户冻结的项目规则假设和与当前 promotion holdout 独立的预注册 calibration split，输出包含 source evidence digest、规则/参数、适用市场/版本、代码/配置、验证结果和 sha256 的不可变 artifact，并 atomic publish 新版本；不得读取当前未暴露 holdout 的结果、训练模型、签发晋级 verdict 或改写正在被 training/offline-evaluation/paper 使用的版本。新版本只能供后续新轮次选择；publication 本身不得改写或自动失效仍绑定旧 identity 的 lineage，只有后续轮次采用新 identity，或权威新证据证明旧规则已不再适用时，才由 Promotion Controller 从 training 起追加受影响 receipt 的失效事件。

  ## 一、总体原则

  1. 重构必须先定义系统边界，再写实现。
  2. Polymarket 相关 submit、cancel、balance、approval allowance、user-channel、market-channel 等必须优先基于官方 Polymarket Rust SDK。
  3. 如果官方 SDK 能力不足，必须先列明具体缺口、影响和可选方案，经用户明确同意并限定缺口范围后，才能考虑 raw REST、manual signing、自建
  SDK 或其他旁路实现。
  4. 不允许出现第二套影子 feature pipeline、影子订单解释器、影子账本解释器或影子 SDK。
  5. 数据、model-train、offline-evaluation、paper、live 必须共享同一套市场时间线、订单事件语义和 artifact 合同；training、offline-evaluation、paper、live 的独立 `data-pipeline` runtime 必须调用同一处理核心，禁止 offline driver、online driver 或 Market Context Builder 形成第二套 feature、normalization 或 `ObservationContract` 实现。离线 labels/reward 的可见权限可以按角色收窄，但其 schema、provenance 与 maturity 语义必须一致。
  6. 交易决策、仓位/风控决策、暂停、不下单和撤销未成交 BUY 订单等策略性动作必须完全由模型输出或模型 bundle 明确声明的模型状态机输出；live-trade 不得内置第二套策略或风控来改写模型意图。
  7. 当前版本全系统的主动下单动作面固定为 `BUY-only`：模型、训练样本、offline-evaluation、`sim-system`、paper trade、Intent Bridge、execution adapter 和 live trade 只能创建 BUY 意图与 BUY 订单，不得创建、接受、模拟、发送或保留自有 SELL 动作的 deferred/research/feature-flag/占位路径。外部 orderbook 的 bid/ask、历史成交 side 和平台返回 side 仍可作为完整市场事实输入，不属于本系统主动动作。
  8. 需要表达对 `outcome_up` 的反向方向时，系统通过 BUY `outcome_down` 实现；需要表达对 `outcome_down` 的反向方向时，通过 BUY `outcome_up` 实现。这只是方向暴露和持有至结算策略上的对侧替代，不是平台订单、现金流、库存或成本上的完全等价：互补 BUY 会继续占用资金并增加持仓与成本，但以此换取全系统动作、账本、模拟和执行链路的大幅简化。
  9. 模型决策必须由版本化 `decision_trigger_contract` 中明确、可审计且能在training、offline-evaluation、paper、live间因果重放的模型可见事件触发，不得由固定频率、固定周期、周期性 polling 或固定 decision tick 触发。模型可见事件包括外部市场数据事件、由`ObservationContract`明确准入并进入共享canonical event tape的source coverage/confirmed-gap evidence、NormalizedOrderEvent / ledger 状态变化、market preload/start/end 与 GTD 到期事件、submit response、user-channel、cancel response 或 settlement evidence 实际在客户端变为可见的事件，由上一轮模型或模型 bundle 调度输出因果安排的稀疏一次性 `DecisionWakeEvent`，以及只在cold start/restore后存在应求值scope且没有可恢复有效pending wake时按第4项产生一次的`DecisionBootstrapEvent`。collector source-local transport/subscription恢复状态与operator诊断不是模型trigger；daily manifest中的`collection_day_coverage`也只在已有模型可见事件、`DecisionBootstrapEvent`或`DecisionWakeEvent`求值时参与known/unknown mask计算，不自行创建trigger。没有逐事件typed evidence时不得由online runtime临时暴露具体transport原因、由offline从操作计数猜测或伪造。仅由时间推移产生的`source_information_age`/missingness mask变化也不会自行创造另一个trigger，只在上述求值时按当前逻辑时间重算。平台内部“撮合延迟结束”本身不是模型可见事件，不得在相应 evidence 到达前触发模型；本地 clock 持续推进本身也不会自动调用模型。每个有效模型可见事件都必须先更新该 market 的持续因果状态，再按冻结的合并与排序合同触发模型交易、风控和下一次调度评估；事件触发不等于只向模型输入当前孤立事件。
  第9项中的外部市场数据事件也包括独立data-collect事项已批准、由共享semantic canonicalizer从`binance_aggtrade_v6 record_kind=invalid_input`生成并经`ObservationContract`准入的版本化invalid source event；typed raw中的raw bytes、hash、parser诊断或审计detail不得直接进入模型。该event必须使用collector admission coordinate而非Parquet物理行序或单独receive timestamp进入canonical total order。
  10. live-trade 是模型与 Polymarket/外部平台之间的桥梁，只负责运行编排本实例 `data-pipeline` online-stream runtime / Market Context Builder 与 Model Runtime、BUY-only 模型请求校验与发送、把真实平台返回/成交/拒单/撤单证据送入 NOE/Ledger、记录派生状态，以及权限、协议、schema、钱包、路径等硬边界 fail closed；它不得另行实现 feature、normalization 或 `ObservationContract`，可以拒绝执行不满足硬边界的请求并把原因写入 audit/operator 记录，但不得生成替代交易决策。
  11. 本文中的“真实平台”专指 live trade 连接的 Polymarket/SDK/market channel/user channel/submit response/cancel response；“模拟平台”统一称为 `sim-system`，专指 training、offline-evaluation 和 paper trade 共同调用的订单提交后反馈模拟模块。`sim-system` 只能用真实平台 artifact 与版本化规则证据校准，不得在 live 高频热路径中作为账户、订单或风控状态源。
  12. 所有关键结论必须有 artifact、manifest、schema、日志或测试证据支撑，不能只靠 stdout 或人工判断；用户明确冻结的项目规则假设必须与官方公开事实分开标记 provenance、版本和适用边界。

  ### 训练采集的上游退化、持续运行与缺失数据合同

  本节关于进程连续性和模型学习缺失数据的要求适用于全部 training 外部源。用户已明确冻结“上游不稳定、服务端无数据或一个/多个源缺失不得耗尽预算并令 training collector 退出”；该目标需求取代当前独立 `data-collect` D2 的有限 generation 预算/整进程退出语义。业务静默或 stale 不再触发 subscription refresh、unsubscribe/subscribe、主动 generation 切换或主动断开仍存活的 socket；只有经正向分类的 transport 故障才由相应 source 的 transport owner 在同一 PID 内持续恢复。由于本核心需求整体仍在审核中，这一需求变化不表示当前代码已经修复，也不授权在对应独立 demand/plan/changelog 精确同步前实施。paper/live 只共享因果 availability/missingness/Observation 与决策调度语义，其连接恢复条件、执行权限和运行约束必须由各自需求另行冻结，不得从本节直接复制。

  1. 必须把上游 availability/missingness 事实与本地完整性故障分开。DNS/TCP/TLS/WebSocket 连接失败或断开、heartbeat 超时和 rate limit 是有直接证据的 source availability degradation；服务端无数据、业务消息静默、持续 stale、单个源不可用或全部外部源同时不可用是训练必须保留的正常上游可用性/数据不完整形态。有直接证据的transport/recovery状态形成collector可见的运行诊断，stale payload等typed source evidence按其自身合同保留；没有新业务消息本身不产生collector事件，只能在已知coverage内由last qualifying time与当前逻辑求值时间因果派生age/mask。transport/subscription诊断只有未来通过新的typed evidence与`ObservationContract`决策门并能跨runtime重放后，才可进入模型Observation或成为trigger。上述上游形态都不得仅因持续时间变长而升级为 gap verdict、告警、training run 失败或 collector 进程退出条件；没有 source cadence、sequence hole 或上游证据时，只能表达 observed silence/freshness lapse，不能虚构 confirmed missing messages。无法验证的 parser/schema payload、writer/manifest/atomic publish 失败、磁盘或资源硬边界、内部状态不变量破坏等不属于该豁免，仍按其受影响 scope quarantine 或 fail closed。

  6. `data-pipeline` 必须在每个模型求值时刻因果计算并编码：`source_information_age = decision_logical_time - last_qualifying_event_available_time`、保留值的 `value_age`、`fresh|stale|missing|invalid|unknown_not_observed` mask、已确认 gap 的独立证据，以及恢复后的首条 qualifying fresh 事件。mask分类及任何age边界属于版本化`ObservationContract`/pipeline配置，不属于`DecisionScheduleContract`；`missing`只表示known-observed coverage内按冻结规则缺少合格信息，不等于confirmed gap、具体缺失条数或transport原因，也不得控制subscription/reconnect。精确 age 只允许在 known-observed coverage 内产生；source 启动后尚无 qualifying value 时必须使用 `no_qualifying_value_yet + known_active_elapsed`，coverage 不明时不得伪造 last-fresh、missingness start 或缺失条数。`confirmed_gap_age`只适用于SDK `Lagged(n)`、bounded queue drop、Binance depth update-id hole等具有直接合同证据的确定性缺失，不能与普通业务静默或aggTrade `a`数值前跳混用。training 必须保留并因果重放known coverage内的真实 missingness，不得仅因上游无数据、网络不稳定或一个/多个源缺失而删除样本、停止训练或把数据集判为结构不完整；本地collector coverage无法证明的区间必须保留typed raw但隔离出要求四runtime parity的Observation replay，这不是把外部missingness样本删除。这里的“完整”指 artifact、schema、manifest、provenance、因果时间和缺失编码完整，不要求每个源在每个时刻都有行情。training 还可以通过预注册、版本化且有 provenance 的 scenario artifact 屏蔽相应源事件或注入中性 availability 事实，不得改写 collector typed raw、伪造市场价格，或把“这是注入场景”的事后标记泄漏给模型。
  7. 面对模型可见的数据源退化，暂停交易、`MODEL_NO_SUBMIT`、撤销未成交 BUY 订单以及 BUY 对侧 outcome 中和已有方向风险，都必须由模型或模型 bundle 状态机决定；collector、`data-pipeline`、live-trade 或 execution gate 不得替模型生成这些策略动作。这里的“风险中和 BUY”不是 SELL 或真实减仓：它继续占用 pUSD、增加 gross shares/成本，只能在模型基于当时可见 ledger/market 状态判定能降低既定方向风险时作为 BUY-only intent 输出，`sim-system`、NOE 与 Ledger 必须按真实双侧持仓和现金变化记账。

  ### 稀疏决策调度与离散 `next_wake` 目标候选

  1. 本轮模型框架竞赛批准把“模型或模型 bundle 状态机输出有界离散 `next_wake_bucket`”作为目标候选；这表示共享 runtime、simulator、Observation、输出、reward、artifact 和 parity 合同必须能够公平支持并验证该候选，不表示它已经成为 champion、active 模型或获准实施/部署。确定性单次 age-crossing 加 risk-bearing有限重武装的scheduler保留为同合同下的基线：每次真实事件或wake后都按预注册算法/config重新求下一deadline，单个crossing已经发生不能令仍有风险的scope永久失去wake；有限多级deadline可作为预注册对照；连续delay、hazard、Neural ODE/CDE event function仍是后续研究候选，未获当前实现授权。
  2. 共享模型输出必须把 `trading_risk_intent` 与 `decision_schedule_intent` 分成两个命名空间。目标候选的后者至少包含 `next_wake_bucket`、由runtime提供且模型只能回显的`decision_scope_id`，以及父`decision_id`；模型不得创建、改绑或任意选择scope。bucket集合、最小正间隔、最大允许间隔、量化/舍入、显式`NO_PENDING_WAKE`（若允许）和适用状态必须由版本化`decision_schedule_contract_version`冻结，不得复用旧网络恢复的`3s/6s`数值。`next_wake`不是BUY/SELL交易动作，不改变BUY-only action surface；无法识别的bucket编码、越界、在合同要求有限bucket的状态中缺失，或在不允许`NO_PENDING_WAKE`的状态选择该值，均属于当前runtime scope的合同失败：training使对应trial/candidate无效，offline-evaluation拒绝签发receipt，paper/live进入对应执行权限fail-closed；所有scope都必须审计，scheduler不得自动生成撤单、暂停或对侧BUY。
  3. `decision_scope_id`必须来自版本化、有限且由runtime唯一管理的scope registry；`decision_schedule_contract_version`必须冻结scope种类、创建/retire条件、模型可见事件到受影响scope的映射，以及单runtime active scopes和pending timers总上界。每个`(model_runtime_instance, decision_scope_id)`同时最多存在一个pending wake；scope retire时必须取消timer。模型可见业务、ledger、market lifecycle或经合同准入且可重放的source coverage/confirmed-gap事件在wake之前到达时，只抢占合同映射到的受影响scope：先更新持续状态、使旧timer generation失效并立即重新评估，新输出原子替换旧timer。collector-only transport/subscription诊断不抢占模型timer。`DecisionWakeEvent`到达时只提供一次新的模型决策机会，不直接执行策略动作。相同逻辑时间的真实/ledger/lifecycle/source-evidence事件与timer必须采用冻结的稳定排序并避免对同一scope/time重复求值；restart/checkpoint后不得重复、遗漏或复活已失效timer。
  4. 在active market、活动订单、pending submit/cancel、未结算持仓或其他冻结的risk-bearing状态存在时，调度输出必须选择有限bucket，不能选择`NO_PENDING_WAKE`或永久`WAIT_FOR_EVENT`；无风险且没有活动决策scope时是否允许显式`NO_PENDING_WAKE`由同一调度合同冻结。cold start完成因果状态bootstrap且存在active decision scope，或restore后处于risk-bearing状态但没有可恢复的有效pending wake时，runtime必须按版本化trigger合同产生恰好一次`DecisionBootstrapEvent`，使模型/基线生成首个schedule intent；若checkpoint已有有效pending wake则只恢复它，不再生成bootstrap，已过期pending wake按第7项只触发一次late wake。最小正间隔必须阻止近零延迟busy loop/Zeno，最大间隔只保证模型再次获得决策机会，不代表gap、告警、subscription refresh、reconnect或自动风险动作。禁止的是runtime脱离上轮schedule intent自行启动的外生固定周期；模型或预注册基线在连续决策中因果输出相同有限bucket本身不构成fixed tick，但每次都必须有独立parent decision和timer audit。
  5. 时间戳可以具有微秒或更高表示精度，但表示精度不产生同频率模型调用。training/offline-evaluation 使用确定性虚拟逻辑时钟，paper/live 使用 monotonic clock 调度并另记 UTC audit time；两者运行同一调度状态机。不得每微秒、每毫秒或按其他固定网格物化“时间 + 空市场 + 空 ledger”上下文、空 token、密集 no-op 样本或策略决策。每次稀疏触发都读取截至该 causal cutoff 的完整持续 market/ledger/source状态。
  6. `next_wake` 会改变下一次观察和决策机会，训练与 `sim-system` 必须按变量持续时间/SMDP语义处理：transition记录真实 elapsed `delta_t`，reward覆盖该区间内的 ledger、估值、风险与terminal事实；若使用折扣必须按冻结的 elapsed-time合同计算，不能对不同持续时间机械使用同一 per-event折扣。真实事件提前到达导致的 timer抢占必须记录为被抢占/删失的调度结果，不能伪称原bucket已完整执行。训练合同还必须使用可解释的实际推理成本、决策次数约束或等价资源目标，避免“更多免费观察”令候选恒选最短bucket；具体成本/约束必须预注册并进入公平竞赛合同，不得事后调节。
  7. `decision_schedule_contract_version`必须冻结bucket的`base_logical_time`来源、`effective_due_logical_time`计算、逻辑时间到online monotonic deadline的映射、推理完成时deadline已过期的处理，以及checkpoint字段与restore规则。checkpoint至少保存pending scope、base/due time、bucket、parent decision和timer generation；恢复时未过期timer继续等待，已过期timer只产生一次带lateness的`DecisionWakeEvent`，不得补发多个catch-up wake或启动周期循环。每次调度必须记录parent decision/trigger、decision scope、proposed/effective bucket、base/effective scheduled logical time、actual fire time、lateness、timer generation、创建/取消/替换/restore原因、抢占事件、model/bundle/config identity和最终trigger event id。offline-replay、offline-evaluation、paper、live必须使用同一timer创建、抢占、排序、恢复与审计schema，并通过同输入、同bundle、同初始状态下decision count/order、trigger和Observation parity；online调度延迟必须显式记录，不能被伪装成零延迟或回排到较早时间。

  ## 二、新系统流程要求

  系统必须支持完整 5 分钟 BTC up/down 市场生命周期，并显式区分 active market 与 prefetched next market。

  模型生命周期必须固定为：`model-train 完成并冻结 candidate -> offline-evaluation PASS -> paper trade PASS -> live shadow / NO_SUBMIT_PERMISSION PASS -> 用户逐级授权 small-live 1 个市场 -> small-live 3 个市场 -> formal live 1 小时`。任何模型、数据切分、评估器、paper/live runtime、ModelRegistry API 或人工操作都不得绕过前置阶段；每次真实资金运行仍受独立用户授权、资金授权档和 execution permission 共同约束。

  1. 自检阶段：
     - 启动时必须先冻结 `runtime_role=data_collect_training|data_collect_paper_hot|data_collect_live_hot|training|offline_evaluation|paper_trade|live_trade|promotion_controller|sim_calibration`、对应 binary identity 和本次实际依赖，再执行该角色自己的自检合同；三种 `data_collect_*` 角色不得与四个模型生命周期消费者/交易角色共用同一进程身份，training 与 offline_evaluation 也不得共用运行实例或 artifact writer 身份；Promotion Controller 与 sim-calibration 都可以是短生命周期 CLI/job，但必须使用各自独立 writer identity。
     - 共用检查只覆盖该角色实际依赖的数据源、市场发现、当前/下一个市场、token id、tick size、min size、fee/rebate、reward eligibility、schema、关键 writer、磁盘和资源。
     - `data_collect_training`检查四个外部源的配置与逐源恢复能力、typed raw writer、coverage/availability诊断、last-qualifying/missingness因果基础、manifest、磁盘和采集服务器CPU/RAM；外部源在自检时transport不可达只能令对应源进入有证据的degraded并持续恢复，transport存活但暂时无业务数据只形成idle/零行业务事实，两者都不得阻止collector启动。`data_collect_paper_hot`/`data_collect_live_hot`检查各自服务器上的四个外部源、realtime handoff frame/socket、heartbeat/status、source gap/reconnect/backpressure、binary/path identity和本机资源。三者都不得要求模型bundle、`sim-system`、NOE/ledger、wallet、funder、真实user channel或训练GPU。
     - `training` 检查分配给 train/development/calibration/validation 的 finalized dataset/manifest、`data-pipeline` offline-replay runtime、共享处理核心及冻结 normalization artifact、`sim-system`、NOE/ledger、训练 CPU/GPU/RAM 和训练 artifact writer；不得拥有 offline-evaluation 时间外留出集的读取权限，也不得要求真实 wallet、funder 或 live user channel。
     - `offline_evaluation` 检查不可变 candidate ModelBundle、时间外留出集及其 non-overlap/maturity/coverage manifest、独立 `data-pipeline` offline-replay runtime、共享处理核心及 bundle 内冻结 normalization artifact、`sim-system`、NOE/ledger、评估合同和 report/receipt writer；不得加载 optimizer、修改权重、重拟合 normalization、要求真实 wallet/funder 或写入 training/ModelRegistry artifact 根。
     - `paper_trade` 检查来自独立 `data-collect-paper-hot` 进程的 realtime handoff、`data-pipeline` online-stream runtime / Market Context Builder、共享处理核心及冻结 normalization artifact、模型 bundle/runtime、有效 `OfflineEvaluationReceipt`、`sim-system`、paper NOE/ledger 和 audit writer；不得要求真实 wallet/funder。
     - `live_trade` 检查来自独立 `data-collect-live-hot` 进程的 external-market realtime handoff、`data-pipeline` online-stream runtime / Market Context Builder、共享处理核心及冻结 normalization artifact、前序 qualification receipts、真实 user channel、官方 Rust SDK 能力、模型 bundle/runtime、live NOE/ledger、关键 append-only audit writer、部署路径和本机 CPU/RAM；不得绕过 handoff 再建第二条外部 market-data feed，也不得要求训练 GPU。live shadow 必须固定为 `NO_REAL_FUNDS + NO_SUBMIT_PERMISSION`，不得要求或加载可提交 wallet/funder；真实资金 run 才额外检查本 run 有效的 `UserFundsAuthorizationReceipt`、wallet/funder、对应 tier 和 submit/cancel/reconciliation 能力。
     - `promotion_controller` 检查唯一 writer 权限、ModelRegistry/current stage、append-only decision/receipt-state/`FundsAuthorizationStateLog` writer、receipt schema/digest、最新 consume/revoke/invalidation event、`active_admission_run_id` 和用户授权证据；不得加载训练 optimizer、模型推理、wallet secret 或交易 submit/cancel 能力，也不得替阶段 runtime 生成结果 receipt。
     - `sim_calibration` 检查唯一 calibration writer 权限、预注册 calibration split 与真实平台证据 provenance、当前 promotion holdout 不可达、版本/规则/参数/代码/配置 digest、验证与 atomic publish writer；不得加载模型 optimizer/wallet、读取当前晋级结果或就地改写任何运行中 simulator artifact。
     - 自检失败只能阻止对应组件或运行角色进入自身热路径；training-only、offline-evaluation-only、paper-only、live-only 或 data-collect-only 依赖不得互相阻断。共享合同本身不一致时，也必须分别记录每个受影响角色的 verdict 和 effect。

  2. 热身阶段：
     - 按 runtime role 验证热身合同：三种 `data_collect_*` binary 只验证各自外部 market source 与 writer/handoff；training 与 offline_evaluation 分别在隔离 replay runtime 验证 T-30/bootstrap、两个 outcome 的模拟 BUY submit/cancel/fill、`sim-system` response、NOE/ledger，其中 evaluator 仍只读 candidate；paper_trade 在在线输入下验证同一模拟闭环；live shadow 只验证 read-only/NO_SUBMIT 的 user channel、SDK query/reconciliation、NOE/ledger，只有持本 run 有效用户授权的 small/formal live 才能在授权范围内验证真实 BUY submit/cancel/fill。不得让 data-collect binary 承担订单热身，也不得把 SELL 路径作为当前版本热身项。
     - 所有角色都必须记录 `runtime_role`；只有 paper/live 角色记录 `funds_authorization_tier=NO_REAL_FUNDS|SMALL_LIVE_1_MARKET|SMALL_LIVE_3_MARKETS|FORMAL_LIVE_1H` 和 `execution_permission=ALLOW_SUBMIT|NO_SUBMIT_PERMISSION|CANCEL_ONLY_PERMISSION|PAUSED_PERMISSION`，data-collect、training、offline-evaluation、promotion_controller、sim_calibration 对后两字段必须写显式 null/N/A 及 not-applicable reason，不能伪造 paper/live 权限。paper 与 live shadow 的资金授权都固定为 `NO_REAL_FUNDS`，live shadow 的 execution permission 固定为 `NO_SUBMIT_PERMISSION`；它们不是模型策略态。任何一轴都不得与 `model_strategy_mode` 或 `gate_verdict` 混用。
     - `UserFundsAuthorizationReceipt` 本体必须与 `FundsAuthorizationStateLog` 最新权威事件联合验证：run admission 前最新状态必须为有效 `UNCONSUMED`、未撤销且未过期，admission 后必须为只绑定本 run 的 `BOUND_TO_THIS_RUN`；同一 `(environment, wallet, funder, account_global_ledger_id)` 或同一 promotion chain 不得存在另一个 outstanding live admission。不满足时不得用真实下单冒充热身通过。任何真实资金 run 只能使用 receipt 声明的 tier、market/count/duration，结束后必须追加终态事件并关闭 admission。
     - small-live 与正式 live 均使用 `./wallets/.env.wallet1`；本地源路径为 `/home/chillchill/btc-updown-marketmaker/wallets/.env.wallet1`，`./wallets` 作为 gitignored 钱包 secret/env 部署材料上传或复制到交易服务器，远端实际落点必须由部署 receipt 记录且不得通过 Git 同步；需求层不限制资金规模；每次执行前必须单独向用户
     申请授权，获得批准后才能执行。
     - small-live 分为 1 个完整 5 分钟市场和 3 个完整 5 分钟市场；正式 live 为连续 1 小时程序运行。
     - 热身结果必须写入 artifact，不得只看控制台输出。

  3. T-30 秒预加载阶段：
     - 对任一目标 market `M`，必须在 `M.start - 30s` 前完成发现并开始外部市场源采集；`next` 只是相对角色，不是 lifecycle state。
     - `data-collect` 负责 T-30 source subscription、market metadata、orderbook/depth、tick/min size、token id、raw evidence、coverage、health/gap 和 manifest；模型所需 feature context 与 runtime market context 由本角色独立 `data-pipeline` runtime 调用共享处理核心生成，paper/live 的 Market Context Builder 是其 online-stream driver；资源预算和模型 bundle 由 Model Runtime 承接。
     - market `M` 在 `M.start - 30s` 到 `M.start` 之间只能进入 `prefetched` context，`M.start` 后才允许 `prefetched -> active`；prefetched context 不能污染当前 active market 的订单、持仓、open order 或账本。

  4. Active market 持续决策阶段：
     - 当前活跃市场中，模型必须在每个决策点看到所有必要数据源当时可证明的 `fresh|stale|missing|invalid|unknown_not_observed` 状态、`source_information_age` 与 `value_age`；源不可用、source从未启动或coverage未知时不得用伪造、保留值或未来数据补成“全部可用”，也不得把业务静默冒充confirmed gap。
     - 每个有效模型可见业务/ledger/lifecycle事件、经合同准入且可重放的source coverage/confirmed-gap事件、一次性`DecisionBootstrapEvent`或`DecisionWakeEvent`到达并完成时间排序、去重、market隔离、timer generation、NOE/ledger projection与causal availability判定后，必须更新该market的持续状态并按调度合同触发一次模型交易、风控与下一次调度评估；collector-only transport/subscription诊断不得成为online-only trigger，没有新的模型可见事件时也不得由固定频率调度器凭空生成策略决策。
     - 模型输入必须包括 price to beat、orderbook/depth、Binance/外部价格、逐源 availability mask、`source_information_age`、`value_age`、known/unknown coverage、独立的 confirmed-gap evidence、本地 ledger 派生的 pUSD CASH、position、目标 market 内完整的 `open_order_list`、`pending_submit_list`、pending cancels、active resting count、账户级 NAV 字段、订单生命周期状态、最近 submit/cancel/fill/partial-fill 反馈，以及 cancel requested、cancel ack、cancel rejected、cancel retry、cancel timeout、matched-cancel、overlapped terminal 等 cancel order 生命周期反馈。具体 transport/subscription 原因默认只是运行诊断，不进入共享 Observation；未来若要成为模型输入，必须先通过新的可回放typed evidence与ObservationContract决策门。
     - `open_order_list` 中每笔 BUY order 至少包含 order reference、market/outcome/token、GTC/GTD order type、`limit_price_pusd_per_share`、accepted original shares、客户端当前已见 cumulative fill/remaining shares、`open_order_reserved_pusd`、created/accepted time、当前可见 execution/lifecycle state 和 pending-cancel state。FOK/FAK 不得产生 resting open remainder。该列表只能反映当时客户端已经可见的 NOE/ledger projection，不得泄露 `sim-system` 的平台真实状态或尚未到达的 fill。
     - `pending_submit_list` 只容纳 `UnknownSubmitOutcome` 等尚未获得 accepted/rejected 权威证据的本地 BUY intent，必须显式保留其 order type、对应的 limit 或 market BUY 输入字段及 `pending_submit_reserved_pusd`，标记 provisional，不能计入 open order 或 active resting count。只有官方 SDK 合同能够安全生成并验证 expected platform order hash，或 cancel-all/cancel-by-market 等 SDK scope 不需要伪造 order id 时，该 provisional entry 才能提供合法 cancel target/scope；否则模型只能等待可关联证据，不能构造 platform order id。
     - 模型必须能在完整 5 分钟市场窗口内基于持续因果状态做交易决策，而不是只看到 250ms 的孤立片段；“完整窗口”不表示按时间戳精度物化每个微秒/毫秒，也不要求把无事件时刻作为空记录或token输入模型。
     - live-trade 不得基于自身规则改变模型输出的 outcome/token、price、quantity basis、submit、cancel、`MODEL_PAUSE`、`MODEL_NO_SUBMIT` 或风控动作；`order_action=BUY` 是当前版本系统常量，任何非 BUY 请求都必须在 action-surface preflight 中拒绝并进入 audit，不得被改写成另一笔交易。平台返回的执行结果进入本地事件和 audit，硬边界拒绝原因只进入 audit/operator 记录，不作为模型输入或模型反馈。
     - 系统必须估算并记录模型运行需要多少显存、内存、CPU、线程和 batch/sequence 配置。

  5. 当前市场结束前 T-30 秒：
     - 必须开始预加载下一个市场的全部模型输入。
     - 模型对当前市场 open order 发出的单笔或全部取消、平台对遗留订单产生的到期/市场关闭终态、成交确认、持仓结算、ledger close、artifact close 与下个市场 preload 必须并行但隔离；旧 market 的 reserve、matched-pending 和结算变化仍须更新唯一的 account-global 投影。
     - 任何 market switch 都不能让上一个市场的订单事件污染下一个市场。

  ## 三、模型输入与训练窗口要求

  1. 模型训练、offline-evaluation、paper trade、live trade 都必须维护目标 market 从 `start - 30s` 到 market end 的持续可见上下文，并在稀疏模型可见触发点读取截至当前 causal cutoff 的状态；这 30 秒是目标 market 的 pre-start prefetched context，不得把上一个 market 的订单、持仓或 lifecycle 明细混入目标 market-local 投影。由旧 market 未结算订单或持仓产生的 account-global pUSD CASH、reserve、matched-pending exposure 和 NAV 影响不属于污染，必须通过带同一 ledger sequence 的只读 account-global snapshot 对目标 market 可见。
  2. 模型输入不得截断为孤立的 250ms 数据片段，必须保留第 1 条规定的完整持续状态与可见历史边界；不得把完整上下文误写成固定时间网格、密集空样本或需要模型逐token记忆所有无事件时刻。
  3. 每个训练样本、offline-evaluation 决策、paper 决策、live 决策都必须带有 causal cutoff，确保模型只能看到当时真实可见的信息。
  4. 训练样本、offline-evaluation、paper 和 live 决策必须与权威模型可见事件触发点对齐；该触发点可以是实际变为可见的业务/ledger/lifecycle事件、经`ObservationContract`准入且进入共享canonical tape的source coverage/confirmed-gap事件、一次性`DecisionBootstrapEvent`，也可以是由上一轮调度输出安排的`DecisionWakeEvent`。每次决策至少记录trigger_event_id、trigger_event_type、event_available_time、decision_ts、causal_cutoff_ts、decision scope与适用的timer generation/parent decision。collector-only诊断、固定间隔重采样或`tick_stream`可以作为运行审计、派生特征、统计、兼容分析或回放索引，但不得成为模型决策触发器，也不得生成没有权威trigger对应的策略决策样本。
  5. 模型输入至少应包含：
     - market_id、两个 outcome 的 token_id、外部市场 book/trade side、time-to-expiry、active/prefetched 标记；
     - 所有数据源的时间对齐状态、known/unknown coverage、`source_information_age`、`value_age`、fresh/stale/missing/invalid/unknown_not_observed mask及独立confirmed-gap evidence；
     - orderbook、depth、spread、price to beat、tick size、min size；
     - `account_global_projection` 中的 `cash_balance_pusd`、`pending_submit_reserved_pusd`、`open_order_reserved_pusd`、`cancel_reconciliation_reserved_pusd`、`total_reserved_pusd`、`available_cash_pusd`、matched-pending settlement exposure、账户级 NAV 和 ledger sequence；以及 `market_local_projection(market_id)` 中两个 outcome 的 provisional/confirmed position、目标 market 内完整 open BUY order list、pending submit list、pending cancels 和 active resting count；各 market reserve 切片之和必须与 account-global 总额闭合，不能形成第二份可花现金；
     - submit/cancel/fill/partial-fill；
     - 不得包含独立 account_state；如需账户状态，只能使用本地 ledger 派生字段；
  6. training、offline-evaluation、paper、live 的模型输入必须由同一版本化 `data-pipeline` 确定性处理核心生成，并使用同一 `ObservationContract`、feature schema、处理配置、冻结 normalization artifact、pipeline state schema，以及统一的 cold start、T-30 warm-up/bootstrap、reset、checkpoint restore、reconnect、gap/backfill 合同。允许字段在某些环境下为空，但不能为空缺语义；不同环境的实际市场值或 ledger 值可以不同，但给定相同 source evidence、causal cutoff、内容及 sequence/digest 相同的本实例只读 ledger projection、initial state/checkpoint 和上述版本化 artifact，输出的非浮点/规范字段必须精确相同，浮点模型 tensor 必须满足冻结数值容差。`canonical_observation_hash` 必须基于版本化 canonicalization 与浮点量化规则计算，不得要求容差内但原始字节不同的浮点值直接产生相同原始字节 hash。
  7. 模型输出必须分为可审计的 `trading_risk_intent` 与 `decision_schedule_intent`。前者保持 BUY-only，例如 `submit_buy`、`cancel_order(order_ref)`、`cancel_all_open_orders(scope)`、`model_strategy_mode=MODEL_NO_SUBMIT|MODEL_CANCEL_ONLY|MODEL_PAUSE`、目标 outcome/token、`order_type=FOK/FAK/GTC/GTD`、GTD expiration 和 post-only；GTC/GTD limit BUY 必须输出 `limit_price_pusd_per_share + size_shares`，FOK/FAK market BUY 必须输出 `spend_pusd + worst_price_pusd_per_share`。`order_action=BUY` 是当前交易合同常量；quantity basis 由 order type 决定，不得再把四种 order type 统一成同一份额数量输入。`MODEL_CANCEL_ONLY` 只限制模型不再 submit，实际撤单仍须由明确的 `cancel_order` 或 `cancel_all_open_orders` intent 产生。后者按本需求的调度合同输出离散 `next_wake_bucket` 或基线bundle的等价确定性调度结果；它只有唯一scheduler consumer，不进入Intent Bridge或交易平台。live-trade只把前者交给Intent Bridge并回传execution feedback，Model Runtime scheduler只消费后者且不得生成替代交易动作。
  8. 每个训练样本、offline-evaluation 决策、paper 决策、live 决策必须在 audit metadata 或 run manifest 中记录 pipeline_core_identity、runtime_binary_sha256、pipeline_config_digest、pipeline_state_schema_version、initial_state_digest、checkpoint_digest、state_provenance、observation_schema_version、feature_schema_version、normalization_artifact_sha256、online_rule_version、model_version、causal_input_digest、ledger_projection_sequence、ledger_projection_digest、canonical_observation_hash、feature_hash、decision_trigger_contract_version、decision_schedule_contract_version及适用的timer trace identity；不适用的 initial/checkpoint/timer 字段必须为空并带明确语义。审计 metadata 中额外记录的 orderbook 摘要只能作为 audit hash，不是额外模型特征，但这不禁止模型消费 feature schema 已声明、按 causal cutoff 生成的 orderbook/depth 特征。
  9. 模型只能读取 `data-pipeline` 输出的模型可见 `ObservationContract` 及其中来自本实例的只读 ledger projection，不得直接调用、写入或绕过 NOE/Ledger。模型不得直接以未归一化的真实平台或 `sim-system` 订单返回作为权威订单状态、execution-feedback label 或策略输入；raw response 只能作为 raw evidence、digest/reference、审计材料或受控调试材料保留。模型可以学习由 `NormalizedOrderEvent`、ledger 和 causal projection 派生出的订单生命周期状态、submit/cancel/fill 执行反馈、cancel pending/retry/ack/terminal 状态、延迟分布、fill hazard、风险状态和策略响应；market supervision label、execution-feedback label、reward、未来 outcome 和 label maturity 字段不得进入 paper/live 依赖路径或任何模型可见 Observation。
  10. 外部市场数据中的 bid/ask、maker/taker 或 BUY/SELL side 必须与本系统自有 `BUY-only` action surface 命名空间隔离；保留完整外部市场事实不代表系统具有自有 SELL 能力。

  ### 当前版本交易动作与盈利机制

  1. 当前版本只允许 BUY 两个 outcome，并只允许以下两种盈利机制；训练目标、`sim-system`、paper 报告、live 审计和模型评估不得引入第三种隐含交易机制。
  2. **互补 outcome 折价配对。** 只有同一已确认配对数量 `paired_qty = min(confirmed_outcome_up_qty, confirmed_outcome_down_qty)` 对应的 `outcome_up` 与 `outcome_down` 单位 all-in acquisition cost 之和小于 `1 pUSD` 时，才能把该部分记为配对机制，并以完整互补持仓的 `1 pUSD` 结算价值与实际总成本之间的差额获利。是否满足 `< 1` 必须按真实或 `sim-system` 的 confirmed fill、实际 fee 和已入账 rebate 计算；未配对数量、partial fill、未成交第二腿和相关资本占用必须另记为 incomplete/directional exposure 与风险，不能计入已闭合配对收益。静态盘口、中间价或下单意图不得冒充已实现配对收益。
  3. **结果趋明后的正确侧持有。** 当市场结果随因果可见信息逐渐明朗时，模型可以增加 BUY 其当时判断为正确的 outcome，并持有至最终结算获利。训练和评估只能使用决策时已可见信息，不得用最终结果倒灌决定“正确侧”；该机制必须完整计入判断错误、成交成本、资金占用、未成交和最终结算风险。
  4. 卖出 `outcome_up` 所表达的反向方向由 BUY `outcome_down` 表达，反之亦然；这是当前 BUY-only 策略对方向暴露的实现约束，不得把互补 BUY 记成 SELL、减仓、释放资金或提前实现收益。
  5. fee、已入账 rebate、现金占用和结算差异是上述两种盈利机制的经济或会计组成，不得被描述为独立第三种盈利策略。reward 只是由版本化 RewardContract 从已入账、可回放的 ledger 状态以及同一因果边界内的 valuation/terminal evidence 派生的训练目标/诊断信号，不是现金流、收入、offline promotion verdict 或第三种盈利机制。两种机制可以在同一账户轨迹中并存；归因必须分别报告并显式保留无法唯一拆分的 interaction/residual，全部归因合计必须与账户级 ledger、NAV 和 settled PnL 闭合。


  ## 四、数据采集与数据消费要求

  1. 数据采集和数据消费必须解耦，但共享同一套 schema、manifest 和时间线语义；本文中的“数据采集与处理”是 umbrella，不等于单一 `./data-collect/` 模块。
  2. `data-collect` 必须支持 T-30 秒外部源预订阅和预加载，不得只在市场开始后才启动；当前四源合同为 Polymarket market channel、Binance BTCUSDT depth、Binance BTCUSDT aggTrade、Polymarket RTDS Chainlink BTC/USD。模型可见 input/features 只能由 `data-pipeline` 共享处理核心生成；Market Context Builder 只是 paper/live 的 online-stream driver 与运行编排层。market supervision labels、execution-feedback labels、tick_stream、train/development/calibration/validation split、replay context 和 offline-evaluation 时间外留出集属于 `data-pipeline` offline-only 数据构建分支；model-train 只能消费训练 manifest 分片，offline-evaluation 只能消费互斥的留出 market data 与外生 outcome/resolution/settlement 评分证据，当前 candidate 的 execution feedback 必须由本次评估闭环生成，reward signal 仍只属于训练模块的 RewardContract。上述离线专属信号和产物不得进入 paper/live 模型输入路径，留出集的 labels/maturity 也不得进入 offline-evaluation 的模型可见 Observation。
  3. 市场发现不能只依赖 slug，必须保留 market_id、condition_id、token_id、start/end、market lifecycle state、runtime current/next role 和真实平台原始响应。
  4. `new_market`、market switch、prefetch、active transition 等事件不能丢失。
  5. 原始数据必须保留 raw_json 或等价原始证据。
  6. Parquet 可以作为 typed raw mirror，但不能成为唯一事实来源；paper/live 必须保留 append-only event log 或等价可回放事件流，且该 event log 不由 `data-collect` 生成或解释，只能由对应 online-stream runtime 按共享处理核心的输入合同消费。
  7. 数据处理模块必须覆盖历史采集数据处理，不能绕过已采集的三四个月历史数据直接重做新链路；这里的数据处理指 `data-pipeline / data-processing`，不是 `data-collect`。
  8. 必须先制定全盘数据处理计划，再加入旧数据处理；旧数据处理结果应作为设计新的“数据采集 -> 数据处理”工作流的基础。

gate。顶层继续为`data_collect_daily_manifest_v3`；legacy v3缺coverage定义为unknown且不得回填，新writer必须写合法`data_collect_collection_day_coverage_v1`，非法对象按manifest完整性fail proof。
  11. 数据采集与处理必须作为 training、offline-evaluation、paper trade、live trade 的共用合同：`data-collect` 提供外部市场源 typed raw / coverage / manifest 或 realtime handoff；training、offline-evaluation、paper、live 分别运行隔离的 offline-replay 或 online-stream runtime，但都必须调用唯一的版本化 `data-pipeline` 确定性处理核心生成模型可见 features 与 `ObservationContract`，并运行同一版本化decision scheduler。driver 只负责 I/O、framing、无损 transport decoding 和本实例运行编排；从 decoded source evidence 到 canonical event 的字段、单位、枚举、timestamp/causal-availability 映射必须由共享 semantic canonicalizer 完成。offline-only label builder、feedback-ingestion、训练切分、校准数据池和评估留出集不得进入 paper/live 依赖路径，model-train 不得读取评估留出分片。四个 runtime 只共享代码、schema、配置、normalization artifact、状态合同、时间线、causal cutoff、feature/input contract、事件触发、调度和可回放语义，不共享进程、队列、checkpoint、状态缓存、运行根或 ledger；collector-only transport/subscription诊断和`tick_stream`等固定间隔派生产物不得决定模型决策频率，也不得替代权威业务/ledger/lifecycle/经准入source-evidence/`DecisionBootstrapEvent`/`DecisionWakeEvent` trigger。
  12. 时间戳必须命名空间隔离：`source_ts` 是外部源时间；训练 typed raw 中的`timestamp_received`表达采集进程接收时间，并与collector host/region元数据共同确定provenance；paper/live handoff中对应字段为`collector_recv_time_utc_ms`，进入paper/live runtime后必须另记该运行主机的`runtime_receive_time_utc_ms`；`decision_ts`/`causal_cutoff_ts`是模型可见边界，`scheduled_wake_logical_time`与`actual_wake_time/lateness`属于独立调度命名空间。共享处理核心必须按版本化且跨runtime一致的total-order key、同毫秒tie-break、duplicate、late、gap/backfill、timer generation和causal-availability合同处理模型可见证据；不得按较早`source_ts`或计划wake time回排迟到事件、改写已经产生的Observation，或让finalized replay静默用未来backfill修补先前模型输入。confirmed gap、业务missingness、backfill和调度timer只有在对应因果证据进入共享canonical tape时才作为模型事实可回放；真实reconnect及其原因若只存在于source-local operator诊断或既有daily reconnect counter，只能用于运行解释，不得成为模型trigger或从计数伪造精确原因/episode。任何跨schema映射必须显式记录source field、target field、host、region和clock evidence status，不得把上述时间戳互相覆盖。live/paper实测延迟标签只能来自对应运行主机artifact，不能用采集主机接收时间冒充。下文冻结的爱尔兰双向延迟profile是`sim-system`的项目代理假设，不是真实live/paper出站延迟标签。
  13. training、offline-evaluation 与 paper 无论实际运行在哪台机器，通过 `sim-system` 模拟的订单请求和平台反馈都必须使用同一版本化爱尔兰延迟 profile；各运行机当时的本地 RPC 延迟不得替代该 profile。订单/取消请求的 client-to-platform leg、平台反馈的 platform-to-client leg 和平台内部 accepted/matched/response-emission 时间必须分别记录，不得把一个延迟样本同时记作两段、RTT 或撮合延迟。历史训练或评估行情已经以 `timestamp_received` 表达采集端可见时间时，不得再次叠加同一入站延迟。

  ## 五、订单微结构与毫秒级竞态要求

  订单微结构必须作为 P0 需求，不能只写成实现细节。

  1. 单笔与批量 submit response envelope：
     - 按当前官方 [Post a new order](https://docs.polymarket.com/api-reference/trade/post-a-new-order) 和 [Post multiple orders](https://docs.polymarket.com/api-reference/trade/post-multiple-orders)，`POST /order` 接收一笔并返回一个 response object；`POST /orders` 接收最多 `15` 笔的 array，批内订单并行处理，一次 HTTP response 返回一个 response array。单笔或批量形式由 Intent Bridge 实际调用的官方 SDK submit 路径决定，不是平台随机选择的结果。
     - [pinned 官方 Rust SDK](https://github.com/Polymarket/rs-clob-client-v2/blob/3ae1aae5e9ded38f984464c9fc0f307f8a9f41fb/src/clob/client.rs#L1839-L1885) 的 `post_order` 返回一个 `PostOrderResponse`，`post_orders` 返回 `Vec<PostOrderResponse>`；批量 HTTP body 完整接收并解析后才作为一个 envelope 对客户端可见，不得把同一 batch 的 item 模拟成多次独立 HTTP response 到达。多次独立 single submit 各自拥有独立 envelope 与 transport leg，可以乱序、迟到或缺失；批内每笔订单的平台处理、订单状态和 user-channel 事件仍各自独立，可以先于或后于整个 batch response envelope 可见。
     - SDK/HTTP transport 成功不等于订单 accepted，batch envelope 成功也不等于每个 item 成功。按官方 [CLOB error codes](https://docs.polymarket.com/resources/error-codes)，HTTP 200 的同一 response array 可以同时包含 live、matched 和逐项失败；request-level transport/non-2xx/解析失败与 HTTP 200 内的 per-item 结果必须分开建模，batch 不得按原子全成或全败处理。
     - 本项目真实资金 artifact 已记录[单笔 submit 产生一个 Post observation](/home/chillchill/sdk-live-trade/poly-arb-ai/rust/sdk-live-trade/artifacts/live-validation/pullback/platform-sellable-maturity-live-20260626T133250Z/platform_sellable_maturity_buy_submit_attempts.stream.jsonl:1)，也记录[一个 4-item batch 共享同一 batch id、raw response hash 和 actor completion/timestamp record，其中 1 笔 accepted、3 笔 rejected](/home/chillchill/sdk-live-trade/poly-arb-ai/rust/sdk-live-trade/artifacts/remote-r5-runs/r5-three-market-live-funds-20260621T131804Z/trading-runtime/orders.jsonl:70)。这些 artifact 未保留完整 HTTP wire body，只证明当时 SDK/Intent Bridge 实际观察到的返回形式和 mixed outcome 分支，不用于冻结频率或响应数组顺序保证。
     - 对由 create-order/submit response 推导的 accepted 路径，single object 或 batch item 只有同时满足非空 platform order id、状态非 UNKNOWN、无拒单/错误文本、scope/decision_id/local intent 可安全对应、数量可解释，才允许该 response 进入 accepted hot path；不得只看 `success` 字段。
     - 官方文档只声明批量请求中每笔订单有一个 response，未明确公开承诺 response array 与 request array 的索引顺序保持不变。正常路径只能在版本化的本项目 batch 关联合同下按 slot 对应 request item 与 response item：必须同时校验 request/response count、保留有序 signed request、batch/envelope id、request/response index、local intent id、signed-order digest/预计 order hash、raw request/response digest 和 envelope receive time，且不存在其他 mapping anomaly。该 slot 对应是项目关联假设，不是平台公开顺序保证，也不能单独作为 accepted 或 platform order identity 证明；关联合同无法满足时，对应 item 必须保持 `UnknownSubmitOutcome` 并等待 user-channel 或 reconciliation evidence，不得猜测映射。[SDK issue #30 的生产报告](https://github.com/Polymarket/rs-clob-client-v2/issues/30) 只作为“同批一项空 order id/status、另一项 matched”的社区异常场景证据，不是平台官方保证或发生率证据。
     - 能够安全关联到具体 request item 的明确 per-item rejection/error evidence 必须只把该 item 归为 rejected，不得污染 sibling item；明确且可验证为撮合前整体拒绝的 request-level validation error 才可把对应已发送项归为 rejected。blank order id + UNKNOWN/empty status 且无决定性 error、count mismatch、无法关联的 response item，以及整个 response envelope 超时、丢失、截断或解析失败，都不得当作 accepted 或 rejected；已发送项必须进入 `UnknownSubmitOutcome` 或等价 provisional 状态，不能盲目重提、不能伪造 platform order id。mixed decision timestamp 或超出当前 SDK/platform batch limit 必须在创建 reserve 和发送前由 batch preflight 明确拒绝。
     - 未通过 response accepted classifier 的订单不得仅凭该 response 进入 open order 权威状态或应用 fill ledger delta。已安全确认 rejected 的 item 按拒单合同释放 pending-submit reserve；仍为 `UnknownSubmitOutcome` 的已发送项继续占用 pending-submit reserve，直到能够与 local intent / client id / platform order id 安全关联的权威 user-channel order/fill/reconciliation evidence 将其解析为 accepted、rejected、partial-fill、filled 或 terminal，并仍须经过 NormalizedOrderEvent 与 ledger。

  2. 订单类型、流动性角色与费用：
     - BUY-only submit 必须明确选择 `FOK`、`FAK`、`GTC` 或 `GTD`。按 [Polymarket Orders Overview](https://docs.polymarket.com/trading/orders/overview)，`FOK/FAK` 是立即吃取对侧 resting liquidity 的 market-order types；FOK 只在模型给定的 worst-price/slippage bound 内能够全部成交时成交，否则整单零成交并取消，FAK 只成交该 bound 内当前可得数量并取消未成交余量。`GTC/GTD` 是带价格边界的 limit-order types，GTC 持续有效直至成交或取消，GTD 还可由平台在指定时间到期。
     - 订单金额域统一使用 Polymarket CLOB V2 的 `pUSD`，价格单位统一为 `pUSD/share`，份额数量使用 `shares`；依据当前官方 [pUSD 说明](https://docs.polymarket.com/concepts/pusd)，不得在业务 schema、模型 intent、ledger 或报告中继续使用含义不清的裸 `USD`、`USDC` 或以 quote/base 暗示资金单位的字段。pUSD 使用 6 位小数，但具体整数编码、舍入和最小单位必须委托 pinned 官方 Rust SDK，并由 parity 测试冻结，需求层不得另写手工换算旁路。
     - GTC/GTD limit BUY 的业务输入必须是 `limit_price_pusd_per_share + size_shares`，其最大本金占用 `max_principal_pusd = limit_price_pusd_per_share * size_shares`；价格改善后的实际成交金额只能来自权威 fill evidence，不能把最大本金冒充实际花费。marketable GTC/GTD 仍是限价单，不得因为立即成交就改写成市价单。
     - FOK/FAK market BUY 的业务输入必须是 `spend_pusd + worst_price_pusd_per_share`：模型决定愿意花费的 pUSD 金额和最差成交价保护，Intent Bridge 必须把这两项交给 pinned 官方 Rust SDK market-order builder，由 SDK 生成 signed maker/taker amounts 与隐含 shares，不得在领域层手工复刻编码、截断或舍入；实际成交份额、成交金额和未花费金额只由平台或 `sim-system` 权威 evidence 确定。虽然 pinned SDK 的兼容 API 符号仍可能写作 `Amount::usdc(spend_pusd)`，CLOB V2 中该值的业务语义必须记录为 pUSD，且该兼容符号只能存在于 SDK adapter 内；不得向模型或领域合同暴露 `Amount::shares` 作为 market BUY 的另一套数量口径。
     - Intent Bridge 对两类订单都必须记录订单类型、模型原始输入、SDK 编码输入、requested/accepted shares、signed maker/taker amounts、最大本金或 spend、fee、精度转换及 raw digest。队列与份额守恒统一使用 shares；pUSD 现金守恒独立计算，二者不得相加或共用同一 `size` 字段。
     - maker/taker 是每一段实际成交的流动性角色，不是订单类型的永久标签。订单入簿后被其他订单成交的数量为 maker；立即消耗 resting liquidity 的数量为 taker。marketable 的 GTC/GTD 不改变其 order type，立即成交部分按 taker 处理，未成交余量再按 GTC/GTD lifecycle 继续开放或到期；同一订单因此可以先产生 taker fill、再产生 maker fill。
     - post-only 只允许与 GTC/GTD 组合；会立即跨价成交时必须拒单，与 FOK/FAK 组合也必须拒单。只有通过 post-only accepted 并实际 resting 的订单才可在提交时保证不成为 taker。
     - fee、rebate 和 cost 必须使用撮合时该 market 生效的 fee metadata 与实际 maker/taker role 计算。按当前 [Polymarket Fees](https://docs.polymarket.com/trading/fees)，maker 平台费率为零，只有启用 fee 的市场才对 taker 成交收费；不得仅凭 order type 推导固定手续费，也不得把尚未入账的 maker rebate 当作该 fill 的即时负手续费。
     - 平台对 marketable order 返回的 delayed/unmatched 等状态及相应不可取消窗口必须按当前 market metadata、官方规则版本和真实 artifact 模拟；它们属于平台订单生命周期，不是程序自行生成的撤单决策。

  3. venue dust 与平台订单终态：
     - `sim-system`、NOE 和 ledger 必须分别记录 platform order status、order lifecycle state、actual cumulative executed base quantity、trade settlement state 和客户端可见状态。[真实资金 artifact](/home/chillchill/sdk-live-trade/poly-arb-ai/rust/sdk-live-trade/artifacts/live-validation/pullback/platform-sellable-maturity-live-20260626T133250Z/platform_sellable_maturity_samples.jsonl:18) 已证明：原始 `5` shares 的 BUY order 可以在 `size_matched=4.999165` 时由官方 SDK 查询为 `MATCHED`，cancel 返回 exact matched-cancel，且该 asset 的 open-order count 为 `0`；因此平台订单可以已经 terminal，而 `executed_base_qty` 仍小于 `accepted_base_qty`。该 sample 因 fill size 低于 probe 配置而标记 `valid=false`，只能证明此平台生命周期分支存在，不能用于估计发生频率或冻结统一 threshold。
     - `venue_dust_closed_base_qty` 只能在 platform status/terminal cause、精度或舍入证据、actual executed quantity、open-order 状态和版本化 artifact 共同支持 venue dust 时使用。FAK kill、模型 cancel、GTD expiry、平台市场关闭和 submit rejection 必须分别进入 canceled、expired、market-closed 或 rejected 语义，不能归入 dust。官方 [Get single order](https://docs.polymarket.com/api-reference/trade/get-single-order-by-id) 将 status、original size 与 size matched 分开返回，当前官方资料没有发布全局统一 dust threshold；成熟社区 [NautilusTrader Polymarket adapter](https://github.com/nautechsystems/nautilus_trader/blob/develop/docs/integrations/polymarket.md) 也把 rounding tolerance 明确作为 adapter normalization policy。dust tolerance 必须按协议版本、order type、数量/价格精度和本项目真实 artifact 校准并版本化，不得写成 Global 官方常量。
     - 权威 match/fill evidence 到达客户端时，ledger 必须按 actual executed quantity 一次性减少 `cash_balance_pusd`、等额消耗该订单当时所在的 pending-submit/open-order/cancel-reconciliation reserve、增加 provisional shares/cost basis，并把该 fill 标记为 matched-pending settlement exposure；matched-pending 只表达结算风险，不再从 `available_cash_pusd` 重复扣减。`CONFIRMED` 只把 provisional position 成熟为 confirmed，不重复应用现金或份额；`RETRYING` 保持 pending；`FAILED` 必须按权威失败证据精确冲回该 provisional cash/share/fee delta。venue dust terminal 本身不生成额外 fill、share 或交易现金流，只按 terminal cause 释放经权威数量确认的未花费 reserve。
     - venue dust 必须作为常规、可重复验收的订单生命周期分支，覆盖平台 `MATCHED` 但 `executed_base_qty < accepted_base_qty`、exact matched-cancel、late user-channel、重复 evidence、结算成功/失败和 reserve 释放；同一经济变化只能 ledger apply 一次。

  4. 模型撤单与毫秒级竞态：
     - 策略性撤单只能来自模型输出的 `cancel_order(order_ref)` 或 `cancel_all_open_orders(scope)`。程序不得按订单提交后的固定经过时长、market switch 或固定清理规则自行生成撤单决策；FOK/FAK 的 kill、GTD 到期、平台市场关闭和用户/操作员触发的紧急 cancel-all 是独立的订单或运行安全生命周期，其中 operator cancel 不得冒充模型策略或训练标签。
     - 时间合同必须为 `decision_ts`、`model_cancel_intent_ts`、`cancel_enqueue_ts`、`cancel_send_ts`、`cancel_exchange_arrival_ts`、`platform_match_ts`、`platform_cancel_effective_ts`、`cancel_response_emit_ts` / `cancel_response_receive_ts`、`user_channel_event_emit_ts` / `user_channel_event_receive_ts` 和 `reconciliation_ts` 提供独立 schema slot。每个非空时间戳必须同时记录 `timestamp_authority=local_measured|platform_reported|simulated`、`clock_domain`、`host_id`、`region`、来源字段/通道以及 clock-sync evidence status；模拟时间还必须记录 profile/scenario/seed。live 只有在官方 SDK/channel raw evidence 明确提供时才能写 platform-reported 的平台内部时间，不可观测 slot 必须为 null 并记录 unavailable reason，不能用客户端 send/receive time 倒推。不得把不同主机、平台真实顺序与客户端接收顺序合并成一个“取消时间”。
     - submit 与 cancel request leg 独立采样且按平台 arrival time 排序；cancel 可能先于原 submit 到达平台。此时平台返回的 not-found/unresolved 不能追溯取消随后才 accepted 的订单，原 submit 仍可进入 accepted/resting/matched lifecycle；模型在新证据可见后才能决定是否再次取消，程序不得复用旧 cancel intent 自动关闭该订单。
     - 模型只依据当时客户端可见的 `open_order_list` 与具有合法 cancel target/scope 的 `pending_submit_list` 决策。若一笔 accepted original size 为 `5 shares` 的订单已有 `3 shares` 在平台成交、但 fill evidence 尚未到达客户端，则模型仍会针对本地显示 remaining size 为 `5 shares` 的整笔订单发出 cancel intent；官方 cancel 路径按 order ID/scope 操作，并不由模型提交一个已知平台 remainder 数量。cancel 到达平台时，`sim-system` 必须只取消平台真实未成交的 `2 shares`。普通 cancel response 若只确认 order ID 已取消而没有返回 effective canceled quantity，则客户端必须进入 `cancel_effect_qty_pending_reconciliation`：先移出 open order，并把尚无法分解的 `open_order_reserved_pusd` 原额转入 `cancel_reconciliation_reserved_pusd`，既不能向模型泄露平台真实的 `2 shares`，也不能按本地可见的 `5 shares` 释放 reserve。迟到的 `3 shares` fill 或其他权威 cumulative evidence 到达后，才确定 `executed=3、canceled=2、open=0`，应用 fill、消耗对应 reserve 并准确释放未花费 reserve。
     - 若 cancel 到达前平台已经把全部数量 matched，必须返回 matched-cancel；若平台已经以 venue dust 关闭订单，则返回相应 terminal/matched-cancel evidence 并保留真实 executed quantity 与 dust quantity。cancel response 不得反向制造 fill。
     - 订单终态必须按平台因果顺序、单调 cumulative fill 和实际 cancel effect 共同仲裁，不得按客户端最先收到的 terminal message 简化裁决。先收到 cancel ack 后仍可接收并应用平台更早发生、但客户端更晚看到的 fill delta；重复或已覆盖 evidence 只能 alias/audit，不得重复入账、重复释放 reserve 或重新打开订单。

  5. cancel response 语义：
     - generic not-found、not_canceled、absent target 不能直接当作成交证明。
     - 本项目真实资金 artifact 中出现的精确 `matched orders can't be canceled` 是经 artifact 校准的“平台已无可取消 remainder”证据语义，不得扩写为 Global 官方公开保证。它可以关闭 cancel lifecycle，但经济成交数量只能来自先前或随后到达的权威 platform cumulative fill/trade evidence；若 cumulative quantity 仍不完整，对应 reserve 必须转入 `cancel_reconciliation_reserved_pusd` 并保持不可用，直至 fill/dust/reconciliation evidence 完成数量分解，不能由错误字符串单独制造成交或释放资金。
     - plain not-found 应作为 order-local retryable warning 或 unresolved evidence，等待其他权威来源关闭。
     - cancel 网络入口必须收敛到官方 SDK 的 single-order、multi-order 或 cancel-all 路径，不允许不同入口各自解释 terminal/fill/cancel。
     - 模型可见的 cancel order 生命周期状态必须覆盖 cancel requested/enqueued/pending、cancel accepted/ack、cancel rejected、retryable warning、retry scheduled、retry budget exhausted、transport/timeout、matched-cancel、overlapped terminal 和 final terminal；transport retry 只能幂等重试同一个模型 cancel intent，不得生成新的策略性撤单。这些状态只能由 NormalizedOrderEvent 与 ledger/projection 派生，不得由 live-trade 生成替代撤单策略。

  6. NormalizedOrderEvent：
     - 所有 SDK submit、`post_order` response object、`post_orders` response envelope/item、cancel、cancel batch、user-channel、fill/partial-fill、transport/observation timeout、平台到期/市场关闭/结算证据、operator emergency cancel 和 reconciliation evidence 都必须先进入 NormalizedOrderEvent 或等价权威事件层。不得用未定义来源、未携带 authority/provenance 的本地伪造关闭事件直接关闭订单或修改 ledger。
     - single/batch 归一化前必须保留平台原始 envelope 形状、raw digest 和 receive time。batch 内每个 item 分别生成可仲裁的 NormalizedOrderEvent，但必须共享同一 response_envelope_id/digest/receive time 并保留 request/response index 与关联证据；不得把归一化后的多个 item 伪装成多次平台 HTTP 返回。
     - NormalizedOrderEvent 是订单反馈归一化事实层，也是 ledger、模型可见投影和审计的共同输入；execution-feedback label 只能由本来源实例达到 maturity 的 NormalizedOrderEvent 与 ledger apply 结果共同构建，不能在 ledger apply/maturity 前由 NOE 直接生成。NormalizedOrderEvent 不是 live-trade 生成新策略或风控决策的入口。
     - NormalizedOrderEvent 的业务归一化必须由程序化、版本化、可回放、可测试的合同完成；不得把 accepted classifier、terminal arbitration、matched-cancel/dust/late evidence 归一化、ledger_apply_policy 或 validator 事实一致性检查完全交给模型训练自行学习。
     - `sim-system` raw evidence 必须通过同一套归一化合同后分别进入 training、offline-evaluation 或 paper 各自隔离的 NOE/ledger/audit/replay；达到 label maturity 的 NOE 与 ledger apply 结果才可以进入 offline-only execution-feedback label builder。真实平台 raw evidence 必须通过该合同后进入 live NOE/ledger/audit，并且只能经 `feedback-ingestion` 离线复制到 offline-only execution-feedback label builder 和 `sim-system` 校准链路。`sim-system` 证据不得进入 live ledger、live audit 或 live 状态，live runtime 也不得调用 `sim-system`。不同运行模式不能拥有各自的影子订单解释器。
     - validator 只能验证 normalized rows、raw digest、reference integrity 和 artifact consistency，不能成为第二套业务解释器。

  ## 六、账户、订单与热路径 ledger 权威

  1. training replay、offline-evaluation replay、paper、live 每个运行实例都必须拥有彼此隔离的本地 append-only ledger；共享的是版本化 schema、NOE 和 apply policy，不是状态实例。该实例的 ledger 是其账户、两个 outcome 持仓、BUY 挂单、pUSD 现金、NAV 和 active resting 状态唯一热路径权威。订单生命周期 evidence 必须严格路由为 `sim-system raw evidence -> training/offline-evaluation/paper NOE` 或 `真实平台 raw evidence -> live NOE`；除此之外，ledger 只能消费本实例的 local provisional intent 和第 2 条定义的版本化非订单经济/控制事件。`data-pipeline` 只能读取本实例带 sequence/digest 的 ledger projection，模型只能读取由处理核心纳入 `ObservationContract` 的只读投影；二者都不得写 ledger。任何实例都不得直接消费另一实例的 ledger 或 raw evidence。
  2. ledger 的全部经济变化必须来自带 authority、幂等 key、causal time 和 provenance 的版本化事件：启动 bootstrap、外部充值/提现、submit/cancel/fill/partial-fill NOE、fee/rebate、settlement/redemption 以及明确的 reconciliation event。market channel/orderbook 可以提供估值、market lifecycle 或 resolution evidence，但不能自行创造账户订单、成交、持仓或现金变化；raw snapshot 也不得直接覆盖 projection。
  3. 账户资金字段必须统一为 `cash_balance_pusd`、`pending_submit_reserved_pusd`、`open_order_reserved_pusd`、`cancel_reconciliation_reserved_pusd`、`total_reserved_pusd = pending_submit_reserved_pusd + open_order_reserved_pusd + cancel_reconciliation_reserved_pusd` 和 `available_cash_pusd = cash_balance_pusd - total_reserved_pusd`；本文模型输入中的 CASH 专指决策时刻由本地 ledger 派生的 `available_cash_pusd`。模型 BUY intent 只有通过 action-surface、订单参数、资金和协议 preflight，并在进入 submit queue 前，才依据 limit BUY 的 `max_principal_pusd` 或 market BUY 的 `spend_pusd`、当前 fee metadata 与 pinned SDK fee 语义计算并创建 `pending_submit_reserved_pusd`；reserve artifact 必须明确 fee 是否已包含，禁止重复加 fee。accepted 后转入 open-order reserve，immediate fill 则直接消耗对应 reserve；明确且可安全关联的 rejection/确定未接受释放一次，`UnknownSubmitOutcome` 持续保留。无 effective quantity 的 cancel ack 把 reserve 转入 cancel-reconciliation bucket，待权威累计成交证据完成分解。权威 fill 入账时同时减少 `cash_balance_pusd` 与对应 reserve；matched-pending settlement exposure 另记且不得从 available cash 重复扣减。取消、到期或 venue dust terminal 只释放经权威数量确认的未花费 reserve。
  4. 本地 preflight 拒绝发生在 submit queue 与 pending-submit reserve 创建之前，不产生平台订单、pending-submit item 或持久 reserve。已经发送到平台的 item 只有在 rejection evidence 能安全关联到该 item 时，才以 `accepted_base_qty=0` 关闭 submit lifecycle 并释放其 pending-submit reserve 一次；无法安全关联或 transport outcome 不确定时必须保持 `UnknownSubmitOutcome` 和 reserve，不得因“看起来像拒单”提前释放。
  5. 模型输入、artifact 和报表不得使用 wallet allowance 表达任何 pUSD cash 字段；Polymarket/SDK balance/allowance/approval 只能作为启动 bootstrap、权限/协议 preflight 或显式 reconciliation evidence，不是热路径第二账本，也不是 pUSD CASH、NAV 或 PnL 的替代来源。
  6. live 启动 baseline 必须由同一 causal cutoff 下可核验且完整的 SDK/account evidence 建立，至少覆盖 pUSD balance、所有相关 outcome positions、open/pending orders、未成熟成交/结算和外部资金流游标；证据不完整时不得宣称 baseline 完成或据此计算累计 PnL。启动后的充值与提现必须分别进入版本化 `external_fund_flow` ledger event，定义 `external_net_flow_pusd = deposits_pusd - withdrawals_pusd`。
  7. PnL 不是独立账本权威状态；未带限定词时，`cumulative_pnl_pusd = current_nav_pusd - startup_baseline_nav_pusd - external_net_flow_pusd`，表示程序启动后跨市场累计 PnL。只有 baseline 已证明仅含 pUSD CASH、无历史持仓/挂单/未成熟结算且期间无外部资金流时，才可简化为 `current_nav_pusd - startup_cash_pusd`。per-order/per-market PnL 只能作为可闭合的审计切片，不能替代累计 PnL。
  8. NAV 必须按版本化 `nav_valuation_contract=conservative_bid_depth_v1` 在决策时刻从同一 ledger projection 计算：`cash_balance_pusd` 只计一次，reserve 只是现金可用性分桶，不得再次从 NAV 扣除；provisional/confirmed positions 按 ledger 数量只计一次并显式标记 settlement maturity。市场权威 resolution evidence 可见后，按可赎回价值估值；此前按 causal cutoff 下新鲜、无 gap 的可成交 bid depth 做保守 liquidation valuation，深度不足的剩余份额估值为 `0 pUSD` 并记录 `unpriced_qty`。必要 orderbook 缺失、过期或 gap 未闭合时，NAV/PnL 必须标记 unavailable，不得用 midpoint、last price 或未来盘口补值。每个 NAV 必须可由 ledger sequence、valuation time、book digest、freshness 和 depth coverage 重放。
  9. 真实平台 balance/position/open-orders/trades 查询只允许用于启动 bootstrap、通道 gap/重连恢复、明确的 operator reconciliation 或定期审计，不得作为模型决策的 polling trigger，也不得直接生成、覆盖或否定热路径 ledger。查询结果必须先保留 raw evidence，再通过版本化 reconciliation/NOE 产生 ledger delta；订单未出现在一次 open-orders snapshot 中本身不是 fill 或 terminal 证明。
  10. 当前 action surface 不存在 SELL；任何自有非 BUY submit 都是模型 bundle、intent schema 或执行桥合同违规，必须在平台提交前拒绝并写入 audit，不得作为可重试交易、训练动作或 `sim-system` 候选。
  11. credential、scope、schema、wallet/funder、关键 append-only audit writer、模型 bundle 合同属于真实下单硬边界；这些边界缺失、不匹配或不可验证时，live-trade 必须将 `execution_permission` 设为 `NO_SUBMIT_PERMISSION` 或更严格权限，并记录原因。late user-channel、generic not-found 等证据应按具体 scope 进入 warning/quarantine/reconciliation，不得一律 hard fail，也不得由此生成非 BUY 动作或第二套订单解释路径。
  12. ledger 必须可回放、可重建，并能从回放结果复算 pUSD CASH、NAV 和累计 PnL；run manifest 必须记录 bootstrap evidence/digest、外部资金流游标、ledger/valuation contract version 和数据范围。ledger 派生状态可以作为模型输入与审计证据；硬边界只能设置 `execution_permission=ALLOW_SUBMIT|NO_SUBMIT_PERMISSION|CANCEL_ONLY_PERMISSION|PAUSED_PERMISSION`，不得作为模型输入/反馈，也不得把模型 intent 改写成策略性不下单、撤单或另一笔下单动作。

  ## 七、训练、offline-evaluation、paper trade 与 live trade 的真实交易反馈

  1. `sim-system` 是训练模块、offline-evaluation 与 paper trade 共同调用的订单执行反馈模拟模块。三类业务产生 BUY-only 模拟订单后，必须提交给各自隔离的 `sim-system` 实例；`sim-system` 模拟订单到达平台后的 accepted/rejected、排队、成交、部分成交、不成交、取消竞态、延迟和结算反馈，再输出模拟 raw evidence。三者不得各自实现另一套 simulator 或 fill 解释器。
  2. `sim-system` 的受控离线校准流程必须由唯一 `sim-calibration` writer 以真实平台回流的订单生命周期、成交/撤单/拒单反馈、ledger 结果和由 NAV 派生、可回放的程序启动后跨市场累计 PnL 反推并冻结版本，证据至少来自 sdk-live-trade、online-feedback、当前官方规则、用户冻结的项目规则假设、issues 和真实交易 artifact。training、offline-evaluation 和 paper 只能加载并验证已经冻结的同一 `sim-system` 版本及校准证据，不能在各自 run 中修改参数或用本轮训练/评估/paper 结果现场校准；新校准只能 atomic publish 为供后续新轮次选择的新版本，publication 不改写旧 lineage，只有采用新 identity 或旧规则被权威证据判定不再适用时才触发相应 receipt 失效。
  3. 离线目标与信号必须分为三个不可混用的命名空间：`market supervision labels` 由 offline-only label builder 从 finalized typed raw 与权威 resolution/outcome evidence 生成，必须记录 causal cutoff、label maturity 和 provenance；`execution-feedback labels` 必须来自 `sim-system` raw evidence 经本来源 training/offline-evaluation/paper NOE 归一化、由本实例 ledger apply 并达到 maturity 后的结果，或来自真实平台证据经 live NOE/live ledger apply 达到 maturity、再由 `feedback-ingestion` 离线复制并审查后的训练反馈；`reward signals` 必须由训练模块唯一的版本化 RewardContract 根据 model trading/schedule action、decision_id、本训练实例 ledger_before_sequence、ledger_after_sequence、可回放 ledger delta、真实 elapsed `delta_t`、valuation/terminal evidence digest 和 reward_maturity_ts 派生，并记录 reward_contract_version 与 reward_config_digest，必须可重算且不得修改 ledger。对离散 `next_wake` 候选，RewardContract还必须区分timer完整到期与被真实事件抢占/删失，使用冻结的elapsed-time折扣语义，并绑定预注册的实际推理成本、决策次数约束或等价资源目标；不得把固定per-event折扣或事后调整的wake惩罚混入公平比较。训练可以按 frozen split manifest 消费前两类 labels；offline-evaluation 在运行前只能把未进入模型 Observation 的权威 outcome/resolution/settlement evidence 作为独立评分面，当前 candidate 的成交、取消、持仓、PnL 和执行结果必须由本次评估自身的 `sim-system raw evidence -> NOE -> Ledger` 产生，禁止用历史行为策略的 execution-feedback labels 代替或推断当前 candidate 的结果。reward 不得进入 offline-evaluation/paper/live 模型输入或晋级 verdict。execution-feedback labels 不得直接读取真实平台 raw response，也不得手写冷路径状态标签。每条订单 execution-feedback label 至少记录 source_kind、transition、normalization_reason、ledger_apply_policy、cancel_outcome、error_category、order_id/local_intent_id、source_ts/receive_ts、order_type、limit_price_pusd_per_share、size_shares、spend_pusd、worst_price_pusd_per_share、max_principal_pusd、requested_base_qty、accepted_base_qty、client_visible_cumulative_executed_base_qty、client_visible_remaining_base_qty、platform_cumulative_executed_base_qty、cancel_effect_base_qty/state、venue_dust_closed_base_qty、canceled_base_qty、expired_base_qty、market_closed_base_qty、open_base_qty、ledger_delta_fill_base_qty、actual_execution_notional_pusd、fee_pusd、execution_class、lifecycle_state、terminal_reason 和 trade settlement state；不适用于该 order type 的另一套输入字段必须为空并带明确 not-applicable 语义。平台真实数量只能留在 `sim-system` truth/audit 与成熟标签中，不能在相应 evidence 到达前泄露给模型。market switch、ledger open-order state、user-channel freshness 只能作为上下文或审计元数据，不得替代订单结果标签。
  4. 每笔模拟 BUY order 必须先由 `sim-system` 按 exchange arrival、engine acceptance 和撮合顺序生成独立于客户端可见性的模拟平台真实状态，再分别生成 create-order/submit response 与 user-channel order/trade evidence 的 emission time、receive time、迟到或缺失/截尾结果。`sim-system` 必须保留 Intent Bridge 选择的 `single|batch` submit mode：single 生成一个 response object，batch 生成一个含逐项 mixed outcome 的 response array envelope，整个 envelope 只有一组 emit/receive/缺失结果；批内每笔订单的平台处理和 user-channel 事件仍独立调度。accepted resting order 的平台侧成交时间、完整成交或部分成交必须先于相应可见证据确定；这些时间必须能导致 full fill、partial fill、cancel complete、matched-cancel、late fill、venue dust close 等生命周期结果，而不是只按理想成交价记账或把本地尚未收到回报误写成平台尚未 accepted/matched。
  5. **FIFO 项目规则假设。** 本项目按用户在 `2026-07-12` 明确确认并冻结的项目规则假设，视目标 Polymarket Global 与 Polymarket US 在订单排序上都采用价格优先、同价按进入撮合系统的时间先后执行的 FIFO/price-time priority。`sim-system` 必须模拟该规则。该结论是用户冻结的项目规则假设，不得写成 Global 官方公开事实；[Polymarket US `2026-07-02` Rulebook §5.4](https://polymarketexchange.com/files/legal/Polymarket%20US%20Rulebook%20%282026.07.02%29.pdf) 与 [US FIX Order Entry](https://docs.polymarket.us/institutional/fix-api/fix-order-entry-overview) 只构成 US 官方证据。规则假设的 authority、版本、访问日和适用 market 必须进入 online_rule_version、run manifest 与 `sim-system` artifact，并在 paper/live 前重新核验。
  6. **Global 队列可见性边界。** 截至 `2026-07-12`，本轮核验的 [Global Orders](https://docs.polymarket.com/trading/orders/overview)、[Global Orderbook](https://docs.polymarket.com/trading/orderbook) 公开接口及官方 Rust SDK `main` commit `3ae1aae5e9ded38f984464c9fc0f307f8a9f41fb` 不提供 open order 的 queue_position、rank、quantity_ahead 或其他真实全局队列位置字段；聚合 L2 也不能唯一分解同价档内的新增、取消和成交。因此 `sim-system` 不得声称恢复我方订单的真实 FIFO 名次。该边界只针对 Global 当前公开接口；Polymarket US institutional FIX 的 MBO 能力是独立证据面，不能冒充 Global 可见性。
  7. **FIFO 同价队尾入队。** 对不会立即成交、被撮合引擎接受为 resting 的 BUY order，`sim-system` 必须在 engine acceptance time 把它追加到该价格档所有更早被引擎接受且尚未消耗的同价数量之后，初始 `quantity_ahead_at_acceptance` 等于这些前方数量之和，不得把我方订单随机插入任何更早位置。例如撮合引擎接受我方订单时该档已有 `100 size`，我方新增 `5 size`，则初始前方量为 `100`，我方数量对应累计数量区间 `(100, 105]`；这表示数量位置，不表示五笔独立订单排名。marketable BUY 必须走相应 taker/marketable lifecycle，包括适用的撮合延迟、FOK/FAK 行为或 GTC/GTD 未成交余量处理，不能套用 resting queue。
  8. **队列不确定性边界。** 本地看到的 L2 price-level size 只是 engine acceptance 前的聚合证据，不必然等于撮合引擎接受我方订单时的真实前方量。`sim-system` 必须按因果顺序处理 snapshot、client send、exchange arrival/acceptance 之间可见的同价新增、成交和取消：在我方之前被接受的同价新增量进入前方量，接受前已成交或已取消的数量不再排在前方。随机或情景假设只能用于无法从公开 L2 唯一识别的并发到达、网络/撮合延迟、gap/reconnect，以及我方入队后同价档取消发生在前方还是后方等归因；不得改变 FIFO 队尾入队规则，也不得把已知更早数量随机移到我方之后。
  9. 队列状态必须影响 time-to-first-fill、actual executed shares、quantity ahead、取消竞态和未成交结果，并输出 engine-acceptance 时间、证据边界、assumption/scenario id 及不确定性标签。marketable/taker leg 必须先在 price/worst-price bound 内按对侧价格优先、同价 FIFO 消耗唯一且不可重复使用的 eligible liquidity budget；只有随后被接受为 resting 的 GTC/GTD residual leg 才建立我方 `quantity_ahead`，并按第 7、8 条 FIFO 消耗前方量。每笔 engine-accepted order 的 shares 必须始终满足：`accepted_base_qty = executed_base_qty + venue_dust_closed_base_qty + canceled_base_qty + expired_base_qty + market_closed_base_qty + open_base_qty`，上述 `*_base_qty` 字段的单位均明确为 shares，各项不得为负且同一数量只能归入一个 bucket；submit rejection 的 `accepted_base_qty=0`，不进入平台订单数量守恒域、队列或 open-order reserve。若 item 已经发送，其 pending-submit reserve 仍必须按第六节第 4 条由安全关联的 rejection evidence 释放一次；本地 preflight rejection 则从未创建 reserve。`spend_pusd`、`max_principal_pusd`、actual execution notional、fee、open reserve 与 released reserve 必须在独立 pUSD 现金守恒中闭合，不能与 shares 相加。
  10. execution 与 lifecycle 必须分轴记录：`execution_class` 至少区分 no-fill、partial、full，`lifecycle_state/terminal_reason` 至少区分 open、fully-matched、canceled、expired、market-closed 和 venue-dust-terminal。FAK 可以是 partial+canceled，GTC/GTD 可以是 partial+open、partial+canceled 或 partial+expired，数值上 partial 的订单也可以因 venue dust 成为 terminal；FOK 则必须在 price bound 内 full，或零成交结束。模型 cancel、order type、平台到期、市场关闭和 venue dust 必须按各自 terminal cause 分桶。
  11. matched-cancel 必须由 `sim-system` 的平台状态机与事件时间线生成。模型只能基于当时已经可见的 create-order/submit response、user-channel、NOE、ledger、`open_order_list` 和具有合法 target/scope 的 `pending_submit_list` 决定取消；cancel intent 经过 client-to-platform 延迟到达模拟平台后，再按该时刻的平台真实 order status、open base quantity 和 terminal cause 判定。平台因 fully-matched 或 venue-dust-terminal 而无可取消 open remainder 时，`sim-system` 必须生成与真实资金 artifact 一致的 exact `matched orders can't be canceled` 模拟 raw evidence；FAK kill、GTD expiry、先前 cancel 或其他 terminal cause 必须生成各自对应的 canceled/expired/not-found evidence。generic `order can't be found - already canceled or matched` 不得替代 exact matched 证据。cancel response 只能描述平台实际 cancel effect，不能制造成交或覆盖随后到达的既有 fill。live trade 不使用 `sim-system`，真实平台 matched-cancel 只能来自 SDK cancel response 或 user-channel/SDK 可验证证据。

  3. active 模型才能真实下单；shadow 模型只能产出对照决策和评估 artifact。
  4. 训练批次排名表必须与 ModelRegistry 对齐：训练内选出的产物只能先冻结为 candidate，不得直接进入 shadow、paper 或 live。candidate 只有依次通过模型 bundle/训练完整性 gate、独立 `OfflineEvaluationGate`、paper qualification，才可进入 live shadow / `NO_SUBMIT_PERMISSION` 验证；shadow 通过后，还必须由 Promotion Controller 校验完整 receipt chain，并在用户明确授权首次 `SMALL_LIVE_1_MARKET` 时才允许转为 active。active 只是可提交模型状态，不自动产生真实资金授权；后续 `SMALL_LIVE_3_MARKETS` 与 `FORMAL_LIVE_1H` 仍须逐级验证和逐次用户授权。
  5. 当前模型框架的不同神经网络层级、模型容量和训练参数候选必须共享同一 BUY-only 动作合同、两种盈利机制、数据、`sim-system`、NOE、ledger、reward 和评估边界后再比较；不符合当前 BUY-only action contract 的候选不得进入当前 leaderboard 或训练批次排名表。
  6. 上线前必须做 action-surface audit，确认模型只能输出 BUY 两个 outcome、取消未成交 BUY、`MODEL_NO_SUBMIT`、`MODEL_PAUSE` 和允许的风控意图，并与实际 SDK/order/venue 硬约束一致；任何自有 SELL schema、head、candidate、consumer 或执行路径都必须判定失败。
  7. 模型 bundle 必须定义交易动作与风控动作输出合同；live-trade 只能验证 BUY-only action surface 是否满足平台、SDK、权限、schema 和钱包硬约束，不能改写模型的交易或风控 intent。
  8. 模型 bundle 与训练报告必须分别声明并报告“互补 outcome all-in cost < 1”和“结果趋明后增加正确侧并持有至结算”两种盈利机制的适用条件、风险、分别归因及 interaction/residual；不得用未结算方向收益或不完整配对冒充已实现利润，全部归因必须与总 ledger economics 对账。
  9. `promotion_stage` 必须与 ModelRegistry、`funds_authorization_tier`、`execution_permission` 分轴记录，至少覆盖 `TRAINED_CANDIDATE -> OFFLINE_EVALUATION_PASSED -> PAPER_PASSED -> LIVE_SHADOW_PASSED -> SMALL_LIVE_1_PASSED -> SMALL_LIVE_3_PASSED -> FORMAL_LIVE_1H_PASSED`。每次转换必须由 Promotion Controller 消费前序 PASS receipt 并输出不可变 `PromotionDecision`；禁止跨级、倒序、缺证据推进，禁止把这些阶段名称加入 active/shadow/candidate/retired 枚举。
  10. 全部阶段 receipt 与 `PromotionDecision` 必须区分跨阶段不变量和阶段本地证据。跨阶段必须保持同一 candidate bundle sha256、pipeline core/config/state、Observation/normalization、BUY-only Intent、NOE/Ledger 合同身份以及可适用的 online rule provenance；TrainingCandidateReceipt、OfflineEvaluationReceipt 与 PaperQualificationReceipt 还必须绑定同一冻结 `sim_system_version + sim_calibration_artifact_sha256`，live receipt 只能绑定真实平台/官方 SDK/runtime 证据并引用该训练 lineage，不得写成 live 使用 `sim-system`。首次 small-live 1 admission 建立的 environment、公开 wallet/funder/address 和稳定 `account_global_ledger_id` 必须在 small-live 1、small-live 3、formal-live 1h 全链保持相同；账户 identity 变化必须失效全部真实资金 receipt、关闭 admission 并回到 `LIVE_SHADOW_PASSED` 重新从 small-live 1 授权，environment/live runtime/hardware identity 变化还必须失效 `LiveShadowReceipt`、回到 `PAPER_PASSED` 重做 live shadow。每个 receipt 本体都必须不可变，至少记录 receipt/schema id、stage、issuer/runtime binary sha256、issued/expiry time、verdict、evidence/run-manifest digest 和前序 receipt digest；consume/revoke/expire/invalidate 只能通过 Promotion Controller 的 append-only 状态事件引用 receipt id 与前序状态 digest，不能原地改 receipt。runtime binary、host、hardware identity、initial/checkpoint 和 run id 是各阶段本地证据，不要求跨 training/offline/paper/live 相同，但必须证明对应目标阶段的 parity 和资源 gate。模型权重/bundle、normalization、pipeline/Observation/action、`sim_system_version`/calibration artifact、关键 NOE/Ledger/evaluation contract 或适用平台规则变化时，必须按受影响范围使既有 receipt 失效并从 training 起最早受影响阶段重新验证；评估器、runtime 或人工操作不得自行豁免。
  11. 各阶段 receipt 的签发者和最低完成条件必须固定：model-train 在训练有效性检查完成、唯一 candidate 冻结且未读取留出集后签发绑定 training split/data manifest、训练报告/排名、`sim_system_version` 与 calibration artifact digest 的 `TrainingCandidateReceipt`；offline-evaluation 在最新未见留出集闭环得到 PASS 后签发绑定 `OfflineEvaluationDatasetManifest`、evaluation report、初始 Ledger/checkpoint/cash/position/reserve/open-order state 和 scenario/seed set 的 `OfflineEvaluationReceipt`；paper runtime 在 `NO_REAL_FUNDS` 下完成预注册运行与对账后签发 `PaperQualificationReceipt`；live shadow runtime 在最终 live 硬件上以 `NO_REAL_FUNDS + NO_SUBMIT_PERMISSION` 完成只读数据、推理、SDK query/reconciliation、重启和长运行验证后签发 `LiveShadowReceipt`。small-live 1、small-live 3、formal-live 1h 只有在各自一次性用户授权范围内完整结束、账本/订单/结算/资源证据闭合，且 Promotion Controller 已追加 `COMPLETED` 授权终态事件并关闭 admission 后，runtime 才能依次签发 PASS `SmallLive1Receipt`、`SmallLive3Receipt`、`FormalLive1HReceipt`；每份真实资金结果 receipt 必须绑定 authorization id、run-admission decision digest、environment、公开 wallet/funder/address、稳定 `account_global_ledger_id`、`admission_start_ledger_sequence/digest`、`completion_end_ledger_sequence/digest` 和 terminal `FundsAuthorizationStateLog` event digest。阶段 runtime 只能签发本阶段结果 receipt，只有 Promotion Controller 可以验证 receipt 与终态事件并在 completion decision 中同时绑定二者、推进 stage。
  12. offline-evaluation、paper、shadow 或任一 small/formal-live 发生 FAIL、QUARANTINE、证据不完整、超时、中断或授权撤销时，不得签发 PASS receipt、不得推进 stage，并必须保留原因和最后一个已通过阶段；Promotion Controller 必须为真实资金 authorization 追加对应 FAILED/INTERRUPTED/EXPIRED/REVOKED/INVALIDATED 终态事件并关闭 `active_admission_run_id`，runtime 必须停止新 submit，并按本 run 已验证的权限路径完成必要 reconciliation 或模型/operator cancel。不得原地修改不可变 receipt。上述结果不得把训练 run 改写为失败，也不得自动把模型设为 retired；ModelRegistry 回退或 retired 必须是独立、可审计的 PromotionDecision。paper/live 反馈不得自动更新当前 bundle 权重，任何基于反馈的重训都必须产生新 model_version，并重新执行适用的未见数据与晋级链。
  13. live runtime 只有在以下条件同时成立时才能令 `execution_permission=ALLOW_SUBMIT`：`model_registry_state=active`；当前 `promotion_stage` 与申请的资金档顺序匹配；存在 Promotion Controller 针对同一 bundle/run/tier/market/count/duration/environment/account identity 签发的 run-admission `PromotionDecision`；不可变 `UserFundsAuthorizationReceipt`、该 decision、`FundsAuthorizationStateLog` 最新权威事件和 live preflight 实际读取的公开 wallet/funder/address、`account_global_ledger_id`、environment 完全相等，admission 前状态为 `UNCONSUMED`、随后为本 run 唯一有效的 `BOUND_TO_THIS_RUN`，未撤销/未过期且 `active_admission_run_id` 等于当前 run；同一 `(environment, wallet, funder, account_global_ledger_id)` 或同一 promotion chain 没有其他 outstanding live admission；目标硬件、SDK、schema、writer、reconciliation 与相应 `LiveStageGate.admission_verdict` 全部 PASS。实际 submit 还必须来自合法 BUY-only 模型 intent 并通过逐单 preflight；运行结束后的 `LiveStageGate.completion_verdict=PASS` 只负责签发本阶段结果 receipt，不能倒置为启动前置条件。任一 admission 条件缺失或不匹配都必须 fail closed，active 状态或用户授权任何一项单独存在都不构成下单权限。

  ## 九、硬件与训练效率要求

  1. 训练设计必须考虑硬件使用效率，而不是只让代码能跑。
  2. 计划最高使用 4 张 NVIDIA RTX 5090；对应资源按用户当前配置记录为：4 张 NVIDIA RTX 配置合计约 148G VRAM、100 vCPU、360GB RAM；单卡配置为
  NVIDIA RTX 5090 32GB VRAM、25 vCPU、Intel Xeon 8470Q、90GB RAM。
  3. 由于 32GB * 4 与 148G VRAM 存在口径不一致，需求中必须要求运行时用 `nvidia-smi`、`lscpu`、`free`、cgroup limit、driver/runtime manifest
  固化实测值，以实测值作为调度和验收依据。
  4. 必须建立 5090 run manifest/profiler contract，记录 Python interpreter、git commit、sync root、batch size、num workers、shard、epoch time、GPU util、VRAM、CPU、RAM、IO、throughput、质量指标。
  5. 不得用单一 GPU 利用率或单一 batch size 判断训练成功。
  6. batch 变大不必然更好；必须同时比较吞吐、显存、内存、rolling worst、验证集质量和端到端训练时间。
  7. DataLoader worker、prefetch、shard、cache、validator materialization 必须有 profiler 证据后再调整。
  8. 训练服务器内存、CPU、GPU 随 GPU 数增加而成套增长，但系统仍必须支持单卡、双卡、四卡分级运行。
  9. 训练模块必须系统探索当前模型框架在不同神经网络层数、深度、宽度、hidden/state 维度、参数量、序列/记忆容量及训练参数下的交易能力；训练参数至少覆盖经预注册的 optimizer、learning rate、batch、regularization、loss/reward 配置、seed 和训练轮次，不得把单一小模型配置预设为最终答案。
  10. 候选比较必须在相同数据、BUY-only 动作合同、两种盈利机制、`sim-system` 版本、评估区间和资源预算合同下进行，以交易能力、风险、稳定性、校准、结算后收益和资源成本共同判断，不能只按参数量、训练 loss 或单一 leaderboard 指标选择。
  11. 当前 live-trade 交易服务器的 CPU、内存或推理能力不得成为训练阶段选择神经网络层级、模型容量和体积上限的先验硬限制，也不得因此提前排除、压缩或降级交易表现更好的较大模型。
  12. 如果胜出候选超过当前交易服务器的推理延迟、内存或稳定运行能力，必须在独立字段或部署 gate verdict 中记录 `deployment_hardware_status=requires_hardware_upgrade`，不得改变其 active/shadow/candidate/retired ModelRegistry 状态。系统必须保留其原始模型与交易能力证据，并在用户升级交易服务器后重新执行 runtime parity、延迟、内存和长运行 gate；硬件升级完成前不得部署该候选，但也不得仅为适配旧服务器而自动改选较弱模型。
  13. 交易服务器可以升级不等于部署门取消。任何模型进入 paper 前必须在 paper 目标硬件上通过相同输入、输出、数值 parity、事件到 intent 延迟、峰值内存、连续运行和 fail-closed 验收；进入 live shadow 或任一真实资金档前，必须在最终 live 目标硬件上重新通过对应验收。live 目标硬件不足不得反向阻断训练完成、offline-evaluation 或不依赖该硬件的 paper 资格，只能阻止 live 部署并保留 `deployment_hardware_status=requires_hardware_upgrade`。

  ## 十、P0 gates 与验收边界

  核心重构必须至少包含以下 P0 gate 或等价机制：

  1. OnlineFeedbackGate：online-feedback 规则版本、真实平台潜规则和 issues 是否已纳入。
  2. ModelBundlePreflight：模型bundle、pipeline core identity、pipeline config/state schema、Observation/feature schema、normalization artifact、ONNX/runtime、固定BUY-only trading/risk action surface、两种盈利机制、decision trigger/schedule contract、scheduler kind、runtime-owned scope registry/总bound、离散bucket/min/max、base/due-time、timer排序/抢占/restore/overdue/bootstrap、调度成本或决策预算与模型可见事件合同是否匹配，并拒绝任何自有SELL能力、外生固定decision tick、非法/缺失调度输出、模型创建/改绑scope或offline-evaluation/paper/live重拟合normalization的路径。
  3. MarketDiscoveryGate：active/next market、token、tick、min size、start/end、market lifecycle state 与 runtime role 是否可靠。
  4. MarketSwitchGate：active 与 prefetched context 是否隔离，切换是否可审计；旧 market 只有满足 `market_resolved` 事件路径或 fallback metadata retired predicate 后才能进入 retired，否则只能标记 stale/gap/quarantine。该 gate 只产生 verdict、隔离或切换阻断 effect，不是执行 actor；切换期间仍可由各自权威事件路径处理既有模型 cancel intent、平台到期/关闭或 operator emergency cancel，但 gate 与 market switch 都不得自行生成策略性撤单。
  5. ResourceWatermarkGate：CPU/RAM/VRAM/IO/disk/artifact writer 是否满足阈值，并覆盖 writer queue、flush/finalize latency、backpressure 和 ResourceWatermark 阈值动作。
  6. HardwareTierGate：单卡/多卡训练配置、实际硬件、运行参数是否匹配；训练候选容量探索与最终部署硬件准入必须分开判定，不得用当前交易服务器配置提前裁剪训练候选。
  7. SupplyChainGate：SDK、依赖、模型 artifact、数据 artifact、部署产物 sha256 是否可追踪；外部 repo、脚本和依赖默认 pinned readonly，不得默认 install/run、读取 secrets 或联网出站，任何例外必须有隔离环境、审批和审计 artifact。
  8. TrainingFeedbackGate：真实交易反馈、paper 反馈、market supervision labels、execution-feedback labels、reward signals、online_rule_version、内部 split、训练批次排名表是否各自闭环且未混入模型可见 Observation；必须验证本次训练实际消费的 data/schema/manifest/split/causality、normalization、RewardContract、artifact identity 和 `sim-system -> NOE -> trial ledger` 的可回放完整性。尚未成为本轮冻结必需输入的 paper/live feedback 缺失或覆盖不足只能形成 coverage WARNING，不能阻止训练完成；execution reality、PBO/DSR 和训练内表现必须进入报告，但未经独立下游证据校准的弱表现只能形成 WARNING/排名/研究证据，不能自动 early-stop、据此 `FAIL_CLOSED_TRAINING`、阻止合同有效产物落盘或把训练内评估冒充晋级 verdict。
  9. ModelIntentBridgeGate：BUY-only 模型 trading/risk intent、独立decision schedule intent、两者各自唯一consumer、trigger_event_id到模型调用与两类intent的可审计映射、live-trade发送合同、平台反馈回传合同和“禁止live-trade改写模型交易/风控决策、禁止scheduler把wake改写为策略动作”的边界是否满足。
  10. DataIngestRuntimeGate：`data-collect` 与数据消费运行时是否满足 Rust async/non-blocking、bounded queue、writer lag、backpressure、source health/gap/reconnect trace、上游 availability degradation 下的 source-local 无限恢复和 training collector 进程连续性、事件排序/去重/market 隔离、finalized-only discovery、temp/running/rsync-partial 排除和 blocking pool 隔离。
  11. SimSystemFidelityGate：training、offline-evaluation 与 paper 是否共同调用同一版本化 `sim-system`，BUY-only FOK/FAK/GTC/GTD、两套订单单位合同、实际 maker/taker role、single response object/batch response array envelope、batch 逐项 mixed outcome 与关联证据、FIFO 项目规则假设、resting order 在 engine acceptance time 的同价队尾入队、因果前方量更新、shares 数量守恒、pUSD 现金守恒、venue dust terminal、模型单笔/全部撤单、取消竞态、raw evidence -> NOE -> ledger、规则 provenance 和不确定性场景是否闭合；还必须核验爱尔兰延迟 profile 的 dataset/filter/sample/provenance/hash、request/feedback 各 leg 未重复计时、平台真实状态与客户端可见状态分离、single/batch submit envelope 及其整体超时/丢失/解析失败、create-order/submit response 与 user-channel 的先到/后到/同毫秒/迟到/缺失矩阵、cancel 到达前平台实际 executed/open quantity 的因果推导、dust close 的 `cash_balance_pusd` / reserve / `available_cash_pusd` 分账，以及相同 profile+seed 的逐事件确定性重放。不可见事件、通道可见性和 L2 变化归因使用版本化情景假设；FIFO 入队顺序保持冻结，matched-cancel 由平台状态机因果推导，入站观测 profile 继续保持项目代理假设边界。
  12. ModelCapacityExplorationGate：当前模型框架是否在预注册、公平预算内探索不同神经网络层级、容量和训练参数，是否用交易能力而非当前交易服务器硬件作先验筛选；较大胜出模型是否以独立 `deployment_hardware_status=requires_hardware_upgrade` 或等价 gate verdict 保留，并在升级后的目标硬件上重新验收，且没有污染 ModelRegistry 状态。
  13. ObservationParityGate：training offline-replay、offline-evaluation offline-replay、paper online-stream、live online-stream 是否分别运行隔离实例并调用同一pipeline core与decision scheduler。第一层必须把同一批可关联、被`ObservationContract`准入的source evidence分别编码为finalized typed raw与realtime handoff，验证经共享semantic canonicalizer后的canonical event id、payload、causal-availability、model-visible coverage/confirmed-gap字段和total-order-key digest精确一致；collector-only transport/subscription health/reconnect诊断必须在独立data-collect验收中验证，不得作为online-only Observation字段或trigger混入该parity。第二层必须使用同一canonical event tape、内容及sequence/digest相同但来自隔离实例的ledger projection、相同initial state/checkpoint、causal cutoff、pipeline config/state schema、normalization artifact、bundle与schedule contract，验证runtime-owned scope registry、timer create/cancel/replace/generation、模型可见事件抢占、同刻排序、base/due-time、restart/checkpoint restore、overdue单次late fire、decision count/order、trigger event、Observation非浮点/规范字段和按冻结canonicalization/量化规则计算的hash精确一致，模型tensor浮点字段处于冻结数值容差内。还必须覆盖cold start/T-30 bootstrap、restore有有效pending wake、restore无timer时单次`DecisionBootstrapEvent`、reset、gap/backfill、全部外部源静默、wake前事件、事件前wake、同刻冲突、late fire和失效timer；若测试reconnect，只能比较其后实际进入canonical tape的source evidence与状态影响，不能伪造或要求模型看到未持久化的transport cause/episode。验收必须证明不存在影子canonicalization/feature/normalization/Observation/scheduler路径和label/reward泄漏。任何first-divergence必须生成可审计artifact，并按scope阻止training candidate有效性、offline-evaluation receipt、paper或live部署。
  14. TrainingCandidateGate：训练 run 是否只因数据/因果/合同/数值/账本/Reward/artifact 的确定性无效问题 fail closed；未经独立下游证据校准的训练内弱表现是否只形成 WARNING、排名或研究证据且不自动 early-stop；停止是否仅因确定性无效或预注册的非表现资源预算，并保留可恢复 checkpoint；唯一 candidate 是否在留出集解析/暴露前冻结并生成有效 `TrainingCandidateReceipt`。只有 Promotion Controller 可以消费该 receipt 注册 ModelRegistry candidate。
  15. OfflineEvaluationGate：是否在 candidate、evaluation contract、阈值、baseline policy、initial Ledger policy 和 scenario/seed set 冻结后，通过确定性 cutoff 从全部合格集合自动选择 end_time 最新、完全未进入 adaptive lineage 的时间外留出集，并由独立 runtime 对最终 ModelBundle 完成闭环评估；是否具备 non-overlap/purge/embargo、coverage、外生评分 maturity、本候选执行结果 maturity、baseline、统一初始账本/scenario/seed、ledger economics、settled PnL、风险、执行现实、统计不确定性和全部 identity 证据。首轮或未经 offline -> paper/live 独立配对证据校准时，利润、Sharpe、fill rate、胜率等表现阈值必须 advisory；数据或统计证据不足必须 QUARANTINE 而不是判模型 FAIL。完整合格数据上只有按本文受限 hard criteria 得到的 `gate_verdict=PASS` 才能签发 `OfflineEvaluationReceipt` 并允许进入 paper，WARNING、QUARANTINE、FAIL_CLOSED 都不得推进。
