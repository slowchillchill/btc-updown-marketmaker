## 1. 业务目标

本事项要把现有交易系统重构为一条可验证、可审计、可回放、能够反映真实平台约束的统一
业务链路，使同一套市场事实、模拟执行、账户经济和模型合同能够支撑训练、独立离线评估、
模拟盘和实盘，同时避免不同运行模式各自形成影子数据解释、影子订单解释、影子账本或影子
交易客户端。

重构结果必须覆盖重构前错误台账中的问题类别，但单条历史事故只作为证据，不把范围扩张为
无边界重写。

## 2. 业务范围

1. 项目只支持 Polymarket Global CLOB 的 `btc-updown-5m` 完整市场生命周期；当前主动交易
   动作面固定为 `BUY-only`，通过买入两个结果侧表达方向，不建设自有 SELL 路径。
2. training、offline-evaluation、paper 和 live 必须共享同一版本化市场语义、模型输入、
   执行意图、订单与经济反馈、账户投影和审计合同；各角色的进程、运行状态、权限、数据集、
   账本实例和产物必须隔离。
3. 模型或模型包状态机是交易、风险和稀疏决策调度意图的唯一业务来源。数据、模拟器、执行
   适配器、门禁和交易程序只能验证、允许或阻止意图，不能替模型生成或改写策略动作。
4. `sim-system` 是 training、offline-evaluation 和 paper 共用的唯一模拟平台。它必须基于
   可追溯的平台规则和真实证据，模拟订单生命周期、成交与撤单竞态、平台约束、手续费、
   maker/taker rebate、结算、时延与可见性，并保持确定性、因果性、账户隔离和资源有界。
   live 不得调用模拟器生成或覆盖真实执行事实。
5. 真实平台和模拟平台的原始证据必须经过同一归一化合同和各自隔离的本地 Ledger，形成可
   重建的现金、预留、持仓、订单、返佣应收款、NAV 和 PnL；同一经济价值不得重复入账或重复
   进入训练奖励。
6. 训练必须使用可追溯、最终化且显式准入的数据。当前训练、开发、校准和评估数据的谱系根
   固定为 `/home/chillchill/new-datasets`，UTC 日不得早于 `2026-07-30`；达到日期下限不自动
   取得任何数据集归属。
7. 训练必须在公平的数据、模拟器、账本、奖励、评估和资源合同下探索不同模型容量与训练
   参数，冻结不可变候选。当前交易服务器能力不得反向成为训练候选容量上限；不满足目标硬件
   的候选只能被部署门阻断，不能被静默降级或淘汰。
8. 模型生命周期必须依次经过训练候选、独立 offline-evaluation、paper、live shadow 和逐档
   真实资金验证。ModelRegistry 状态、晋级阶段、单次资金授权和执行权限必须分离；任何阶段
   不得跳级，每次真实资金运行都必须取得针对该次运行的用户明确授权。
9. 实盘交易的构建、SDK、模型产物、钱包、服务器和部署边界必须失败即关闭。Polymarket 的
   认证、签名、下单、撤单和查询只能使用官方 Rust SDK；已经单独批准的 `sim-system` 公共
   规则只读冷启动例外不得扩展到交易或账户能力。

## 3. 固定交付顺序与归属边界

当前跨模块主线固定为：

```text
已完成 data-collect(training)
  -> data-pipeline(training) 门 A：REAL_EXECUTION_TAPE_READY
  -> sim-system 黄金事件与真实管道事件联合验收
  -> 外部归一化与 training Ledger 能力就绪
  -> data-pipeline(training) 门 B：TRAINING_DATASET_READY
  -> model-train
  -> 独立 offline-evaluation
  -> paper
  -> live shadow
  -> 逐次用户授权的真实资金阶段
```

`data-pipeline(training)` 门 A、门 B、公共 V2 合同和两类回执由
`plan/data-pipeline-training-plan.md` 唯一拥有；rebuild-core 只消费其合同与回执，不实现、
复制或签发 DPT 产物。`sim-system` 的领域实现与验收由 `plan/sim-system-plan.md` 唯一拥有；
rebuild-core 只负责跨模块顺序、身份绑定和总集成证据。

## 4. 非范围

- 不重开或改写当前 `data-collect` 生产实现、schema、数据、服务或部署。
- 不把 `data-pipeline(training)`、`sim-system`、外部归一化层、Ledger、`model-train`、
  offline-evaluation、paper、live、Promotion Controller 或 `sim-calibration` 的归属实现复制进
  总集成层。
- 不建设第二套原始数据排序器、特征流水线、模拟器、订单归一化器、账本、SDK 客户端、
  训练框架或规则引擎。
- 不读取、迁移、回填、统计、拟合、训练、校准或评估日期下限前的数据，也不以当前平台值
  回填历史运行。
- 不授权远端操作、部署、推送、外部发布、敏感材料访问、钱包操作、真实下单或真实资金。

## 5. 验收标准

1. 重构前错误台账中的每类问题都能追溯到计划任务、真实测试或验收证据，且没有无关扩张。
2. 合格真实数据能够确定、因果且可追溯地进入唯一市场事件合同；黄金事件不能替代真实纵向
   链路，真实纵向链路也不能替代归一化与 Ledger 闭环。
3. training、offline-evaluation、paper 和 live 在相同因果输入与合同下产生一致的市场语义
   和模型输入，同时保持运行实例、权限、状态和产物隔离。
4. `sim-system` 对固定规则、事件、请求、场景和随机种子的结果可逐事件重放，并覆盖真实订单
   生命周期、平台竞态、返佣和结算；live 依赖图与运行路径均不可达模拟器。
5. 订单、现金、预留、份额、返佣、NAV 与 PnL 可由原始证据、归一化事件和 Ledger 重建，
   任一重复、迟到、缺失或重放不会重复应用同一经济变化。
6. 模型是交易、风险和调度意图的唯一来源，全链路只有自有 BUY 动作；所有执行结果、阻断和
   权限变化都有可审计映射，且不存在策略改写或影子执行路径。
7. 模型训练、未见数据评估、paper、live shadow 和真实资金阶段不可跳级；任何缺失、失效或
   不匹配的凭据、身份、权限或单次授权都会阻止下一阶段。
8. 数据、代码、依赖、模型、运行时、规则、配置和产物身份均可追溯并可哈希；失败或中断不
   留下半成功产物，资源使用具有实测硬上限。
9. 目标发布依赖与运行边界可由实际构建产物证明；live 服务器不承担 Rust 构建、训练或离线
   重处理，模型与敏感材料不通过 Git 混合分发。
10. 需求、计划和 changelog 职责清晰且相互一致：需求保持宏观，计划独占当前业务与技术规范，
    changelog 只记录事实与取代关系；全部未决项和未授权动作保持明确阻断。
