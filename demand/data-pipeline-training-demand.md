## 1. 用户冻结的目标与新顺序

用户在 2026-08-03 确认：此前先独立完成 `sim-system`、再建设
`data-pipeline(training)` 的顺序有误。真实类型化原始数据已经由
`data-collect(training)` 采集并形成样本，模拟器需要尽早接受真实、规范、同因果边界的
市场事件验证；但完整训练 Observation 又需要模拟反馈、外部归一化层和 Ledger 投影。
因此当前顺序固定为：

```text
1. data-collect(training)                                      [已完成]
2. data-pipeline(training) 需求批准与共享合同冻结
3. data-pipeline(training)-A 上游投影门
   最终化 typed_raw -> 唯一规范事件带 -> ExecutionMarketEvent
   + 同源市场侧 Observation
4. sim-system
   黄金事件组件验收 + 真实管道事件纵向验收
5. data-pipeline(training)-B 训练闭环门
   归一化反馈/Ledger 投影合并 -> 完整 Observation
   -> 标签、切分、归一化与训练产物
6. model-train
```

`data-pipeline(training)-A` 和 `data-pipeline(training)-B` 是同一模块、同一版本化代码库、
同一唯一语义规范化核心的两个交付门，不是两套管道、两个规范事件真相或可独立演进的
实现。门 A 的通过不能冒充训练数据集已经就绪；门 B 未通过时不得进入 `model-train`。

本需求只覆盖离线训练角色。`data-pipeline(offline-evaluation)`、
`data-pipeline(paper/live)` 的运行方式需要在对应模块进入活动范围时另行批准；后续若复用
本文定义的核心，也必须保持运行实例、输入权限、状态、检查点、产物根和 Ledger 投影隔离。

## 2. 模块定义、唯一职责和边界

### 2.1 唯一职责

1. `DPT-G-001`：`data-pipeline(training)` 是六类已解码类型化原始源证据到唯一规范
   市场事件带的唯一语义归属方。它负责准入、无损读取、字段/单位/枚举规范化、因果
   可用性、稳定全序、按事件类型去重、缺口/陈旧/重同步、市场隔离和规范身份标识。
2. `DPT-G-002`：`ExecutionMarketEvent` 与 `ObservationContract` 必须从同一规范
   事件带派生，并绑定相同的规范事件谱系、全序键、因果截止点和输入摘要；不得分别实现
   两套源解释、排序或状态重建路径。
3. `DPT-G-003`：门 A 负责把真实市场证据投影为可由 `sim-system` 消费的
   `ExecutionMarketEvent`，并生成不含账户/执行反馈的市场侧 Observation 因果外壳。
4. `DPT-G-004`：门 B 在 `sim-system -> 外部归一化层 -> 调用方自有 Ledger` 合同可用
   后，只读合并本训练实例的 Ledger 投影，补齐完整 Observation、成熟标签、训练切分、
   归一化产物和可复现训练数据集。
5. `DPT-G-005`：模块不得拥有或改变采集器、模拟平台、订单、账户、NOE、Ledger、奖励、
   模型训练或晋级状态。读取 Ledger 投影不产生写权限；构建执行反馈标签不产生平台事实。
6. `DPT-G-006`：所有输出必须是框架中立、版本化、可哈希的领域/列式合同；不得直接输出
   PyTorch、JAX、TensorFlow 或其他训练框架私有运行时对象。

### 2.2 唯一允许的数据流

```text
data-collect(training) 最终化 typed_raw + 每日清单
    -> data-pipeline(training) 唯一规范化核心
       -> 规范事件带
          -> ExecutionMarketEvent -> sim-system
          -> 市场侧 Observation 因果外壳

sim-system 原始反馈
    -> 外部归一化层 -> training Ledger
       -> 只读 Ledger 投影 -> data-pipeline(training)-B
          -> 完整 Observation + 成熟标签 + 训练数据集
             -> model-train
```

### 2.3 禁止的数据流

以下路径不成立：

```text
typed_raw / Parquet / data-collect 运行时 -> sim-system
data-pipeline -> data-collect 写入器或采集运行时
data-pipeline -> sim-system 内部订单簿、账户或随机状态写入
data-pipeline -> NOE / Ledger 写入
data-pipeline -> RewardContract / 奖励 / 模型筛选
未来结果 / 标签 / 模拟反馈 -> 因果 Observation 的过去截点
model-train / sim-system / 验证器 -> 第二套原始数据排序或语义规范化
门 A 临时实现 -> 门 B 另一套正式实现
```

## 3. 两级完成门

### 3.1 门 A：`REAL_EXECUTION_TAPE_READY`

门 A 的目标是建立最小但真实的上游纵向链路：

```text
已准入并最终化的 typed_raw
-> 唯一规范事件带
-> 稳定全序、因果可用性、去重和状态转换
-> ExecutionMarketEvent + 同源市场侧 Observation 因果外壳
```

门 A 到上述产物及其独立合同/能力验证为止，不以 `sim-system` 实现或集成结果作为自身
通过条件。`sim-system` 的真实管道事件纵向门在门 A 之后独立验收；若该门发现生产者和
消费者合同不兼容，必须形成跨模块失败回执并修复相应归属方，但不能把尚未发生的下游
集成倒置为门 A 的前置条件。

门 A 每次评估都必须输出带能力范围和 `tape_assessment=PASS|PARTIAL|FAIL` 的门回执。
`tape_assessment` 只描述本事项的真实事件带评估，不替代或映射
`rebuild-core` 的跨范围 `gate_verdict`。只有全部必需能力通过且
`tape_assessment=PASS` 时，才能签发状态
`REAL_EXECUTION_TAPE_READY`。若当前输入只能满足 L2、公开成交、价格、外部参考价或
市场判定等部分语义，只能输出状态 `REAL_EXECUTION_TAPE_PARTIAL` 和未通过能力；该状态
不是就绪回执，不能满足门 A 或 `sim-system` 面向真实训练需要的完成条件。CLOB
`min_order_size`、逐市场 `feeSchedule`、`itode` 和其他低频平台规则不属于门 A 事件带
字段，也不影响 `REAL_EXECUTION_TAPE_READY`；它们由 `sim-system` 新运行冷启动通过固定的
官方公开 HTTPS 窄加载器查询并冻结。日期早于 `dataset_date_floor` 属于输入准入失败，不能
降级为 `PARTIAL`。

门 A 不包括：外部归一化层、Ledger 写入、完整账户 Observation、执行反馈标签、奖励、
最终训练切分、归一化拟合或模型训练。

### 3.2 门 B：`TRAINING_DATASET_READY`

门 B 必须在有明确批准归属的实现已经以通过证据证明 `sim-system` 原始反馈、外部归一化
合同及实现、training Ledger 及其只读投影可用后完成；本事项只消费这些外部产物，不负责
补实现归一化层或 Ledger。最终回执必须绑定 `sim-system` 组件符合性回执、DPT/sim 联合
真实纵向回执、外部归一化合同/实现回执和 training Ledger/只读投影回执各自的 ID 与
SHA-256，还必须绑定以同一门 B 候选运行的 `sim-system` 阶段 7 联合训练闭环证据 ID/SHA；
该证据与 `DPT-AC-013` 是同一次联合运行，不得重复建设第二套闭环。最终回执再按后续用户
对正式时延配置档门时序的决定绑定适用状态和身份。

当前已确定的是三项外部能力和四类机械回执；尚未确定的是批准归属应为两个事项还是三个
事项：`sim-system` 始终由其独立事项负责，外部归一化与 training Ledger 可以由
`rebuild-core` 同一批准范围覆盖，也可以各自由独立事项覆盖。现有 `rebuild-core` 计划采用
前一种结构，而本需求早期草案曾直接写成三个事项，二者没有可引用的用户决定可以自动裁定。
该选择必须在受影响的门 B 工作开始前由用户决定，但不阻断门 A。无论选择哪种结构，均只
批准相应需求与计划一次，不要求用户逐份人工批准四类回执；DPT/sim 联合真实纵向回执是
双方共同验收证据，不构成额外事项批准门。

1. 合并同一训练实例的只读 Ledger 投影和市场侧状态；
2. 冻结完整 `ObservationContract`、决策因果截止点与触发合同；
3. 生成成熟的市场监督标签和执行反馈标签，显式处理未成熟、删失和未知；
4. 冻结严格时间前推的训练/开发/校准边界及其清洗期、隔离期；
5. 只用训练许可范围拟合归一化产物；
6. 原子发布完整训练数据集、清单和 `TRAINING_DATASET_READY` 回执。

门 B 未通过时，门 A 产物只能用于管道/模拟器开发、符合性测试、性能分析和受控研究，
不得启动正式 `model-train` 或签发训练候选有效性凭据。

门 B 完成的是训练数据底座、动态回放接口和反馈闭环能力，不要求在模型训练开始前预先
生成尚不存在的模型动作及其全部模拟反馈。验收可以使用冻结的确定性脚本意图建立闭环；
正式训练中的模型动作仍须在各自训练运行内经共用桥接器、`sim-system`、外部归一化层和
本实例 Ledger 形成反馈，再由同一个处理核心生成后续 Observation 和达到成熟度的样本。
`TRAINING_DATASET_READY` 不得被解释为未来模型相关轨迹已经预知或物化。

### 3.3 两门的共同身份

两个回执必须绑定相同的 `pipeline_core_identity`、规范事件合同版本、
`dataset_lineage_root`、`dataset_date_floor`、精确 UTC 日期/范围、输入清单及 SHA-256、

`training_split_manifest_id/hash`，并引用同一输入谱系的门 A 回执；
不得扩展到日期下限前、未分配或未被该门 A 回执覆盖的数据。
门 B 还必须增加前述四类外部通过回执及同一候选的 sim 阶段 7 联合训练闭环证据 ID/SHA、

全序、字段语义或因果时间的修改都必须发布新合同版本，
重新生成受影响的门 A 产物，并使旧门 B 回执失效。

## 12. 失败语义、安全和依赖

1. 日期早于 `dataset_date_floor`、未知 schema、路径逃逸、路径/分区/清单日期不一致、
   清单/文件摘要不符、必需身份矛盾、规范数量不守恒、无法建立
   唯一全序、输出摘要不一致或内部不变量失败，必须使受影响运行失败且不发布成功回执。
2. 可定位到单一市场/范围的业务缺口、无效证据或不支持规则可以按版本化政策隔离；隔离
   必须保留原因、范围和数量，不能升级为成功样本或污染其他市场。
3. 管道必须默认离线运行，不访问网络、钱包、交易凭据或真实平台。不得调用原始 REST、
   手动签名、重放真实订单或从互联网补齐当前输入缺失字段。
4. 实施时优先复用成熟的 Arrow Dataset、PyArrow/Arrow、Parquet 和现有 Rust/仓库依赖
   的明确能力；精确语言/依赖选择、版本、许可证、安全公告和锁定方式由计划阶段验证。
   不得自研 Parquet、通用排序数据库、调度器或训练框架替代品，除非已证明成熟工具无法
   满足冻结合同并取得用户决定。
5. 外部库只能处理 I/O、列式计算和通用算法；本项目的因果、去重、市场状态和合同语义
   必须存在唯一、可测试的本地薄层，不能隐含在不可审计的默认行为里。

## 13. 已知上游缺口和决策门

截至 2026-08-04，已确认：

1. metadata v5 schema 没有专用 `min_size`、`fee_schedule_raw`、`feeSchedule`、`itode` 或
   `rebateRate` 列；旧 `min_size` / `fee_schedule_raw` 只属于旧 metadata 布局或发现阶段
   内存结构。低频平台规则已经明确不属于 `ExecutionMarketEvent`，因此这不是门 A 的上游
   字段缺口，也不要求重开 `data-collect`。
2. 当前四日合格数据共 491 个 Parquet、151,056,246 行、9,202,902,694 字节；metadata 为
   97 个 v5 文件、4,620 行、4,119,473 字节。1,167 个 Gamma 原始证据载荷中存在
   `orderMinSize`、`feesEnabled`、旧手续费及其他同名或相似键，但它们是采集时点的原始
   证据，不是模拟器新运行的规则配置。
3. 同时删除十个相似键的反事实 ZSTD-3 压缩收益约 9,317 字节，只占 metadata 的约
   0.226%、全部合格数据的约 0.000101%，并要求重写载荷和关联摘要。当前不存在语义上可
   安全删除的重复字段；`data-collect` 不新增规则专用列，也不删除现有证据 JSON 键。十个
   键的观测值、逻辑字节和逐键压缩反事实由
   `data-collect/docs/current/contracts.md` 第 3 节唯一记录。
4. 四日数据实际有 624 条 `tick_size_change`，涉及 156 个市场，均为 `0.01 -> 0.001`；
   `old_tick_size/new_tick_size` 是运行中动态事实，必须继续进入规范事件带，不能由冷启动
   `initial_tick_size` 替代。公开成交 `fee_rate_bps` 同样是事件证据，不是
   `feeSchedule`。
5. RTDS v4 没有独立采集器接纳时间/序号，只能显式降低该源的排序与因果证据质量。
6. 2026-07-31 清单能证明发生缺口和日内重新激活，但自由文本不能证明精确缺口区间。
7. 公共 L2 没有逐订单队列身份，`price_change` 与 `last_trade_price` 没有共同权威因果
   ID，不能声明真实 FIFO、精确账户成交或精确成交到价位变化归因。
8. 当前样本没有账户提交/撤单/`user-channel`/Ledger 证据，不能生成执行反馈标签或校准
   全部模拟平台行为。

`sim-system` 的冷启动规则来源限定为固定的官方公开 HTTPS 端点，并由窄类型响应加载器
只解析首版已定义消费者所需的字段。官方 Rust SDK 的类型覆盖缺口不再阻断该加载器；但
平台响应缺少必需字段、字段非法、条件/市场/代币身份不一致、重复结果冲突，或 CLOB 与
Gamma 的交叉绑定冲突时，受影响的模拟器冷启动能力仍必须失败即关闭。首版未消费的 `oas`
只登记为未消费字段，不单独阻断冷启动。本管道本身继续保持完全离线，不得调用该加载器、
访问任何 REST/HTTPS 端点、手动解析平台响应、自建 SDK、硬编码或改名补齐缺失字段。若本文、
`data-collect` 当前事实、下游合同、代码、真实样本或用户最新决定冲突，必须停止受影响的
需求判断或实施，列出精确位置、影响和现实选项交由用户决定。
